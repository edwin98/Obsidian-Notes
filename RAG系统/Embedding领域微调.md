# Embedding 领域微调

完整维护 Bi-Encoder、难负样本、对比损失、GradCache、多维表示与领域评测。共同训练闭环和部署见 [[RAG系统/03_Embedding与Reranker微调全流程]]；项目规模与配置以 [[RAG系统/项目事实与实现状态]] 为准。

## Embedding：模型、数据与训练

### 2.1 架构选型：为什么用 Bi-Encoder

Embedding 模型承担 **离线入库 + 在线查询编码** 两个职责，对延迟和吞吐量要求较高。

| 架构 | 延迟 | 适用场景 |
|------|------|----------|
| Bi-Encoder | 查询与文档独立编码，文档表示可预计算 | 大规模召回（百万级） |
| Cross-Encoder | 每个候选与查询联合编码，成本随候选数增长 | 精排（百级） |

Bi-Encoder 的核心优势是**向量可以预先离线计算并缓存**，查询时只需对 Query 编码一次，然后做向量相似度检索（ANN），这是常用的大规模语义召回路线；词法、稀疏与多向量路线也可用于召回。单向量压缩会损失细粒度信息，效果差异需按任务比较。

本系统选用 `gte-multilingual-base` 作为统一的 Bi-Encoder，模型默认 768 维，并支持弹性稠密表示；本项目采用 **384 维**和 **768 维**两档，不表示只有这两种可用维度。[GTE 模型卡](https://huggingface.co/Alibaba-NLP/gte-multilingual-base)

- **384 维**：负责第一层粗筛，优先保证吞吐量
- **768 维**：结合用户 SAP 画像做第二层精筛，优先保证语义覆盖

#### 单稠密、稀疏与多向量表示

| 表示方式 | 文档表示 | 匹配特点 | 主要代价 |
| --- | --- | --- | --- |
| 单稠密向量 | 文档压缩成一个向量 | 适合较低成本的语义召回 | 细粒度内容可能被压缩。 |
| 稀疏向量 | 只有部分词项或特征维度非零 | 有利于词项与术语匹配 | 依赖对应的稀疏索引与表示规则。 |
| 多向量 late interaction | 保存 token 或图像 patch 等多个表示 | 在打分阶段保留细粒度交互 | 存储和打分开销较大。 |

多向量不是把单向量的维度调大，也不能直接当作原单向量索引的等价输入。Sentence Transformers 6.x 提供 `MultiVectorEncoder`，覆盖 ColBERT/ColPali 等路线；稀疏表示则有 `SparseEncoder`。[官方迁移指南](https://www.sbert.net/docs/migration_guide.html)

### 2.2 基座选型

基于以下维度筛选基座：

- **多语言支持**：系统同时处理中文技术文档和英文协议标准
- **参数量与延迟**：线上推理延迟约束 < 50ms（单查询 P99）
- **预训练语料**：是否包含技术文档/代码相关语料，影响迁移学习的起点

候选基座对比：

| 模型 | 参数量 | 最大序列长度 | 多语言 | 说明 |
|------|--------|-------------|--------|------|
| BGE-M3 | 568M | 8192 | 是 | FlagEmbedding 系列，支持稠密+稀疏+多向量，但参数量偏大 |
| E5-mistral-7B | 7B | 模型卡示例 4096 | 部分，官方建议英文 | 需使用 query 指令，长输入与在线成本单独评估 |
| multilingual-e5-large | 560M | 512 | 是 | 基于 XLM-R，多语言能力强，但不支持多维度输出 |
| **gte-multilingual-base** | **305M** | **8192** | **是** | **阿里 GTE 系列，推理快，原生支持 384/768 维输出** ✓ |

E5 的模型卡示例、任务指令与语言边界见 [官方模型卡](https://huggingface.co/intfloat/e5-mistral-7b-instruct)。表中的性能描述是项目约束下的候选比较，不能单凭模型规模推导固定延迟。

**选型结论**：选用 `gte-multilingual-base`（305M），它原生支持 384 维和 768 维两种输出维度，可用同一个模型同时满足粗筛和精筛两个通道，节省部署成本。

#### Qwen3 检索模型候选

Qwen3 提供 0.6B、4B、8B 的 Embedding/Reranker 系列。Embedding 支持较长输入和可变维度表示，使用方式还涉及任务指令；Reranker 不能默认套用所有传统 CrossEncoder 的输入和打分流程。

候选比较应同时记录领域效果、显存、输入长度、延迟、指令模板和向量维度。更大的模型不保证在现有领域与负载下全面更优，原 GTE/BGE 等模型仍可作为历史选型与较低成本候选。[Embedding 模型卡](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B)、[Reranker 模型卡](https://huggingface.co/Qwen/Qwen3-Reranker-4B)

### 2.3 数据集构建

训练数据的质量、覆盖范围和标注准确性会直接影响微调效果，应优先检查这些因素，再调整模型与训练参数。

#### 2.3.1 数据格式

标准的对比学习训练样本格式：

```
(query, positive_doc, [hard_negative_1, hard_negative_2, ...])
```

- `query`：用户的自然语言问题
- `positive_doc`：与 query 相关的正样本文档段落
- `hard_negative`：与 query 表面相似但实际不相关的文档段落

#### 2.3.2 正样本来源

**来源一：历史问答日志挖掘**

系统上线后积累的真实问答日志是最宝贵的数据源：
- 用户 Query + 系统返回的 Top-1 文档（被用户点击/采纳则标记为正样本）
- 筛选条件：用户对答案满意（通过显式点赞或对话持续深入来判断）
- 问题：冷启动阶段数据量不足，且存在选择偏置（模型自身的偏好被放大）

**来源二：Qwen2.5-72B 合成问答对（主要来源）**

对每个知识 Chunk，调用 **Qwen2.5-72B** 生成对应的问题，构成 `(合成问题, Chunk)` 正样本对，共生成 **75 万条** QA 语料，经数据清洗与质量过滤后 **48 万条**参与微调训练：

```python
PROMPT = """
你是一个无线通信专家。以下是一段技术文档：

{chunk_text}

请根据这段文档内容，生成 {n} 个不同角度、不同难度的技术问题。
要求：
1. 问题必须能从文档中找到答案
2. 包含概念型、原理型、故障排查型、参数配置型等多种问题类型
3. 问题应使用真实工程师会问的口语化表达
4. 避免直接复制文档中的句子作为问题

输出格式（JSON）：
[
  {{"question": "...", "type": "概念型"}},
  ...
]
"""
```

合成策略要点：
- 每个 Chunk 生成 3~5 个问题，覆盖不同提问视角；知识库共约 19 万个 Chunk，平均每 Chunk 产出 4 个问题，共生成 75 万条原始语料
- 区分 **概念型**（X是什么）、**原理型**（X如何工作）、**配置型**（X参数如何设置）、**故障型**（X场景如何排查）
- 对长文档 Chunk，先用 Qwen2.5-72B 提取关键事实点，再对每个事实点生成问题，避免问题集中在段落前几句
- 选用 72B 而非更小模型的原因：70B+ 量级模型在无线协议等高专业度领域生成的问题更自然、歧义更少，有效降低低质样本比例

**来源三：人工标注（少量高质量种子集）**

- 邀请无线领域工程师人工编写 200~500 个高质量 QA 对
- 这部分数据主要用于：评测集构建 + 对合成数据进行质量校准
- 不应作为主要训练来源，人工标注成本高且容易引入个人偏好偏置

#### 2.3.3 难负样本挖掘（核心环节）

Hard Negative 的质量直接决定模型的区分能力。以下是从易到难的三级负样本体系：

**第一级：BM25 负样本**

对每条 query，用 BM25 检索 Top-K 文档，剔除正样本后剩余的文档即为 BM25 负样本。

```python
from rank_bm25 import BM25Okapi

# 对query做BM25检索，取Top 50，排除正样本
bm25_candidates = bm25_index.get_top_n(query_tokens, corpus, n=50)
bm25_negatives = [doc for doc in bm25_candidates if doc not in positive_set][:5]
```

BM25 负样本的特点：词汇上与 query 高度重叠但语义不匹配，是中等难度负样本。

**第二级：语义相似负样本（ANN 负样本）**

用当前版本的 Embedding 模型对 query 做向量检索，取出语义相近但不相关的文档：

```python
# 用base模型编码query
query_vec = base_model.encode(query)

# 从向量库中检索Top 100
ann_candidates = vector_index.search(query_vec, top_k=100)

# 过滤掉正样本，剩余作为ANN负样本
ann_negatives = [doc for doc in ann_candidates if doc not in positive_set][:5]
```

这类负样本是模型最难区分的，因为它们在表示空间中距离正样本很近。

**第三级：LLM 生成混淆负样本**

针对特别关键或难区分的知识点，用 LLM 专门生成"看似相关实则无关"的干扰文档：

```
对于问题："HARQ 最大重传次数如何配置？"

正样本：【介绍 HARQ 参数 maxHARQ-Tx 配置方法的段落】

LLM 生成混淆负样本：
- 【介绍 ARQ 重传机制的段落】（相关但不相同的技术）
- 【介绍 HARQ 进程数配置的段落】（同技术但不同参数）
```

**负样本质量过滤**

避免假负样本（实际相关但被标记为负样本）污染训练集：

```python
# 用交叉编码器（Reranker）对候选负样本打分
# 得分超过阈值的认为是假负样本，从训练集中移除
reranker_scores = reranker.predict([(query, neg) for neg in candidates])
filtered_negatives = [
    neg for neg, score in zip(candidates, reranker_scores)
    if score < FALSE_NEGATIVE_THRESHOLD  # 通常设 0.3~0.4
]
```

#### 2.3.4 数据增强策略

**查询侧增强**

- **同义改写**：用 LLM 将原始问题改写为不同表达方式（正式/口语、长/短、有缩写/无缩写）
- **跨语言增强**：将中文 query 翻译为英文，或将英文标准文档段落翻译为中文，构建跨语言正样本对

**文档侧增强**

- **Chunk 边界扩展**：正样本 Chunk 随机扩展 ±1 个相邻句子，增加位置鲁棒性
- **摘要替换**：用 LLM 生成 Chunk 的摘要作为正样本变体

#### 2.3.5 数据质量控制

```
Qwen2.5-72B 合成数据（75 万条）
    ↓ 规则过滤（去重、去短文本、去乱码、JSON 格式异常）
约 68 万条
    ↓ 相关性过滤（用现有 Reranker 对 (query, pos) 打分，低于阈值 0.4 过滤）
约 54 万条
    ↓ 假负样本过滤（用 Reranker 对硬负样本重新打分，高于阈值 0.3 的移除）
约 48 万条（最终训练集，共过滤掉约 36% 的低质语料）
```

训练/验证/测试集分割：
- 按**文档**级别分割（而非按样本），避免同一文档的问题同时出现在训练集和测试集
- 比例：8:1:1

### 2.4 训练方法

#### 2.4.0 训练方案设计的核心思考

在进入具体实现细节之前，有必要先梳理这套方案中几个关键决策的底层逻辑。

**为什么用对比学习，而不是分类或回归？**

最直觉的做法是把 Embedding 训练视为二分类：给定 (query, doc) 对，预测是否相关（0/1 标签）。这样做有一个根本缺陷：模型在推理时要在数十万个文档中找出最相关的，这本质上是一个相对排序问题，而不是孤立的二分类问题。用分类训练出来的模型只知道"这个文档相关/不相关"，不知道"这个文档比那个文档更相关"。

对比学习的训练范式与推理任务完全对齐：每个训练样本的结构是"从 N 个候选中找到唯一正样本"，这和查询时"从全库中找最相关文档"是同一个任务形式。这种对齐叫做**训练-推理一致性**（train-test consistency），是对比学习效果好的根本原因。

**为什么 InfoNCE，而不是 Margin/Triplet Loss？**

Triplet Loss 是对比学习的早期方案：要求 `sim(q, d+) - sim(q, d-) > margin`。它有两个工程上的硬伤：

1. **Margin 是固定的超参数**。不同难度的负样本需要不同的 margin，一刀切的固定值意味着对"几乎分不清楚"的负样本惩罚不足，对"差异悬殊"的负样本浪费了梯度信号。
2. **每次只比较一对 (正, 负)**。样本利用率低，且不同 pair 之间的训练信号彼此独立，模型无法感知整个候选集的分布。

InfoNCE 的本质是 Softmax 分类：把正样本的相对得分最大化，所有负样本的得分同时作为分母参与竞争。这意味着：
- 哪个负样本得分最高，它对梯度的贡献就最大（自动聚焦到难样本）
- 一个 batch 内所有文档的分数形成一个竞争场，模型需要同时学会区分所有对比

**温度系数 τ 的几何意义**

温度系数控制的是相似度得分分布的"尖锐程度"。假设模型计算出正样本余弦相似度 0.85，三个负样本分别是 0.80、0.60、0.30：

- `τ = 0.1`：0.85 和 0.80 之间的差距被放大 10 倍，模型会强烈关注最难的负样本（0.80 那个）
- `τ = 0.5`：分布变得平缓，所有负样本都有近似相等的梯度贡献

从优化角度看，小 τ 等价于将 Hard Negative 的权重放大，训练信号更集中但更容易不稳定（梯度方差大）。这是为什么训练初期用较大的 τ（0.05），随着模型逐渐收敛再降低到 0.01~0.02，让后期专注于真正难以区分的样本。

**In-batch Negatives 为什么有效：以及为什么 batch 越大越好**

In-batch Negatives 的核心假设是：随机从数据集里取出来的另一条样本的正文档，大概率与当前 query 不相关——这个假设在大规模知识库场景下通常成立（因为文档话题足够多样）。

从信息论的角度，InfoNCE Loss 是互信息（Mutual Information）下界的最大化：

$$\mathcal{L}_{\text{InfoNCE}} \approx -\hat{I}(Q; D^+)$$

batch size 越大，对互信息的估计越准确（更多负样本 → 更好的负样本分布覆盖 → 更精确的梯度方向）。这也是为什么大规模对比学习（SimCLR、CLIP 等）都需要极大的 batch size，以及为什么这里要用 GradCache 将有效 batch 扩展到 1024。

**三阶段训练的课程学习逻辑**

这套训练流程本质上是课程学习（Curriculum Learning）的工程落地：从简单到难，逐步提升任务难度。

- 阶段一只给合成正样本，任务是"认识领域词汇"，就像先让学生背专业词汇
- 阶段二加入 BM25 + ANN 硬负样本，任务是"区分相似但不同的文档"，相当于开始做难题
- 阶段三用 Reranker 的软标签蒸馏，任务是"学习文档间的细粒度相对排序"，相当于向资深工程师学习隐性知识

如果一开始就只用 Hard Negative，模型可能难以区分领域中的正负样本，导致训练不稳定。因此，本方案先学习较容易的样本，再加入难负例；是否需要分阶段，应通过验证集比较。

#### 2.4.1 损失函数选择

**InfoNCE Loss（主训练损失）**

对比学习的核心，公式如下：

$$\mathcal{L} = -\log \frac{\exp(\text{sim}(q, d^+) / \tau)}{\exp(\text{sim}(q, d^+) / \tau) + \sum_{i=1}^{K} \exp(\text{sim}(q, d_i^-) / \tau)}$$

其中：
- $\text{sim}(q, d)$ = 余弦相似度
- $\tau$ = 温度系数（通常 0.01~0.05）
- $K$ = 负样本数量

**温度系数的作用**：温度越小，对相似度的区分越敏感（梯度集中在难分样本上），但也越容易训练不稳定。通常从 0.05 开始，随训练进行逐步降低到 0.01。

**In-batch Negatives 策略**

同一 batch 内其他样本的正文档自动作为当前样本的负样本：

```python
# batch_size = 64 时，每个样本有 63 个 in-batch 负样本 + 若干 hard 负样本
# 这使得实际负样本数量 = batch_size - 1 + num_hard_negatives

# 实现时需要注意：避免同一文档的变体同时出现在一个 batch 中
# （否则会引入假负样本污染）
```

In-batch Negatives 利用同一次对比损失中的其他正文档作为负例；更多负例是否有益取决于假负样本、批次构造等。普通梯度累积只累加各 micro-batch 的梯度，不会自动扩大负样本池。

**GradCache 技术**

GradCache 将一个逻辑 batch 分块编码、缓存表示并对全批次计算对比损失，再分块重新前向和反向传播。它减少同时保留的编码器激活，以额外重算换取大负样本池；缓存表示/表示梯度仍占显存，不能固定说显存翻倍。

双卡 DDP 默认只同步参数梯度；跨卡负样本需要损失实现额外聚合各卡表示（例如 all-gather）。[Sentence Transformers 损失文档](https://sbert.net/docs/package_reference/sentence_transformer/losses.html)。

#### 2.4.2 多阶段训练策略

**阶段一：大规模弱监督预热（Warmup）**

- 数据：仅用 LLM 合成的 (query, positive) 对，不加 Hard Negative
- 目标：让模型快速适应领域词汇分布
- 训练参数：较大 LR（2e-4），较少 epoch（1~2 轮）
- 原因：此阶段数据质量低但量大，先建立领域基础表示，避免后期 Hard Negative 将模型带入错误方向

**阶段二：Hard Negative 精调（Fine-grained Tuning）**

- 数据：带 BM25 + ANN 硬负样本的完整训练集
- 目标：提升模型对难以区分样本的判别能力
- 训练参数：较小 LR（1e-5~5e-5），更多 epoch（3~5 轮）
- 监控：每个 epoch 后在验证集评测 Recall@10，MRR@10，若连续两轮不提升则停止

**阶段三：Reranker 知识蒸馏**

用已微调好的 `gte-multilingual-reranker-0.3B`（Cross-Encoder）对每个训练样本的候选文档列表打分，将这些连续分数作为软标签蒸馏到 Bi-Encoder。相比硬标签（0/1），软标签保留了文档之间的**相对相关性梯度**，训练信号更丰富。

**蒸馏流程**

```
Step 1：固定 Reranker 权重，遍历训练集
Step 2：对每个 (query, [doc1, doc2, ..., docN]) 组合，让 Reranker 输出分数向量 s = [s1, s2, ..., sN]
Step 3：将 s 经 softmax(s/T) 得到教师软概率分布 p_teacher（T 为蒸馏温度，通常取 1~3）
Step 4：Bi-Encoder 输出候选文档相似度向量 e = [cos(q,d1), ..., cos(q,dN)]
Step 5：将 e 经 softmax(e/τ) 得到学生概率分布 p_student
Step 6：最小化 KL 散度：L_distill = KL(p_teacher || p_student)
```

**联合损失函数**

实际训练中将蒸馏损失与 InfoNCE 损失联合优化：

```python
# alpha 控制蒸馏强度，通常取 0.3~0.5
# InfoNCE 保证正负样本区分，KL 蒸馏注入相对排序知识

loss = (1 - alpha) * InfoNCE(query, pos, hard_negs) \
     + alpha * KL(p_teacher, p_student)
```

**关键工程细节**

- **Reranker 打分缓存**：Reranker 推理成本高，提前离线对所有训练样本打分并缓存为 `.jsonl`，训练时直接读取，不需要 Reranker 在线参与
- **候选文档组成**：正样本 1 个 + BM25 硬负样本 3 个 + ANN 硬负样本 3 个 + In-batch 随机负样本，共 7~15 个文档送给 Reranker 打分
- **蒸馏温度 T**：T 越大软标签越平滑（弱化边界模糊样本的影响），T=1 时等同于直接用原始分数；本系统取 T=2
- **为什么有效**：Cross-Encoder 做 token 级别全注意力，能感知否定词、数字精确匹配、条件依赖等细粒度关系，这些信号通过软标签隐式传递给 Bi-Encoder，使其表示空间更贴近实际相关性

**实际效果**：在验证集上，单纯 Hard Negative 精调后 Recall@10 = 82.3%，叠加蒸馏后提升至 86.7%，提升约 4.4 个百分点。

#### 2.4.4 多维度输出支持

`gte-multilingual-base` 原生 768 维表示采用 Matryoshka 设计，支持前缀截断。Sentence Transformers 用 `truncate_dim`，而非 `output_dim`；截断后重新做 L2 归一化：

```python
# model 为已加载的 SentenceTransformer，texts 为待编码文本
embeddings_384 = model.encode(texts, truncate_dim=384, normalize_embeddings=True)
embeddings_768 = model.encode(texts, truncate_dim=768, normalize_embeddings=True)
```

384 维主要减少向量存储、传输和检索计算；编码器仍执行完整前向，不能据此声称编码耗时减半。领域微调若需保留各截断维度效果，应联合优化对应前缀损失并分别验证，不能只训练 768 维就保证全部小维度效果。

这使得同一个微调后的模型可以直接服务 384 维粗筛和 768 维精筛两个通道，节省部署和维护成本。

### 2.5 评测体系

#### 2.5.1 离线评测指标

在独立的测试集上评测以下指标：

- **Recall@K**：Top K 命中的相关文档数 / 全部相关文档数，再对查询取平均；除以 K 是 Precision@K，是否至少命中一个则是 Hit@K（K=5, 10, 20）。
- **MRR@K**（Mean Reciprocal Rank）：正样本排名倒数的均值，衡量正样本排名的平均位置
- **NDCG@K**：考虑位置权重的归一化折现累积增益，适合多正样本场景（详见下方算法）

**NDCG@K 算法**

DCG（Discounted Cumulative Gain）对排名靠前的相关文档给予更高权重：

$$\text{DCG@K} = \sum_{i=1}^{K} \frac{2^{rel_i} - 1}{\log_2(i+1)}$$

其中 $rel_i$ 为第 $i$ 位文档的相关性分数（二分类时取 0 或 1；多级标注时取 0~3 等整数）。

IDCG（Ideal DCG）为将所有相关文档排在最前时的 DCG 上界：

$$\text{IDCG@K} = \text{DCG@K（按相关性降序排列的理想结果）}$$

最终 NDCG 归一化到 [0, 1]：

$$\text{NDCG@K} = \frac{\text{DCG@K}}{\text{IDCG@K}}$$

**计算示例**（K=5，二分类，正样本排在第 1、3 位）：

```
位置 i :  1      2      3      4      5
rel_i  :  1      0      1      0      0
权重   :  1/log₂(2)=1.0  1/log₂(3)≈0.63  1/log₂(4)=0.5  ...

DCG@5  = (2¹-1)/log₂(2) + 0 + (2¹-1)/log₂(4) = 1.0 + 0.5 = 1.5
IDCG@5 = (2¹-1)/log₂(2) + (2¹-1)/log₂(3) = 1.0 + 0.63 = 1.63  （理想：正样本排1、2位）
NDCG@5 = 1.5 / 1.63 ≈ 0.920
```

**为什么 RAG 用 NDCG 而不只用 Recall**：Recall@K 衡量相关文档覆盖比例，不区分排第 1 还是排第 K；而 LLM 读取检索结果时会受位置偏差影响（前几个文档贡献更大），NDCG 的位置折现正好与此对齐。

**注意**：不要用 Cosine Similarity 的均值来评测，这和下游任务相关性弱；应用排序类指标。

#### 2.5.2 端到端评测

离线指标好不等于线上效果好，还需要接入 RAG 评测流水线：

```
Query → Embedding 检索 → Reranker 精排 → LLM 生成 → 与 Ground Truth 比对
```

端到端指标：答案 EM（Exact Match）、答案 F1、RAGAS 框架下的 Faithfulness 和 Answer Relevance。

## 历史 QA 构建与多维训练记录

**Embedding 模型选择**：基于 [gte-multilingual-base](https://huggingface.co/Alibaba-NLP/gte-multilingual-base) 进行领域微调。微调的核心在于**高质量训练语料的构建**。

**语料构建方式**：使用 **Qwen2.5-72B** 自动生成训练语料对。针对不同类型的数据内容，通过 Prompt 引导大模型生成 JSON 格式的 QA 对。共生成 **75 万** QA 对，经数据处理后 **48 万**条参与微调训练，在 **A30 × 2** 上训练两周。

**核心要点**：
- **问题丰富性**：分别从文档块内容、文档块标题、文档块生成的摘要等多角度出发；摘要可直接作为问题，也可基于文档块同时生成问题与答案
- **后处理的必要性**：异常字符剔除、MinHash 问题去重、Rerank 相关性筛选、去除指代性问题（含 "本文""这""那" 等模糊指代词）
- **长度配比平衡**：使用不同长度的语料进行训练，避免模型对特定长度的偏好
- **多维度联合微调**：同时微调 384 维和 768 维向量表示

**微调效果**：
- 自有数据集：Top10 召回率从 **62% → 88%**（提升 26 个百分点）
- 开源数据集 [DuRetrieval](https://huggingface.co/datasets/mteb/DuRetrieval)：98.8% → 97.8%（微降 1 个百分点，属于合理范围，表明模型在领域适配的同时未严重损失通用能力）

## InfoNCE 损失的直觉与公式

InfoNCE（Info Noise Contrastive Estimation）是对比学习的核心损失函数，本质是一个分类任务的交叉熵——让模型从 K 个负样本中识别出正确的正样本。

公式：

$$\mathcal{L} = -\log \frac{\exp(\text{sim}(q, d^+) / \tau)}{\exp(\text{sim}(q, d^+) / \tau) + \sum_{i=1}^{K} \exp(\text{sim}(q, d_i^-) / \tau)}$$

**直觉理解**：分子是 query 和正样本文档的相似度经温度缩放后的指数；分母是正样本加上所有负样本的同类指数之和。损失最小化意味着正样本相似度要尽可能大于所有负样本——等同于让模型把"从 K+1 个候选中找到正确文档"这道题答对。

**温度系数 τ 的作用**：τ 越小，相似度差异被放大越剧烈，梯度越集中在难分的边界样本上，但也越容易训练不稳定。实际取值从 0.05 开始，随训练逐步降到 0.01。

**In-batch Negatives**：同一损失覆盖的 batch 中，其他问题的正文档可作为负样本候选，但要排除假负样本。逻辑 batch、跨卡聚合与编码分块分别配置；普通梯度累积不自动扩大对比损失的负样本池。

**为什么 RAG 用这个 Loss**：RAG Embedding 微调的目标是"查询-文档相关性"而不是"语义相似度"。InfoNCE 天然对应检索场景——"从大量文档中找到与 query 最相关的那个"，与召回任务目标完全对齐。

## 领域微调的项目设计补充

检索表示还包括稀疏和多向量 late interaction；Qwen3 检索模型提供新候选，Sentence Transformers 6.x 提供多向量入口。表示、指令、维度、pooling 与索引必须兼容，不能仅将新模型向量直接混入旧索引。具体原理与官方来源见 [[RAG系统/03_Embedding与Reranker微调全流程]]。以下模型和数据记录原项目方案。

### 1. 底层逻辑：为什么通用 Embedding 不够用

通用 Embedding 模型（如 gte-multilingual-base）是在开放互联网语料上训练的，其向量空间的语义近邻关系反映的是通用语境。但企业 RAG 的问题是：

**用户问的是"SIB1 的 periodicityAndOffset 参数怎么配"，通用模型认为语义最近的文档可能是"定时器参数配置"这种泛化内容，而不是那份精确描述 3GPP TS 38.331 小区重选参数表的 5G 协议文档。**

根本原因在于：**语义空间的度量对象不对**。通用模型学的是自然语言中词汇共现和上下文替换关系，而领域模型需要学的是"这个问题在这个知识库里能被哪个文档回答"这一检索对应关系。这是两种本质不同的相似度。

### 3. 训练数据构建：高质量语料是关键

#### 为什么用 LLM 生成 QA 对而不是人工标注

人工标注 75 万 QA 对不现实（成本高、速度慢）。用 Qwen2.5-72B 生成有如下优势：
- 能从文档任意角度出发提问，覆盖多样问法
- 能生成语义等价但表达不同的问题（即难负样本训练所需的"近似但不等"样本）
- 速度可达数千条/分钟

#### 三种提问角度的设计逻辑

| 角度 | 示例 | 设计意图 |
|------|------|---------|
| 基于文档块内容 | "随机接入的 preamble 格式是什么" | 覆盖精确事实查询 |
| 基于文档块标题 | "随机接入流程介绍" | 覆盖导航型/综述型查询 |
| 基于生成摘要 | "4步随机接入流程的核心机制" | 覆盖理解型/总结型查询 |
| 近似术语区分 | "SIB1 与 SIB2 的广播内容有何差异" | 覆盖相似名词辨析查询，迫使模型学习细粒度语义边界 |

三种角度对应了用户实际查询时的不同意图模式，确保微调后模型对各类问法均有良好的向量对齐能力。

#### 近似术语区分样本的特殊价值

通信领域存在大量形态相近但语义迥异的术语，例如 SIB1（System Information Block Type 1，承载小区接入参数）与 SIB2（承载无线资源配置参数），或 RRC\_IDLE 与 RRC\_INACTIVE 状态。通用 Embedding 模型在处理这类术语时，往往因训练语料中的共现关系将其映射到向量空间的相邻位置，导致检索时"问 SIB1 返回 SIB2 文档"的混淆错误。

为此，在 QA 对生成阶段，Prompt 中显式要求大模型针对同一文档中出现的近似术语**生成对比性问题**，即在问题中同时点名两个术语并追问其差异。训练前需确认文档能否完整回答该对比问题；仅解释另一术语的文档不自动是负样本，也可能提供部分必要证据。**难负样本必须经过相关性核对**，不能只按术语差异强制标负。对于已经确认只涉及 SIB1 的查询，再用正确标注的相似文档训练区分；实际边界改善由独立评测确认。

#### 后处理流程及其背后的思考

**① 异常字符剔除**
LLM 生成时偶尔会输出乱码、截断JSON、混入控制字符。这类样本不仅无效，还会在 Tokenizer 处理时产生异常，需首先清洗。

**② MinHash 问题去重**
75 万条语料中，针对相似文档块往往会生成语义高度相近的问题。如果大量近似问题都指向同一文档，模型会过度记忆该文档的表面词汇，而非学习真正的语义对齐关系——这是一种隐性的过拟合。

MinHash 是局部敏感哈希（LSH）的一种，通过比较文本 n-gram 的 Jaccard 相似度高效去重，时间复杂度远低于两两比较。阈值通常设为 0.8~0.9，相似度超过阈值则保留一条。

**③ Rerank 相关性筛选**
LLM 生成的 QA 对不保证质量：有时生成的问题与文档块关联很弱（如 LLM 自由发挥引入了文档块中没有的信息）。用 Reranker 模型对每个 (问题, 文档块) 对打分，过滤掉低分样本，确保训练语料的"问答对应"关系是真实有效的。

这一步解决了一个核心问题：**模型学的是"问题和文档的对应关系"，如果这个对应关系本身是噪声，则再多数据也无用。**

**④ 去除指代性问题**
"本文提到的参数是什么"这类问题含有指代词，脱离了原文档上下文后语义不完整。向量化后此类问题的向量无法泛化表达真实查询意图，会污染向量空间。

**⑤ 长度配比平衡**
若训练样本全部是短问题，模型会对短文本产生偏好，遇到长问题时向量质量下降。显式控制不同长度样本的比例（如短问题: 中等问题: 长问题 ≈ 5:3:2）可以让模型在各长度场景下均保持稳定表现。
