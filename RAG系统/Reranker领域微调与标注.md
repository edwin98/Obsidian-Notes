# Reranker 领域微调与标注

完整维护 Cross-Encoder、相关性标签、假负样本、教师辅助标注、训练损失与分数校准。Embedding 负责候选召回，Reranker 学习精排；协同与部署见 [[RAG系统/03_Embedding与Reranker微调全流程]]。历史候选配方尚未确认为最终生产方案。

## Reranker：模型、数据与训练

### 3.1 架构选型：为什么用 Cross-Encoder

Reranker 在召回之后工作，候选集已经缩小到 50~200 个文档，允许更重的计算。

Cross-Encoder 的工作方式：将 `[CLS] query [SEP] document [SEP]` 拼接后送入 Transformer，在 token 级别做全局注意力，最后从 `[CLS]` 位置输出相关性分数。

相比 Bi-Encoder：
- 优势：query 和 document 之间有 **完整的 token 级别交互**，能捕捉细粒度语义关系（如数字匹配、否定关系、条件依赖等）
- 劣势：无法预先离线计算 document 表示，每次检索必须重新计算，O(N) 复杂度，只适用于候选集较小（<200）的精排场景

**为什么 Reranker 更准确**：以 "HARQ 最大重传次数是多少" 为例，Bi-Encoder 对 "HARQ 重传机制" 和 "HARQ 最大重传次数" 的文档表示都很接近 query，难以区分；但 Cross-Encoder 在做注意力时，"最大" 和 "次数" 这两个关键 token 能直接 attend 到文档中对应的数字和参数名，打分差异显著。

### 3.2 基座选型

Reranker 基座的选择逻辑：

| 模型 | 参数量 | 特点 |
|------|--------|------|
| bge-reranker-v2-m3 | 568M | FlagEmbedding 系列，中英双语强 |
| gte-multilingual-reranker-base | 305M | 阿里 GTE，推理快，多语言 |
| ms-marco-MiniLM-L-12-v2 | 33M | 极轻量，但仅英文 |
| Qwen2.5-0.5B + LM-head | 500M | LLM 作 Reranker 新趋势 |

**选型结论**：选用 `gte-multilingual-reranker-0.3B`（305M）。

选择 305M 而非更大模型的原因：Reranker 在在线链路中是阻塞点（必须同步等待结果才能继续），精排 50 个候选文档时 P99 延迟不能超过 200ms，305M 在 A10G GPU 上可以满足这个约束；568M 模型在同等硬件上大约慢 40%。

### 3.3 数据集构建

> **规模说明：区分 QA 数量与实际需要标注的文档对数量**
>
> 48 万条 QA 是可复用的数据来源，不代表 Reranker 必须使用全部问题，也不代表整个标注任务只有 48 万对。若每题召回 50 篇候选，最多会产生约 2400 万个问题—文档对。应先按业务场景去重、采样和筛选候选，再安排模型辅助标注与人工复核。
>
> 一种起步方案是选 2 万个有代表性的问题，每题从 Top-50 中选约 8 篇候选，形成约 16 万对待标注数据，并复用经过核对的已知正样本。这些数量只是方案示例，需根据评测效果和标注预算调整。
>
> Qwen2.5-72B 内网服务可以作为辅助评分候选，但需先通过独立专家标签验证，再在可靠的业务范围内批量使用。人工负责标准制定、疑难复核和自动标签的随机抽查，不能只审核模型自报低置信度的样本。历史记录中的 200 条校准、一致率 > 85%、5~8% 复核比例及 800~1000 pair/min 吞吐均需实际记录支持，不能视为通用标准或当前已验证结果。
>
> 结合 SIB 术语、制式/接口、设备版本和故障排查的完整方案见 [[RAG系统/Reranker领域微调与标注#通信知识库的规模化相关性标注]]。

Reranker 可以使用二分类标签，也可以使用分级相关性、排序或教师分数，取决于训练目标与损失函数。二分类数据格式例如：

```
正样本对：(query, relevant_doc)  → label = 1
负样本对：(query, irrelevant_doc) → label = 0
```

若采用 Listwise 训练，可使用**列表式**格式：一个 query 对应多个文档及其相关性标签。部分相关、同话题但不能回答，以及无法判断的文档需要按标注标准分别处理，不能全部归成正样本或负样本。

#### 3.3.1 正样本构建

**与 Embedding 共用正样本集**，来源相同（日志挖掘 + Qwen2.5-72B 合成的 48 万条 QA 语料），但有一个重要补充：

**难正样本（Hard Positive）**

对于同一个 query，可能有多个相关程度不同的正样本：
- 强相关：直接回答问题的段落（score = 1.0）
- 中等相关：包含相关上下文但需要推理的段落（score = 0.7）
- 弱相关：属于同话题但不直接回答问题的段落（score = 0.4）

使用细粒度分级标注（而非二分类）可以让 Reranker 学到更精确的打分校准，而非只学到 "相关/不相关"。

构建方式：

1. **专家制定标准并标注起步样本**：覆盖 SIB1/SIB2、5G NR/LTE、Xn/N2、设备与软件版本等容易混淆的场景，留出独立样本验证辅助模型。
2. **辅助模型批量初标**：对筛选后的问题—文档对返回标签、原文依据和适用条件；无法判断时保留该状态，不强制给出正负标签。
3. **人工复核与抽查**：优先检查模型分歧、条件不匹配和新场景，同时随机抽查其他自动标签。错误较多的场景转人工或暂不使用，不采用固定复核比例作为质量保证。
4. **按训练目标转换标签**：若采用 1~5 分制，可用 `score_normalized = (llm_score - 1) / 4` 映射到 [0, 1]；这只是数值缩放，不代表经过概率校准。保留人工/自动来源、文档版本和标注标准版本。

#### 3.3.2 负样本构建

Reranker 收到的候选通常已经过初步检索，因此需要重点学习容易混淆的负样本。同时保留适量随机或较容易的负样本，避免训练只覆盖困难样本；具体配比需通过验证集比较。

**第一类：检索候选中当前 Reranker 容易误判的文档**

先通过 Embedding 或 BM25 找候选，再使用当前 Reranker 打分。高分但经可靠标注确认不能回答问题的文档，可作为难负样本；能回答的应补为正样本，不能只因它不是原先的正样本文档就标负。

流程：Embedding/BM25 召回 → 当前 Reranker 打分并筛选候选 → 经验证的模型辅助标注与专家复核 → 采样已确认的难负样本。

目的在于**让 Reranker 学会降低自己容易误判的文档排名**。自动标签需要与人工标签区分存储；不在已验证自动标注范围内的样本，交由专家确认或暂不使用。

**第二类：BM25 召回的干扰文档**

词汇重叠高但语义无关的文档，训练 Reranker 抵抗 "关键词匹配陷阱"。

例：
- Query: "如何解决 PDCP 层 SDU 丢包问题"
- 负样本: "PDCP 层 SDU 重排序窗口配置"（含大量相同关键词，但讨论的是不同问题）

**第三类：LLM 生成的混淆文档（针对高价值 query）**

对系统中频率最高的前 100 个 query，用 GPT-4 专门生成混淆文档：

```python
PROMPT = """
以下是一个技术问题和对应的正确答案段落：

问题：{query}
正确答案：{positive_doc}

请生成 3 个干扰性文档段落，要求：
1. 与正确答案在话题上高度相关
2. 但不能直接回答上述问题
3. 包含与正确答案部分重叠的技术术语
4. 每段约 100~200 字
"""
```

#### 3.3.3 数据平衡与采样策略

正负样本比例是影响 Reranker 性能的关键因素：

- **正负比 1:1**：召回率高，精确率低（模型倾向于打高分）
- **正负比 1:4~1:7**：更接近在线检索时的真实分布（通常 Top 50 中真正相关的只有 3~5 个）
- **动态采样**：训练初期正负比 1:2，后期逐步增大到 1:5，模拟课程学习

**列表采样**：每个 query 配 1 个正样本 + 4~6 个负样本组成一个训练 instance（Listwise 训练格式），比 Pairwise 格式（一次只看一对）训练效率高 3~5 倍。

#### 3.3.4 数据质量控制

Reranker 训练数据的一个特殊问题：**标注一致性**。

同一篇文档对不同问题的相关性判断，人工标注者的主观性差异很大。解决方案：

1. **标注指南**：制定详细的相关性定义标准（如"文档中是否包含可以直接回答问题的信息"）
2. **Calibration 轮次**：正式标注前，多个标注者共同标注 50 条数据，讨论分歧，统一标准
3. **LLM 辅助标注**：先用独立专家标签验证候选模型，再在通过验证的场景中批量初标，要求提供原文依据。模型自报置信度不直接等于标签正确率。
4. **重点复核与随机抽查**：重点检查模型分歧、术语/型号/版本不匹配和新场景，并随机抽查自动接受的各类标签。根据分场景误标情况调整复核比例，必要时暂停该类自动标注。

LLM 标注 Prompt：
```python
ANNOTATION_PROMPT = """
以下是一个搜索查询和一个文档段落。请判断该文档段落对于回答该查询的相关程度。

查询：{query}

文档段落：
{document}

请按以下标准打分（1-5分）：
5分：文档直接、完整地回答了查询
4分：文档包含回答查询所需的关键信息，但不够完整
3分：文档与查询话题相关，但不能直接回答
2分：文档与查询有一定关联，但主要讨论其他内容
1分：文档与查询基本无关

只输出数字分数，不需要解释。
"""
```

### 3.4 训练方法

#### 3.4.1 微调策略：全量 SFT vs LoRA

本节讨论 **全量参数微调 + listwise loss** 候选；概要另记录 **LoRA + Margin MSE**。没有关联运行日志与 checkpoint，不能将两者同时描述为最终线上方案。

**选择全量微调的可检验理由**：

- 0.3B 级模型较小，全量训练可能符合资源预算；但必须计入梯度、优化器、激活和临时缓冲，不能只比较权重显存。两个 FP32 Adam 动量项按 305M 参数约为 2.44 GB，额外 FP32 主权重另算。
- 全量更新允许更多参数适应领域；是否优于 LoRA，需要固定数据与计算预算比较领域排序效果和通用能力。
- 全量 checkpoint 部署直接；LoRA 也可在适用模型上合并权重，不必增加逐请求推理开销。

**LoRA 与 listwise loss 兼容**：LoRA 可配置任意支持的层和 Linear 模块，并非只能用于高层 Q/K。冻结基座权重不阻止梯度通过计算图流向适配器，listwise 损失不要求更新所有参数。资源有限、多领域适配或快速实验时都可比较 LoRA；训练时间和质量收益需要实测。

**全量 SFT vs LoRA 实测对比（305M 模型，2× A10G）：**

| 维度 | 全量 SFT | LoRA (r=16, α=32) |
|------|----------|--------------------|
| 可训练参数量 | 305M（100%） | ~5M（1.6%） |
| 单次训练显存峰值 | ~18 GB（双卡合计） | ~9 GB（单卡可训） |
| 验证集 NDCG@10 | **0.847** | 0.821（低约 3 个点） |
| 收敛所需 epoch 数 | 3~5 | 5~8 |
| 训练时间（3 epoch） | ~5 h | ~2.5 h |
| 部署复杂度 | 低（单一 checkpoint） | 略高（adapter 合并） |

结论：在 300M 规模模型 + 大领域偏移场景下，全量 SFT 3 个点的 NDCG 提升值得额外的约 2.5 小时训练时间。

#### 3.4.2 训练环境与框架配置

当前 Sentence Transformers 有 `CrossEncoderTrainer`，不同模型可能依赖不同 tokenizer/processor 与打分流程。下面保留原训练栈和代码，按当时版本理解，不能将所有新 Reranker 套用为固定 `[CLS] query [SEP] doc` 分类头。[迁移指南](https://www.sbert.net/docs/migration_guide.html)

**硬件配置：**

| 资源  | 规格                             | 说明                              |
| --- | ------------------------------ | ------------------------------- |
| GPU | 2× NVIDIA A10G（24 GB VRAM × 2） | 单机双卡，数据并行（DDP）                  |
| CPU | 32 核 Intel Xeon                | DataLoader 预处理，多进程 tokenization |
| 内存  | 128 GB RAM                     | 训练集全量加载至内存，消除磁盘 I/O 瓶颈          |
| 存储  | 1 TB NVMe SSD                  | checkpoint 存储、tokenized 数据缓存    |

**训练框架栈：**

```
sentence-transformers      # 主训练框架：原生支持 Cross-Encoder、Listwise Loss
transformers（HuggingFace）# 模型加载、tokenizer、学习率调度
accelerate                 # 多 GPU DDP 封装，代码几乎不需改动
deepspeed ZeRO-1           # 优化器状态分片（可选，305M 模型不强依赖）
torch 2.1+ (torch.compile) # 图编译加速，约提升 15% 吞吐
wandb                      # 训练全程监控（loss、NDCG、学习率曲线）
```

**为什么选 sentence-transformers 而非手写训练循环：**

- 原生的 `CrossEncoder` 类封装了 `[CLS] query [SEP] doc [SEP]` 的输入格式构造
- 内置 `CERerankingEvaluator`，每个 epoch 结束自动在验证集上计算 NDCG@10、MAP
- 内置 `RankingLoss`（Listwise Softmax）实现经社区大量验证，无需自行调试数值稳定性
- 与 HuggingFace Hub 上的 reranker checkpoint 格式完全兼容

**训练时间实测（完整链路）：**

| 阶段 | 数据量 | 耗时 | 备注 |
|------|--------|------|------|
| 数据预处理（tokenization + 本地缓存） | 48 万条 query，每条 1 正 + 5 负 | ~1.5 h | 32 核 CPU 多进程并行 |
| 离线 Reranker 打分（用于 Embedding 蒸馏阶段生成软标签） | 同上 | ~3 h | 仅推理，无梯度，单卡 A10G |
| **Reranker 全量 SFT（3 epoch）** | ~280 万 query-doc pair | **~5 h** | 2× A10G，batch=32，seq_len=512 |
| 验证集评测（每 epoch 结束） | 5000 条样本 | ~8 min/次 | NDCG@10 + Precision@3 |
| 全流程总计（数据处理 → 最终 checkpoint） | — | **~10~11 h** | 含离线打分、训练、评测 |

**训练稳定性关键配置：**

- **梯度裁剪** `max_grad_norm=1.0`：Cross-Encoder 前期训练时，Softmax 对分数尺度极为敏感，梯度容易突然放大（表现为 loss 突然跳升），裁剪可有效抑制
- **早停**：监控验证集 NDCG@10，连续 2 个 epoch 无提升则停止，防止小数据过拟合
- **fp16 混合精度**（`torch.cuda.amp.GradScaler`）：训练速度提升约 40%，显存节省约 30%，Cross-Encoder 的 Softmax 分数计算对精度不敏感，fp16 损失可忽略
- **checkpoint 策略**：每 epoch 保存一次，保留最近 3 个，以验证集最佳 NDCG@10 的 checkpoint 作为最终部署版本

#### 3.4.3 损失函数

**方案一：Binary Cross-Entropy（BCE）—— Pointwise**

最简单的方案，将 Reranker 视为二分类器：

```python
loss = BCE(sigmoid(score), label)
# label ∈ {0, 1}
```

优点：实现简单，与下游逻辑回归概率估计兼容
缺点：没有显式建模文档之间的相对排序关系

**方案二：Pairwise Ranking Loss**

每次比较一对 (positive, negative)，要求 positive 得分高于 negative：

$$\mathcal{L} = \max(0, \text{margin} - \text{score}(q, d^+) + \text{score}(q, d^-))$$

优点：直接优化排序目标
缺点：没有利用整个候选列表的结构信息，训练效率低

**方案三：Listwise Softmax Loss（推荐）**

将一个 query 对应的所有文档视为一个列表，用 Softmax 对整个列表建模：

$$\mathcal{L} = -\sum_{i \in \text{positives}} \log \frac{\exp(\text{score}(q, d_i))}{\sum_j \exp(\text{score}(q, d_j))}$$

优点：
- 同时建模所有文档之间的相对顺序
- 利用了负样本的分数差异（不同难度的负样本有不同的惩罚）
- 训练效率高，一个 instance 等效于多个 pairwise 比较

**本系统选用 Listwise Softmax**，配合精细分级的正样本分数（而非二值标签），进一步提升模型对分数值的校准能力。

**三种 Loss 的本质区别**

这三种方案的差异，可以用一个具体例子来说明。假设 query 是"HARQ 最大重传次数如何配置"，Embedding 召回了 6 个候选文档：

```
D1：介绍 maxHARQ-Tx 参数取值的段落        ← 强正样本，应排第 1
D2：介绍 HARQ 进程数配置的段落            ← 弱正样本，相关但不直接回答
D3：介绍 HARQ 工作原理的段落             ← 话题相关但不回答问题
D4：介绍 ARQ 重传机制的段落              ← 中等负样本
D5：介绍 PDCP SDU 重排序窗口的段落        ← 简单负样本
D6：介绍天线端口映射的段落               ← 随机负样本
```

- **BCE（Pointwise）的视角**：独立判断每个文档"是否相关"。D1 = 1，D2 可能 = 1，D3~D6 = 0。问题在于 D1 和 D2 的分数都被推向 1，但它们之间的相对排序没有被显式建模。最终 D2 可能排在 D1 前面，但 BCE 对此没有惩罚。
- **Pairwise 的视角**：比较 (D1, D3)、(D1, D4)、(D1, D5)、(D1, D6) 这些正负对。每次只看一对，D3 的分数不知道 D4 的存在，训练信号相互独立。需要枚举 M×N 对（M 个正样本，N 个负样本），训练效率低。
- **Listwise 的视角**：把 [D1, D2, D3, D4, D5, D6] 视为一个完整列表，做一次 Softmax。D1 的得分直接和所有其他文档竞争，D3 得分高了就会"抢走"D1 的概率质量，产生直接的梯度惩罚。它联合优化列表内竞争关系，但不能等同为固定数量的 pairwise 比较信息量。

**为什么不用 LambdaRank / LambdaMART 类方案**

LambdaRank 是搜索领域经典的 Listwise 方案，它直接对 NDCG 的变化量加权梯度，理论上更接近最终评测指标。但它有两个工程问题：

1. 梯度计算需要对整个列表排序，与神经网络的反向传播框架不能直接兼容，需要手工实现梯度，维护成本高。
2. NDCG 梯度加权依赖于排序位置，在训练早期模型打分混乱时，位置权重不稳定，容易造成梯度爆炸。

Listwise Softmax 在 PyTorch 里就是一个标准的 `cross_entropy` 调用，数值稳定性有框架保证，且实测效果与 LambdaRank 差距在 1% NDCG 以内，工程性价比更高。

**为什么 Reranker 不用 InfoNCE**

Embedding 用 InfoNCE，Reranker 用 Listwise Softmax，两者看起来很像（都是 Softmax + 负样本），但有一个关键区别：Embedding 的 InfoNCE 假设每个样本只有一个正文档，而 Reranker 的候选列表里可能有多个相关程度不同的正文档（D1 强相关、D2 弱相关）。

常见单正例 InfoNCE 实现只指定一个目标，但可扩展为多正例对比学习，并非数学上禁止多个正样本。候选列表内的 softmax 交叉熵与对比损失有相近形式；本方案可使用按相关度构造的目标分布表达多级相关性，应明确标签归一化与损失定义。

#### 3.4.4 Score Calibration（分数校准）

未校准的 Reranker 分数也可在验证集上选择过滤阈值，但不能直接解释为相关概率，模型或数据变化后应重验阈值。校准的目标是让分数具有概率含义（P(相关 | query, doc)）：

```python
# Platt Scaling：用 Logistic Regression 对 Reranker 原始分数做校准
from sklearn.linear_model import LogisticRegression
from sklearn.calibration import calibration_curve

calibrator = LogisticRegression()
calibrator.fit(raw_scores.reshape(-1, 1), binary_labels)

# 校准后：score = 0.7 表示该文档有 70% 的概率与 query 相关
calibrated_score = calibrator.predict_proba(raw_score)[:, 1]
```

校准的工程价值：允许设置动态阈值，当最高分 < 0.3 时触发 "无相关文档" 的降级策略（返回兜底回答），避免用低相关文档生成缺少依据的答案。

#### 3.4.5 训练超参数

| 超参数 | 推荐值 | 选择依据 |
|--------|--------|----------|
| batch_size | 32~64（每个包含 1 正 + 5 负） | 受序列长度限制（query+doc 最长 512 token） |
| learning_rate | 5e-6~2e-5 | Reranker 比 Embedding 更难训练，LR 要更小 |
| max_seq_length | 512 | query + doc 拼接后的总长度 |
| num_epochs | 3~5 | 结合早停，在验证集 NDCG@10 上评估 |
| warmup_ratio | 0.1 | 同 Embedding |
| label_smoothing | 0.1 | 避免模型对正样本过度置信，提升泛化 |

#### 3.4.6 LLM-as-Reranker 的新趋势

近期出现了用指令微调的小 LLM 作 Reranker 的方案（如 RankLLaMA、RankZephyr），本质是将打分任务转化为生成任务：

```
输入：[系统提示] 判断以下文档是否与查询相关，回答"是"或"否"
      查询：{query}
      文档：{document}

输出：提取"是"或"否" token 的 logit 比值作为相关性分数
```

优势：
- 利用 LLM 的推理能力处理复杂相关性判断
- Zero-shot 迁移能力更强

劣势：
- 推理速度显著慢于 BERT 类 Cross-Encoder（生成式 vs 判别式）
- 当前阶段不适合对延迟敏感的在线链路

**当前阶段的建议**：在精排候选集较小（< 20）且有足够计算资源时，可以尝试 LLM-as-Reranker；在本系统的生产环境中，仍然推荐 BERT 类 Cross-Encoder。

### 3.5 评测体系

Reranker 的评测需要从两个层面进行：

**层面一：精排层面（Reranker 自身指标）**

输入：Embedding 召回的 Top 50 候选文档
输出：重排后的 Top 10

- NDCG@10：综合考虑排序质量和位置权重，精排场景最关键指标
- Precision@3：前 3 个文档的精确率（LLM 实际最依赖的是前 3 个文档）
- MAP（Mean Average Precision）：全列表的平均精确率，反映整体排序质量

**层面二：端到端影响**

- Reranker 前后的 Recall@10 变化（Reranker 可能因错误排序降低召回率）
- 答案生成质量：RAGAS Faithfulness 分数（衡量答案是否有文档支持）
- 误召回率下降：以前排名靠前但最终被 Reranker 降低排名的低相关文档比例

## 通信知识库的规模化相关性标注

**几十万条 QA 不等于要人工标注几十万组候选列表。**以笔记中的 48 万条 QA 为例，每题检索 50 篇文档，就会产生最多约 2400 万个“问题—文档对”；不能把 48 万条 QA 当成整个 Reranker 标注任务只有 48 万对。也不必让 Reranker 一开始就使用全部 QA，应先选有代表性的问题，再根据评测结果扩大数据量。

以下是可用于本项目的方案，示例数量不代表已实施配置或实际耗时。

**① 按业务场景选问题，减少重复标注**

从 QA 和线上查询中去重、分层采样，覆盖术语解释、协议流程、参数配置和故障排查。可先选 2 万个问题，每题召回 Top-50，再从中选出约 8 篇有标注价值的候选，交给辅助模型判断。这样待自动标注的候选约为 16 万对，而不是将全部 2400 万对都交给昂贵模型或人工处理。经过核对的已有正样本可以复用，合成 QA 的正确性仍需抽查。

候选应兼顾当前 Reranker 的高分文档、不同检索方式找到的文档，以及少量随机或较容易的样本，避免训练集只剩极难样本。每题候选数不必固定，已经确认的重复内容也不必反复标注。

| 通信场景                           | 容易混淆的候选             | 标注时重点检查                                       |
| ------------------------------ | ------------------- | --------------------------------------------- |
| 术语解释，例如“SIB1 是什么”              | SIB1、SIB2 相关文档      | 是否真正解释问题中的对象；介绍 SIB1/SIB2 差异的文档也可能是正样本，不能只看标题 |
| 制式与接口，例如“5G NR 的 Xn 切换流程”      | LTE 切换、N2 切换或通用切换说明 | 是否符合问题指定的制式和接口，内容能否回答；不能只因出现“切换”就给高相关标签       |
| 参数配置，例如“设备 A 在 V2 版本的切换参数如何配置” | 设备 B 或 V1 版本的配置文档   | 设备、软件版本、适用条件是否一致；旧版文档若仍适用，也不能直接判为负样本          |
| 故障排查，例如“Xn 切换失败如何定位”           | 参数配置说明、故障定位指南、历史工单  | 是否提供问题需要的定位依据；只包含部分排查线索的文档应单独标记，不能全部归为不相关     |

**② 专家先制定标准，再验证辅助标注模型**

专家先标一批覆盖上述场景的问题—文档对，例如以 2000 对作为起步样本，并区分“能直接回答、部分相关、相关但不能回答、完全无关、无法判断”。其中一部分用于讨论标准和调整标注提示词，另一部分独立保留，用来验证调整后的辅助模型。数量应根据场景覆盖与错误情况补充，不以达到某个固定数量作为可靠性的证明。

可将项目已有的 Qwen2.5-72B 内网服务作为辅助标注的候选，但需要比较它与专家的判断。分别统计术语、制式、型号和版本场景中的误标，尤其关注把正样本误标为负样本的比例。模型参数更大、总一致率较高，都不能代替这些分场景检查。

**③ 模型批量初标，人工检查重点样本并随机抽查**

给辅助模型提供问题、候选文档、制式/设备/版本等元数据，以及统一的标注标准。要求输出简短标签、原文依据和不匹配的条件；文档不足以判断时应返回“无法判断”，而不是猜测标签。可以保留分级相关性标签或教师分数，训练时按所用损失函数组织数据，不必把所有候选硬分成正负两类。

人工优先复核当前 Reranker 与辅助模型分歧较大、关键型号或版本不匹配、证据不足，以及来自新业务场景的样本；同时在自动接受的正、负和部分相关标签中随机抽查。若某类场景的自动标签错误较多，就暂停该类自动接收，改由人工确认或暂不使用，再补充样本和修订标准。复核比例根据误标情况和预算调整，不预设“只检查 5%”就足够，也不把模型自报置信度当作真实可靠度。

**④ 用批处理、复用结果和标注界面减少耗时**

- **分开计算与标注**：Embedding 批量编码和检索，当前 Reranker 用 GPU 批量评分；昂贵的教师模型只处理筛选后的候选。接口并发需要受控，并记录限流、重试和实际吞吐。
- **缓存已有标签**：根据问题、文档内容/版本、标注标准版本及教师模型/提示词版本识别重复任务，复用仍适用的结果；保留自动初标、人工修改和最终标签，便于追溯。
- **减少无效输入输出**：优先使用问题对应的 Chunk，并补足判断所需的标题、上下文和适用条件；不能为提速而截掉关键证据。输出保留标签和简短依据即可，不要求长篇解释。
- **提高人工操作效率**：按问题集中展示候选，突出 SIB 编号、制式、设备型号和软件版本，支持并排阅读与快捷键标注。高亮只辅助阅读，不能替代相关性判断。
- **逐轮补充错误样本**：每轮训练后收集新的高分误判和覆盖不足的场景，只对新增或受版本变更影响的数据重新标注，而不是每次重做全部数据。

**⑤ 用独立人工评测决定是否扩大规模**

保留由专家确认的评测集，按问题标注候选列表中的相关文档；按源文档及其近重复版本分组划分训练与评测数据，避免同一文档生成的相似 QA 同时出现在两边。比较不同数据规模下的 NDCG@10、重排后的 Recall@10，以及术语、版本和型号混淆的错误率。评测仍有缺口时补充对应场景，不只增加重复样本。标注耗时和费用按实际处理的文档对数、输入输出 Token、硬件与复核量统计，不沿用未经验证的固定速度。

这类方法可参考 [Cross-Encoder 教师模型蒸馏示例](https://www.sbert.net/examples/cross_encoder/training/distillation/README.html)和 [LLM 辅助修正假负样本的研究](https://arxiv.org/abs/2505.16967)，但是否适合本项目仍需用通信领域样本验证。

## 历史候选训练配置与待核实项
通用的开源 Reranker 模型（如 gte-reranker）虽然适用于多种场景，但对“A3 事件”“Xn 切换”等通信领域术语可能不够熟悉，导致相关文档得分偏低，或把容易混淆的文档排在前面。为改善领域内的排序效果，我们在原模型基础上进行微调：

- **训练样本构建 (Triplet Generation)**：结合开源大模型生成的数据与线上真实问答日志，半自动构建三元组 `<Query, Positive_Document, Hard_Negative_Document>`，即“问题、正确文档、容易混淆但不能回答该问题的文档”，减少完全依赖人工标注的工作量。
  - **正例 (Positive)**：让大模型根据原文档生成问题，将问题与能回答它的原文片段配对；也可以使用经过专家确认的线上问答或工单记录。生成的问题与文档是否匹配，仍需核对。
  - **难负例挖掘 (Hard Negative Mining)**：只使用明显不相关的文档，模型较难学会区分相近术语。因此，利用 BM25 找出**用词相似、但不能正确回答问题**的片段，确认后作为难负例。例如，问题是“5G SIB1 广播读取时间”，可以从“4G SIB1 广播参数”或“5G SIB2 配置描述”等候选中筛选难负例。训练目的是让模型更重视“4G/5G”“SIB1/SIB2”等影响答案的差异，把正确文档排在容易混淆的文档前面。
- **训练方式与损失函数 (Loss)**：
  - **候选损失函数**：BCEWithLogitsLoss 用于学习每个问题与文档是否相关；Margin MSE 用于学习教师模型给出的文档分数差；listwise softmax 用于学习一组候选文档的相对排序。具体选择取决于标签形式和验证集效果，不能预先认定某一种一定更好。
  - **候选微调方式**：可以全量微调，也可以使用 LoRA。LoRA 主要训练新增的低秩矩阵，作用于哪些模块、是否同时更新输出头，由具体配置决定。概要曾记录 Margin MSE + LoRA，详解记录全量微调 + listwise；这些属于不同候选或历史方案，最终采用哪一版，仍需核对训练配置与保存的模型检查点（checkpoint）。
- **效果记录待核实**：笔记中 NDCG@10 从 0.62 提升至 0.76 等历史数字，需要对应的评测集版本、样本量、运行日志和模型检查点支持，才能作为实际测得的结果。
