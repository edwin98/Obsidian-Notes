# 服务架构与性能优化

维护在线 API、离线摄入、任务分流、推流和压测。通用组件原理在工程目录，检索算法在 [[RAG系统/查询改写与检索排序]]。SSE 改善结果交付体验，实际容量仍以完整链路压测为准。

## 基础设施与极简框架组件思路
LangChain、LlamaIndex 等框架能提供通用组件，但百万级文档处理和定制重排流程仍需要明确的模块边界。因此，项目对文档处理、检索和生成接口做了单独抽象：
- **自定义核心接口**：定义 `DocumentParser`、`ChunkSplitter`、`PipelineRetriever` 和 `LLMGenerator` 四个抽象类，分别负责文档解析、切片、检索和生成。使用 **[[04_工程与框架/Pydantic]]** 校验配置与参数的类型和范围；权限、事实和其他业务规则仍需单独检查。
- **文档入库（Ingestion）的限流与重试**：并行切片和生成摘要时，请求量可能超过模型服务的 Rate Limit，产生 HTTP 429 错误。通过**指数退避（Exponential Backoff）**重试和任务队列控制请求速率，减少入库失败。

## 服务端技术栈与实时交互链路

### 1. Python + [[04_工程与框架/FastAPI]] 的微服务架构
- 在线系统使用 **[[04_工程与框架/FastAPI]]** 作为 Web 框架，通过 `asyncio` 事件循环并发等待 ES 检索、RPC/HTTP 模型调用等网络 I/O，适合需要流式输出的 RAG 服务。实际吞吐量仍取决于下游服务和部署配置。
- **基于 [[04_工程与框架/Kafka]] 消息中间件剥离离线高耗时计算**
  大体量的 PDF 解析、知识多模态归纳与向量组装入库不仅耗时长，且极易诱发尖刺性 OOM 资源耗尽。我们将处理层剥离解耦，服务端采用 **[[04_工程与框架/Kafka]] 作为核心消息总线枢纽**。

**流水线机制与部署策略详情**：
1. **异步推投 (Producer 生产化发后即忘)**：FastAPI 线上节点接取工单后即作 Producer 推送 JSON 指令快速返回 200，绝不阻滞主协程。
2. **多态资源组隔离隔离 (Consumer Group 分区隔离)**：利用 Kafka Topic 特性拆解流水操作（如：`topic_pdf_ocr` 分发给装载 T4 GPU 集群专做图像，`topic_text_slice` 送去纯 CPU 高主频节点计算词性）。由 Kafka Broker 的 Consumer Group 调配偏移量，做到容错不重漏（At-Least / Exactly-Once）。
3. **缓冲批量任务**：知识库并发重建时，利用 Kafka 的持久化队列暂存任务，由消费者按处理能力执行，减少短时任务高峰对服务的影响。

### 2. 高效推流交互（Server-Sent Events）
流式输出可以减少用户等待首段内容的时间。Rerank 与长回答生成可能需要数秒，因此应分别观察首 Token 延迟和完整回答耗时：
- 使用生成器（Generator）和 `StreamingResponse` 实现 **SSE 长连接**，在生成过程中逐步返回内容，减少用户等待完整答案的时间。
- 前端无需等待全句返回，只要服务端接受到由于大模型自回归特性产生的第一枚新 Token，便即时刷入界面中形成“逐字敲打（Typewriter Effect）”的视觉效果，显著掩盖了整体实际耗时。

## 系统压测与工程可用性度量体系

为了支撑内部上千甚至上万人的全员日常使用，系统具有三项刚性压测基准（SLI指标库）：
1. **首字 TTFT（Time To First Token）**：全系统经历文本 Embedding（0.5s）-> 粗筛精排二连击（共 1s）-> 模型网络往返开销之后，规定用户从按下回车到见到首个字符蹦出的极限响应时延**不得超出 2.5 ~ 3 秒**。
2. **生成吞吐率（TPS，Token-per-Second）**：后端采用 vLLM 进行推理服务和 KV Cache 管理。历史记录中的生成速度为 30～50 token/秒，具体结果需结合模型、硬件、上下文长度和并发负载核实。
3. **并发容量**：通过 Gunicorn/Uvicorn 多 Worker 与 Nginx 转发分担请求。历史记录中的百并发容量需通过实际负载下的压测确认。

## 在线与离线优化清单

### 调度与有效吞吐

PagedAttention 管 KV 内存组织，prefix caching 减少重复前缀计算，chunked prefill 调整调度，推测解码用候选与验证减少逐步生成开销，P/D 分离减少长提示对 decode 的干扰。它们都有工作负载条件；KV 传输慢时 P/D 分离还可能增加首 token 延迟。因此应结合 TTFT、ITL 和满足目标的有效吞吐。[官方分离式推理指南](https://vllm.ai/blog/2026-09-29-disaggregated-serving-guide)

见 [[01_大模型/推理与接口/vLLM与推理优化]]。

效率优化分在线链路和离线链路两个维度：

### 在线链路（降低 P99 延迟）

**并发检索**：BM25（ES）和 384 维向量检索并发发起，不串行等待，第一层 ~0.5s 内完成。

**两级向量粒度分工**：第一层用轻量 384 维做大范围粗筛（百万级），第二层才用 768 维做精语义重算，避免对全量文档做高维计算。

**BM25 分数缓存复用**：第二层精筛中，BM25 分数直接复用第一层缓存结果，不对全量知识库重新检索，减少一次全量 BM25 开销。

**小模型承担轻任务**：Query 改写（指代消解 + 问题扩展）用 Qwen3-4B 而非大模型，单次改写耗时控制在 1s 内；上下文摘要压缩也走 4B 模型异步 Celery 任务，不阻塞主链路。

**SSE 流式推流**：答案生成走 SSE 逐 token 流式推送，用户感知首字节时间大幅优于等待完整答案，降低主观等待感。

### 离线链路（提升入库吞吐）

**Kafka 异步解耦**：在线问答链路和离线文档入库链路被 Kafka 消息总线完全隔离，大批量文档入库（PDF/Word/Excel）不会冲击在线服务稳定性。

**GPU/CPU 异构 Worker 分流**：图片、PPT 等计算密集型走 GPU Worker，通用文本处理走 CPU Worker，按任务特性分配资源，提升整体吞吐。

**Celery 异步任务**：上下文轮次溢出监控、历史摘要压缩等非实时任务全部异步，不占用请求处理线程。
