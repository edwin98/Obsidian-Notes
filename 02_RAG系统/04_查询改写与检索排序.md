# 查询改写与检索排序

集中维护在线检索链路及算法取舍。本次设计使用的候选上限与历史候选数、耗时和动态权重分别标注，当前冲突和证据状态见 [[02_RAG系统/01_项目事实与实现状态]]；训练方法见 [[02_RAG系统/07_检索模型微调总览与协同部署]]。

> [!note] 当前设计口径（2026-10-25）
> 一个主问题约束意图，多个检索问题扩大召回，合并候选后统一精筛、精排，最后回答用户原需求。以下为本次确定的设计方案，不代表已核实的代码或生产行为；候选上限和历史效果数字仍需评测确认。

## 查询改写：指代消解与问题扩展

### 1. 问题的本质：检索系统无法理解对话上下文

单轮问答中，用户问题通常是完整自包含的。但多轮对话场景下：

```
第1轮：随机接入是什么？
第2轮：它的 preamble 序列是如何设计的？
第3轮：这个机制在 5G NR 里有什么改进？
```

第2、3轮的"它"和"这个机制"对检索系统来说是语义空洞——向量模型无法从这几个词中知道要检索什么。

此外，用户的原始问题表达往往不够检索友好。"CA 是什么"这个问题，如果知识库里的文档标题是"载波聚合技术原理"，字面匹配和短语向量都可能出现偏差。

### 2. 指代消解：还原对话中的省略主语

**任务定义**：给定多轮对话历史 + 当前问题，输出一个语义完整、不依赖对话上下文的独立问题，称为**主问题 Q₀**。只补全指代和省略信息，保留用户的对象、条件、限制及回答要求。

| 问题类型       | 示例                   | 职责                      |
| ---------- | -------------------- | ----------------------- |
| 用户原问题 Q    | “它有哪些优势，怎么配置？”       | 保留用户原始表达和需求             |
| 主问题 Q₀     | “载波聚合有哪些优势，如何配置？”    | 参与召回，作为语义精筛、精排和生成的统一依据  |
| 扩展问题 Q₁、Q₂ | “CA 的性能收益”“载波聚合配置步骤” | 补充检索表达与方向，不自动增加用户要回答的事项 |

若问题已完整，Q₀ 可以与 Q 相同；若历史不足以确定指代，不应猜测实体，需向用户澄清。

**实现方案：Prompt + Qwen3-4B**

选择 4B 小模型而非 72B 大模型的核心考量是**时延**：指代消解是每次用户提问必须走的路径，必须控制在 1s 以内。4B 模型在 vLLM 加速下可以稳定达到这个目标，而 72B 会引入 3~5s 的额外延迟，严重破坏用户体验。

**Prompt 设计的关键规则**（User Prompt 部分）：

| 规则类型 | 示例 | 处理逻辑 |
|---------|------|---------|
| 指代词推断 | "它" → 上轮主语 | 从最近一轮Q&A中提取主语实体 |
| 主语切换但意图延续 | "那5G NR呢" → 5G NR的[上轮话题] | 保留上轮话题，替换主体 |
| 时间描述推断 | "上次说的那个方案" → 具体方案名称 | 回溯对话历史定位实体 |
| 人称指代替换 | "我们公司的设备" → 结合用户SAP画像中的产品线 | 引入用户画像上下文 |

**System Prompt 的约束**：
- 强制 JSON 输出格式，防止模型自由发挥
- 给出标准化输出样例（Few-shot in system prompt）
- 明确定义"改写范围"：只消解指代和补全语义，不允许改变问题的查询意图

### 3. 问题扩展：提高召回覆盖率

**任务定义**：保留主问题 Q₀，再生成 0~2 个补充检索问题 Q₁、Q₂，得到总计 1~3 个检索问题。主问题始终参与第一层召回，避免扩展偏移后丢失原本能够命中的资料。

**设计动机**：
- 用户可能用缩写（"CA"），但文档用全称（"载波聚合"）
- 用户可能用通俗描述，文档用标准术语
- 某个复杂问题的答案可能分散在多篇文档中，单一问题无法全部命中

**扩展策略**：
- 术语扩展：缩写 → 全称，反之亦然
- 同义改写：不同的技术描述方式
- 子问题分解：复杂问题拆分为可独立检索的子问题

**数量与预算约束**：
- 总检索问题数控制在 1~3 个；问题简单时不必强行扩展。
- 对复杂问题，扩展优先覆盖用户明确提出的不同事项，例如“优势”和“配置”；关联背景只能辅助检索，不能替用户增加任务。
- 第一层采用全局候选预算，不能让每个问题都固定取两路各 1500 条，依赖去重后自然变成 3000 条。3 个问题、两路各 1500 条，去重前最多有 9000 条命中。
- 一个简单起点：全局命中预算 B = 3000，N 个检索问题共 2N 路请求，每路最多取 floor(B / 2N) 条。N = 3 时每路 500 条，去重后不超过 3000 个 Chunk。去重导致的空余无需强行补满；预算分配是否影响召回，需在固定预算下评测。

### 4. 多路并发检索的时延处理

**并发发生在第一层内部，三级之间依次执行。** 对主问题及扩展问题，分别并发发起 BM25 与 384 维向量检索；所有候选合并后，只执行一次第二层精筛与第三层精排。

```
主问题 Q₀ ── BM25 + 384维向量 ──┐
扩展问题 Q₁ ─ BM25 + 384维向量 ──┼→ 合并候选 → 第二层 → 第三层
扩展问题 Q₂ ─ BM25 + 384维向量 ──┘

合并：按 chunk_id 去重，保留来源、版本、命中问题、检索通道及各路分数
去重单位：Chunk；同一原文的不同片段可能包含互补证据，不能仅按 doc_id 删掉
```

工程上可用异步客户端和 asyncio.gather() 并发等待请求，并设置并发上限、超时及部分分支失败时的降级策略。仅声明 async 并不能让同步检索自动并发。并发通常可减少串行等待，但实际延迟仍受模型计算、下游排队和资源竞争影响，不能保证扩展后几乎不增加时延。

### 5. 有效性评估

| 评估维度     | 评估方法                                     |
| -------- | ---------------------------------------- |
| 指代消解准确率  | 人工抽样100条多轮对话，判断改写后问题是否语义完整且意图正确          |
| 问题扩展召回增益 | 固定全局候选预算，对比仅 Q₀ 与 Q₀ + 扩展问题的 Recall@3000，避免把更多候选误当作扩展收益 |
| 多事项覆盖 | 检查“优势 + 配置”等明确事项在 Top 80、最终上下文及答案中的覆盖情况 |
| 端到端耗时    | 改写模块以 1s 内为目标，同时记录扩展前后检索及整条链路的 P95 延迟；目标不等于实测结果 |
| 消融实验     | 关闭指代消解后，多轮对话场景 E2E 准确率下降幅度（验证必要性）        |

## 三级召回

系统组合使用 **[[04_工程与框架/09_Milvus]]** 向量检索与 **[[04_工程与框架/08_Elasticsearch]]** BM25 全文检索，并采用**三层逐步筛选**策略，在召回覆盖率、排序质量和查询开销之间取得平衡：

1. **第一层（粗筛）**：Q₀ 及最多两个扩展问题分别进行 BM25 + 384 维向量检索，按全局预算分配每路 Top K，合并去重后输出不超过 3000 个候选 Chunk。384 维分数用于各路召回排序，不直接替代第二层的 768 维评分。
2. **第二层（精筛）**：对合并候选，先将各查询分支缓存的 BM25 分数分别归一化，同一 Chunk 取最高归一化分数，形成关键词信号；同时只用**主问题 Q₀**的 768 维向量对全部候选统一计算语义分数。两路各取最多 Top 160，取并集后通过 **RSF（内部命名的线性分数融合方法）** 排序，输出最多 Top 80。动态权重 α 按 Q₀ 的 Token 数计算。
3. **第三层（精排）**：以 **Q₀ + 每个候选 Chunk** 组成输入，用 Cross-Encoder 统一判断其对完整需求的相关性，经截断和证据覆盖检查后输出最多 Top 10。历史候选模型为 [gte-multilingual-reranker-base](https://huggingface.co/Alibaba-NLP/gte-multilingual-reranker-base)，最终模型仍需核实。

对于“优势 + 配置”等多事项问题，应检查 Top 80 和最终上下文是否覆盖各个明确事项；必要时在现有候选中为缺失事项保留相关片段，仍遵守候选数及 Token 上限。覆盖检查不等于相关性保证，也不为凑齐事项加入低相关资料；缺少证据时在答案中说明。先采用简单的事项清单与覆盖检查，是否增加更复杂的选择算法由评测决定。

> [!tip] 第二层并未重新执行 BM25 检索
> 第二层复用第一层缓存的、按查询分支保存的 BM25 分数，先各自归一化再聚合，不直接比较不同查询的原始分数。向量路独有的候选若没有 BM25 命中记录，其关键词信号记为 0；这表示未进入该路返回列表，不代表实际 BM25 分数必然为 0。

**历史记录**：原方案记载两路各 1500、合并约 3000 → 80 → 10，以及第一层召回率 99% 以上、总耗时约 2s（0.5s + 0.5s + 1s）。这些数字缺少本次方案的评测依据，不能直接沿用为扩展检索后的保证。

> [!question] 为什么要用两个维度的向量库？
> 384 维向量在第一层大规模粗筛中计算效率更高，适合从海量文档中快速缩小候选集；768 维向量语义表达能力更强，在第二层较小候选集上可提供更精准的语义排序。两者配合实现了效率与精度的平衡。

> [!info] SAP 画像说明
> SAP 画像是基于公司 HR 系统（SAP）和历史行为日志提取的用户特征，包含 `所属 PDU`、`CQIC 方向`、`技能等级`、`岗位职能` 等维度。SAP 画像作为标量过滤条件参与 RBAC 权限控制（详见 RBAC 章节）。

## 混合召回

词法与语义互补可以在同一数据库中实现：Milvus 提供 BM25/稀疏向量，ES 9.x 扩展向量与混合检索能力。以下 ES+Milvus 分工记录原项目；当前能力和选型条件见 [[04_工程与框架/09_Milvus]]、[[04_工程与框架/08_Elasticsearch]]。

混合检索贯穿前两层：第一层并行召回 BM25 与向量候选，**第二层**对关键词和语义信号进行归一化融合。向量匹配侧重**语义相似度**，BM25 侧重**关键字精确匹配**，两者互补。

### 1. BM25 算法计算方法简析

BM25 并不是单一的词频统计，而是一种基于概率检索模型的变体，主要通过词频（TF）和逆文档频率（IDF）结合文档长度约束来进行相关度打分。其核心计算公式如下：

$$Score(Q, D) = \sum_{i=1}^{n} IDF(q_i) \cdot \frac{TF(q_i, D) \cdot (k_1 + 1)}{TF(q_i, D) + k_1 \cdot (1 - b + b \cdot \frac{|D|}{avgdl})}$$

- **$IDF(q_i)$**：查询词 $q_i$ 的逆文档频率。表示词汇的语料库稀有程度。
- **$TF(q_i, D)$**：查询词 $q_i$ 在文档 $D$ 中的本页命中词频。
- **$|D|$ 与 $avgdl$**：分别是当前被计算文档的长度和整体知识库的平均文档长度。通过引入这两个变量的比值，BM25 有效惩罚了过长的文档（避免内容庞杂的噪声烂文档由于涵盖废话词太多而占据优势）。
- **$k_1$ 与 $b$**：人工可干预的手工经验调节参数。$k_1$（通常在 1.2~2.0 之间）用于限制词频的无脑叠加增加影响权重；$b$（通常为 0.75）用于控制文档长度对得分归一化的施加力度。

### 2. 混合召回具体实现

采用 **RSF（Rank Score Fusion，内部命名的线性分数融合方法）** 算法。其本质是对归一化后的各路检索分数进行**加权线性求和**（Weighted Linear Score Fusion），区别于业界常见的基于排名倒数的 RRF（Reciprocal Rank Fusion, $\text{score} = \sum \frac{1}{k + rank_i}$）：

> [!note] RSF vs RRF 选型理由
> - **RRF** 仅依赖排名序号，丢弃了原始分数的绝对值信息，适合异构分数分布差异极大且难以归一化的场景。
> - **RSF（线性分数融合）** 保留了归一化后的分数梯度信息，在各路分数归一化后相对可比的前提下，可用于区分候选文档的相关度层次。历史记录称其 Recall@80 比 RRF 高 **3.2 个百分点**，但缺少对应评测依据，不能直接证明本次多查询聚合方案优于 RRF。

**多查询下的具体计算步骤**：

1. 对每个查询分支 i 的 BM25 命中列表，分别做 Min-Max 归一化，得到 bᵢ(d)。未命中分支的值记为 0；若分支所有分数相同，正分数统一记为 1，全为 0 则记为 0，避免除零。
2. 对同一 Chunk 取 B(d) = maxᵢ bᵢ(d)，得到关键词信号。该规则简单，但各分支第一名可能都得 1，不能据此认为不同问题的命中质量完全相同；扩展偏移和分数聚合效果需评测。
3. 用 Q₀ 的 768 维向量对第一层全部候选计算语义分数，在这个候选池内归一化为 V(d)；所有分数相同时统一记为 0，不把没有区分度的信号当作优势。
4. 分别按 B(d)、V(d) 各取最多 Top 160，合并去重得到最多 320 个片段。归一化及分数缓存先于截断完成，片段未进入某路 Top 160 时，仍使用其已算出的该路分数。
5. 在并集内计算加权综合分数，取最多 Top 80。候选不足时按实际数量返回，不补无关片段。

**综合得分公式**：

$$\text{FinalScore}(d) = \alpha \times V(d) + (1 - \alpha) \times B(d)$$

其中，$\alpha$ 代表**向量语义检索的权重**。当 $\alpha$ 趋近 0.7 时（长问题场景），系统更依赖向量语义匹配；当 $\alpha$ 趋近 0.4 时（短问题场景），系统更依赖 BM25 关键字匹配。

**动态权重 $\alpha$ 的计算**：沿用历史 Sigmoid 变体作为待评测起点，根据**主问题 Q₀** 的 Token 数量动态调整，不使用扩展问题拼接后的长度：

$$\alpha = \alpha_{\text{base}} + \frac{0.3}{1 + e^{-\frac{L - k}{s}}}$$

- **$\alpha_{\text{base}}$**：基准权重，默认为 0.4，可受用户 SAP 画像微调（如研究岗位下调至 0.35，项目管理岗位上调至 0.45）
- **$L$**：主问题 Q₀ 的 Token 数量；扩展数量不应改变同一意图的融合权重
- **$k$**：中心值，设为 8。当 $L = k$ 时，$\alpha = \alpha_{\text{base}} + 0.15$（即基准值与上限的中点）
- **$s$**：平滑系数，设为 1，控制权重过渡的坡度

## 设计决策：MMR、重排与去重的分工

MMR（Maximal Marginal Relevance）在贪心选取候选时同时考虑查询相关性和与已选文档的冗余：

$$\operatorname{MMR}=\arg\max_{d_i\in R\setminus S}\left[\lambda\operatorname{Sim}(d_i,q)-(1-\lambda)\max_{d_j\in S}\operatorname{Sim}(d_i,d_j)\right]$$

这里 R 是候选集、S 是已选集合，lambda 控制相关性与多样性的权衡。相关性和证据覆盖并不冲突：技术问答也可能需要多份互补证据。

- **Cross-Encoder 重排**：通常独立对每个 query-document pair 打分，不比较文档间冗余。两个重复且相关的片段可能都得高分，分数阈值不会自动去重。
- **Query Rewrite**：可扩大不同问题方向的召回覆盖，但不同分支仍可能返回相同文档。
- **精确去重**：合并召回分支时先按 chunk_id、规范化正文哈希等去除重复，保留来源与版本信息。
- **MMR**：可在较小候选集上减少语义冗余、提高证据覆盖；过强的多样性惩罚可能牺牲相关性，需要调 lambda 并做消融。

候选数 n、选取数 k、向量维度 d 下，缓存每个候选的最大冗余分数可将相似度计算开销控制在 O(nkd)；简单重复比较所有已选项的实现更贵。不能仅由候选数断言延迟不可接受。

**当前决策口径**：可先采用显式去重 + 重排 + 截断的简单流程。是否加入 MMR，应在固定候选集、上下文 token 预算下比较检索召回、答案质量、证据覆盖和 P95 时延；缺少消融结果时不能断言 MMR 没有价值或已被重排完全替代。

## Cross-Encoder 精排结构
不同于召回层大量使用的**双塔模型 (Bi-Encoder)**（它将问题和文档分别独立经过网络得到降维向量后再求余弦距离，缺乏深层交互），我们在重排阶段采用了 **交叉编码器模型 (Cross-Encoder)**。
- **输入拼接与深层交互层 (Self-Attention)**：
  将主问题 Q₀ 与候选片段拼接为一个序列，例如 `[CLS] Q₀ [SEP] Chunk [SEP]`，一起输入 Transformer。自注意力让问题与文档的 token 交换信息，帮助模型识别术语、数字和条件之间的关系。具体输入格式取决于所用模型。所有候选统一相对 Q₀ 打分，不分别相对扩展问题排出多份 Top 10。
- **打分输出分类层 (Classification Head)**：
  对于使用 `[CLS]` 分类头的模型，取出该 token 的最终表示，送入**线性分类头（Linear Classification Head）**，得到一个相关性分数（logit）。根据模型和训练目标，也可以再经过 Sigmoid 映射到 0～1；该值不自动等于文档相关的概率。

## 精排推理与动态截断
- **GPU 批量推理**：将粗排得到的前 80 篇候选片段组成 Batch，交给 gte-multilingual-reranker 统一打分，利用 GPU 并行计算减少逐条调用开销。历史记录称在 A30 上耗时可控制在 1s 以内；候选数 80 是否合适，仍需结合排序质量、输入长度和实际延迟评估。
- **动态截断（Threshold Cutoff）过滤低相关文档**：为减少无关内容占用上下文，按 Reranker 分数降序排列候选文档，并检查相邻分数差。历史方案以 Top 4 和 Top 5 为例：若 `diff > 0.8` 且 Top 5 的绝对分数较低，则移除 Top 5 及之后的文档。该阈值依赖模型分数尺度，需要验证；不能据此保证保留的文档都正确相关。

## 改写、Embedding 与精排的联动

```
用户原问题 Q + 必要历史
    ↓
[指代消解] → 主问题 Q₀（保留完整意图与限制）
    ↓
[问题扩展] → 保留 Q₀，追加 0~2 个检索问题
    ↓
[第一层]：各问题的 BM25 + 384维向量并发检索
    → 按 chunk_id 合并，保留分支分数 → 不超过 3000 候选
    ↓
[第二层]：分支 BM25 归一化取最大值 + Q₀ 的 768维语义评分
    → 两路各取最多 160，RSF 融合 → 最多 80 候选
    ↓
[第三层]：Q₀ + 候选片段统一 Rerank → 截断与覆盖检查 → 最多 10 片段
    ↓
[生成层]：Q + Q₀ + 必要历史 + 最终资料 + 防幻觉 Prompt → 流式答案
```

**回答时如何使用改写结果**：主问题 Q₀ 帮助模型理解指代与省略，用户原问题 Q 保留表达和回答要求；两者相同时无需重复传入。扩展问题列表默认不进入生成 Prompt，其作用通过召回资料间接体现。若拆分出用户明确提出的多个事项，可将这些事项作为覆盖清单，但不把额外扩展出的背景方向当作新增任务。生成上下文与示例见 [[02_RAG系统/05_答案生成与上下文管理]]。

三个模块是层层递进的质量保障链：
- Query 改写保证检索的**输入质量**（问题语义完整、检索词多样）
- Embedding 微调保证**向量空间的领域对齐**（近邻关系反映领域相关性而非通用语义）
- Reranker 微调保证**精排阶段的细粒度判断**（区分"表面相似但答非所问"的文档）

任何一个环节的失效都会直接体现在最终的 E2E 准确率上——这也是报告中"三类故障归因"（召回失败、重排失败、幻觉生成）能精确定责的前提。

## Query 改写的 Prompt 字段设计

### User Prompt
- **目标**：明确改写的任务目标
- **受众**：定义目标用户角色
- **规则**：
	- 多轮问题解析规则
		- 指代词推断
		- 主语切换但意图延续的场景合理改写
		- 时间描述的推断
		- 人称指代的替换（如结合用户信息）
		- 相关示例
	- 术语和关键词提取
	- 问题改写策略
	- 相关性排序逻辑
	- 最终输出格式

### System Prompt
- **目标**：定义模型角色与任务边界
- **输出格式**：JSON 结构约束描述，分别保留 `original_query`、`resolved_query`、`expanded_queries`；检索列表由 `resolved_query` 加最多两个扩展问题组成，不将这三个字段混成一个问题字符串
- **输出示例**：标准化的输出样例
