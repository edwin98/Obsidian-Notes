# 知识治理与权限隔离

维护知识分类、元数据、文档版本、幂等更新和读取授权。项目业务标签与安全权限分别执行；父块、缓存、引用和原文访问都在授权范围内。

## 知识更新

### 1+X+Y 知识集架构

从两个管理视角出发，形成 **1+X+Y** 的知识分类架构：

- **X（能力视角）**：从 CQIC 能力维度划分，共 7 个方向——设计、软件、硬件、测试、研究、产品管理、项目管理。涵盖产品技术规范、CQIC 建设课程、Wiki、社区文档、博客、案例、需求文档等
- **Y（组织视角）**：从 PDU 维度进行管理，共 8 个方向——基站产品、基站平台、解决方案、MAE、DIS、微波、GUC 等。涵盖 PDU 建设课程、交付大典、Wiki、文档、博客等
- **1（公共视角）**：通用性、跨领域的公共文档，如 IPD 流程、3GPP 协议、无线百科、技术连载、公共业务课程等

> **注意**：同一份文档允许在多个知识集中出现（即允许重复索引），但入库时仅保留一条物理记录，同时**合并所有知识集的标签**（在 Milvus 中以数组字段存储，如 `cqic_tags: ["软件", "测试"]`、`pdu_tags: ["基站产品", "MAE"]`）。

**知识集架构的设计考量**：
- 用户需要能**可见全部**的知识集
- 每个知识集的构建需要**独立看护**，不同团队优先管理和消费自己领域的知识

因此，知识集的构建过程分为三步：

1. **知识生产者**：将各自领域的知识接入 Athena 知识中心，统一看护与版本管理
2. **知识集构建者**：在 Athena 中选择本领域关注的数据源，组装形成知识集，触发向量库入库流程
3. **数据 IT**：将 1+X+Y 的知识集分别匹配对应的流水线进行知识处理（清洗 → 格式转换 → 切片 → 向量化 → 元数据标签注入），最终送入 RAG 知识库

> [!info] 1+X+Y 标签在检索时的协同过滤机制
> 检索时，系统根据用户的 SAP 画像自动取出其所属的 PDU（Y 维度）和 CQIC 方向（X 维度），构造 Milvus 标量过滤表达式（如 `expr="'基站产品' in pdu_tags or '1' in knowledge_set"`），仅在匹配的知识集范围内检索。同时结合 RBAC 的安全级别进行二次过滤（详见 RBAC 章节），实现"业务范围过滤 + 安全权限过滤"的双重保障。1（公共视角）的文档对所有用户可见，不受 X/Y 维度过滤限制。

### 元数据管理 & 标签管理

文档的元数据共分为**四类属性**：

| 属性类别       | 来源            | 内容说明                                              |
| ---------- | ------------- | ------------------------------------------------- |
| **基础属性**   | 产生于原作业系统，直接使用 | 文档唯一性标识：文档 ID、名称、作者、原链接、产生时间、创建时间、URL、密级等         |
| **管理属性**   | 产生于原作业系统，映射适配 | 文档归属信息：产品、版本、部门、领域等。需屏蔽不同原系统的差异，统一管理              |
| **知识管理属性** | 知识管理作业过程中产生   | 分类标记：CQIC 方向、PDU 归属、适用产品线、数据类型（结构化数据、文档、代码、音频、视频） |
| **召回属性**   | 入库时产生         | 检索支撑信息：向量表示、切片内容、权重、切片 ID                         |

**向量化过程**：支持通用流水线处理，如需特殊处理亦支持各产业自定义适配流水线；切片逻辑可定制；Embedding 模型可按需选择。

## 基于 LangChain 的权限控制与数据隔离 (RBAC)

过滤会影响 ANN 的候选覆盖，后过滤可能导致结果不足；pgvector iterative scan 与 Qdrant ACORN 在部分场景通过额外扫描改善召回，不能视为无成本优化。详见 [[03_Agent系统/05_记忆与上下文管理]]。

企业级 RAG 系统需要防止**数据越权访问**，例如普通员工访问无权查看的源码或内部方案。仅在接口入口检查权限还不够，检索、父文档取回、缓存和引用原文访问也需要执行一致的权限规则。这里通过 LangChain 传递用户权限信息，并在各处理步骤中校验。

### 1. 权限信息的端到端透传 (RunnableConfig)
大模型应用常同时处理多个请求，并采用异步流式输出。如果用全局变量传递权限信息，容易混用不同请求的用户数据。这里使用 LangChain 的 `RunnableConfig` 传递每次请求的权限信息：
- 当应用网关 (FastAPI) 接收并验证用户的鉴权 Token 后，会向统一下游解析出用户的关键画像信息（包含其所属的 `PDU 部门`、`安全控制级别 (Level)` 以及参与的封闭 `安全项目组标签`）。
- 将用户画像封装进 `RunnableConfig` 的 `configurable` 字典，通过 LCEL 将其传给**向量检索、工具调用和模型生成**等节点。各节点仍需显式读取并执行权限规则，配置传递本身不等于完成鉴权。

### 2. 深入底层的数据拦截 (自定义 BaseRetriever)
最安全的防泄密做法不是指望大模型去“懂事地闭嘴”，而是在**数据库拉取数据之前就执行强制的物理隔离过滤（Pre-Filtering）**。
- 我们摒弃了调用 `similarity_search` 等默认封装，而是继承并重写了 LangChain 的基类 `BaseRetriever`，打造了带有企业鉴权机制的自定义检索器 `RBAC_Milvus_Retriever`。
- 在内部拦截 `_get_relevant_documents` 与 `_aget_relevant_documents` 核心方法，动态提取出游走至此的权限 Config。
- 将用户的多维度权限拼接为一个符合底层检索引擎（ES 或 Milvus）语法的**强校验标量表达式（Boolean Expr）**。

### 3. 结合 "1+X+Y" 构建坚固防线
这一系列流转最终落地于我们的 1+X+Y 元数据分类架构上：
- 一份最高级的架构设计文档入库（Ingestion）时，早已被打上了诸如 `security_level: 4` 和 `project_tag: ["CQIC_Core_TopSecret"]` 等预制签。
- 在 Milvus 检索请求中附加权限过滤条件，例如 `expr="(doc.security_level <= user.level) and (doc.project_tag in user.projects)"`，限制候选文档范围。该表达式为示意，实际语法需与字段类型和部署版本一致。
- **权限边界**：召回、父块回溯、引用原文获取和缓存读取都必须执行相同 ACL 检查。限制 `<context>` 能减少知识库泄露，但不保证模型不会依赖预训练知识、其他输入或猜测输出敏感内容；还需应用鉴权与输出策略。

## 知识库索引更新机制与底座建设

### 1. [[04_工程与框架/09_Milvus]] 向量检索与索引优化
历史设计面向大规模 Chunk 库（实际规模待核实，见 [[02_RAG系统/01_项目事实与实现状态]]）时，项目引入 **[[04_工程与框架/09_Milvus]]** 承担向量检索，将其与 ES 全文检索分别部署，以便独立分配资源、调整索引和扩展容量。实际并发与延迟仍需压测确认。

**核心技术细节与调优策略：**
- **索引类型选择与硬件调优（HNSW）**：
  应对大量高维向量检索，在 Milvus 底层建立基于图的 `HNSW` 索引：
  - `M` (每个节点允许最大连接边数) 压至 32，在内存占用及图搜素精度间取得甜点。
  - `efConstruction` 提至 256，以增加建索引时的搜索范围，尝试改善图结构和召回效果；同时评估建库时间与资源开销。
  - 动态 `ef` 搜素配置：单机搜索调整在 128 上下，以微弱延迟获取 99% 精搜召回质量。

- **多标签标量混合搜索（Hybrid Search & Scalar Filtering）**：
  在 Milvus Collection 的 Schema 中定义 `pdu`、`cqic_tags` 等业务字段，检索时通过标量过滤限制候选范围，减少不相关文档参与后续处理。

### 2. 数据生命周期与平滑更新保障

区分 doc_id、doc_version、chunk_id，并按 chunk_id 幂等写入。新版本先在不可见范围建立全部子块、父块和 ES/Milvus 索引，验证完整性后通过应用版本目录或索引别名切换；跨数据库不具备自动原子事务，需要版本过滤及失败重试。清理旧版本与已删除切片，缓存同时失效，父块取回再次检查版本和 ACL。
面对线上随时可能发生的文档修正与淘汰：
- **软删除与版本更新（Soft Delete & Override）**：收到文档变更事件后，根据 `doc_id` 写入新版本切片，再将旧记录标记为 `deleted: true`，通过 ES/Milvus 的过滤条件排除旧版本。具体切换过程还需与下文的版本管理和失败重试策略配合。
- **低峰期索引维护**：高频更新会产生旧数据和索引维护开销，可在业务低峰期执行清理或合并。具体维护方式需区分 ES 与 Milvus 的机制，并评估对在线检索的影响。

## 不同来源文档的版本处理

版本管理的核心原则是**同一份文档只保留一条物理记录**，避免多版本同时存在导致召回时出现矛盾答案：

- **设计文档**：仅保留最新版本入库，旧版本在更新时触发离线 Pipeline 标记删除并重新入库，同时在 metadata 中注入 `pdu_tags` 和版本号信息。
- **3GPP 协议**：不同协议编号对应不同物理记录（R15/R16/R17 均保留），通过文件名与协议编号的重映射关系统一标准化，查询时可以通过标量过滤限定版本范围。
- **版本与幂等**：doc_id 标识源文档，doc_version 标识版本，chunk_id 标识该版本的切片；同一文件通常有多个 chunk 向量。以 chunk_id 幂等 upsert，更新时清理旧版本及已消失的切片，并确保父块与子块同版本。跨 ES/Milvus 的更新完成后再切换可见版本，避免新旧混读。
