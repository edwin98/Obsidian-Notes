# 检索引擎选型与过滤检索

本页比较检索产品、库与 ANN 过滤机制。历史项目分工与各产品的版本能力分别记录；不将某一项目方案当成所有检索系统的必要结构。

## 3. 向量库选型与过滤检索

| 方案 | 定位与能力 | 选型边界 |
| --- | --- | --- |
| Chroma | 本地检索开发，以及托管 Cloud 路线 | Cloud Search API 的混合检索、RRF 和自定义排序目前仅限 Cloud，不能套用到全部本地实例。 |
| FAISS | 相似性搜索库，适合自行组装索引与服务 | 持久化、服务层和权限需应用管理；cuVS、过滤及 GPU 打包能力受索引、CUDA 和平台条件影响。 |
| Milvus | 面向向量与混合检索的数据库 | 稠密、稀疏、BM25 和过滤可组合，按规模、更新、资源与实际召回评估。 |
| Qdrant | 向量数据库，提供过滤与多租户能力 | 1.16 的 ACORN 可改善某些复杂过滤场景的召回，但增加搜索开销。 |
| pgvector | PostgreSQL 内的向量扩展 | 可复用关系数据与事务能力；ANN 与过滤的交互需要单独评测。 |
| Redis | 缓存、状态与搜索能力可组合 | Redis 8 整合 Search/JSON；向量索引与缓存各有内存、持久化和隔离要求。 |
| Elasticsearch | 全文、字段过滤、向量及混合检索 | 具体索引、量化和 GPU 建索引路线受版本、部署及许可约束。 |

来源：[Chroma Cloud](https://docs.trychroma.com/cloud/getting-started)、[Cloud Search API](https://docs.trychroma.com/cloud/search-api/overview)、[FAISS 发布记录](https://github.com/facebookresearch/faiss/releases)、[Qdrant 1.16](https://qdrant.tech/blog/qdrant-1.16.x/)、[Redis 8](https://redis.io/docs/latest/develop/whats-new/8-0/)。

### 3.1 ANN 与过滤为何可能导致结果不足？

若先近似扫描、再过滤，候选中只有少部分满足条件时，最终可能不足 Top-K。不同数据库和索引的过滤执行方式并不相同，不能只看未过滤情况下的召回率。

pgvector 0.8 起提供 iterative scan，可继续扫描以缓解结果不足；strict/relaxed order 和扫描预算体现排序、召回与成本的权衡。[pgvector 文档](https://github.com/pgvector/pgvector)

Qdrant 1.16 的 ACORN 可在过滤后探索更多图节点，改善部分多条件过滤场景，但并非无成本提高准确率。其分层多租户和磁盘能力也影响选型。[官方说明](https://qdrant.tech/blog/qdrant-1.16.x/)

## 项目选型：ES 与 Milvus 的职责

原项目的 ES+Milvus 分工保留为当时实现。当前产品能力、选型因素与性能结论分别理解。

### ES 的设计定位

ES（Elasticsearch）基于 **Apache Lucene**，全文检索和结构化查询是其核心能力，同时也支持向量检索。倒排与 BM25 可概括为：

```
倒排索引：词 → 文档列表（精确、快速）
BM25：词频 + 逆文档频率 → 相关性打分
```

### 向量检索的需求

向量检索需要在高维空间中找 **近似最近邻（ANN）**，维度取决于模型与表示配置，常见索引结构包括：
- HNSW（分层可导航小世界图）
- IVF + PQ（倒排文件索引 + 乘积量化）

这些结构与词项倒排索引解决不同的检索问题，但可以集成在同一个产品中；因此不能从“ES 有倒排索引”推导出“ES 不能做向量检索”。

### 当前能力与选型因素

1. **版本与功能**：ES 9.x 已扩展 `semantic_text`、BBQ 量化和磁盘向量索引等能力。是否需要复杂全文查询、过滤和混合排序，往往比单纯按“向量库/搜索引擎”标签选择更有意义。

2. **硬件与许可**：ES 已有部分 GPU 加速向量索引路线，但建索引加速不等于所有查询在 GPU 上执行。其他引擎也需按具体索引核对 GPU 支持，不能把普通 HNSW 直接等同于 GPU 索引。

3. **资源与运维**：比较相同召回目标下的内存、磁盘、构建、更新和扩容成本，也要考虑现有全文数据与运维体系能否复用。

4. **性能与过滤**：同一数据集、过滤条件、负载和硬件下才有可解释的召回与延迟比较。没有项目实测记录，不能宣称 Milvus/FAISS 的延迟固定为 ES 的 1/3～1/5，也不能绝对断言某引擎在复杂过滤下必然更好。

来源：[ES 官方发布记录](https://www.elastic.co/docs/release-notes/elasticsearch)、[版本与许可相关问题](https://www.elastic.co/docs/release-notes/elasticsearch/known-issues)。

### 实际系统的分工

先说明当时的版本、需求、约束和实际项目分工，再说明当前框架、协议、数据库有哪些新选择。新能力出现不表示旧项目必须重做；历史没有实测的数据，也不能借新资料包装成已经验证的项目成果。框架变化见 [[04_工程与框架/10_主流Agent框架对比]]，完整目录见 [[06_调研与归档/03_笔记技术更新核查_2026-10-11]]。

```
ES（BM25）：负责关键词精确匹配，处理协议编号、参数名、专有词
Milvus：   负责语义向量检索，处理语义相似度
RSF 融合：  两路结果合并打分，取长补短
```
