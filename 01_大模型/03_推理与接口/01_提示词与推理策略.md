# 提示词与推理策略

提示词的角色、输入边界、示例和推理策略在此维护。结构化解码见 [[01_大模型/03_推理与接口/02_结构化输出与校验]]；项目专用模板在各项目专题维护。

Prompt Engineering（提示词工程）是通过精心设计和优化输入文本（Prompt），以引导大语言模型（LLM）生成高质量、符合预期输出的一门技术。以下从核心原则、经典框架到进阶策略进行全面总结。

---

## 1. 核心设计原则 (The Golden Rules)

无论使用什么模型，优秀的 Prompt 都应遵循以下三大基本原则：

1. **清晰明确 (Clarity & Specificity)**
   - **错误示范**：“写一篇关于AI的文章。”
   - **正确示范**：“写一篇 800 字的科普文章，面向初中生解答通用人工智能（AGI）是什么，要求语言风趣幽默，并举三个生活中的例子。”
   - **要点**：避免模糊的形容词，明确字数、风格、受众和具体包含的要素。

2. **提供充足上下文 (Context is King)**
   - 单次调用只看到输入上下文；持久记忆需要应用保存并选择性注入。长上下文不等于自动具备跨会话记忆。
   - 告诉模型“你是谁”、“面临什么问题”、“有哪些前置条件”。例如赋予它专家角色（Role-playing）。

3. **结构化与分隔符 (Use Separators and Structures)**
   - 使用 Markdown 标记、XML 标签（如 `<context>`, `<instructions>`, `<output_format>`）或引号（`"""`），将指令、背景数据和输出要求严格隔开。
   - 这有助于明确输入边界，但不能单独保证事实正确或消除指令遗忘。

---

## 2. 经典的 Prompt 结构框架

为了系统化地编写长篇 Prompt，业界总结了多个有效框架，最常用的是 **CRISPE** 和 **BROKE** 框架：

### CRISPE 框架（最通用）
- **C (Capacity & Role)**：能力与角色（例如：“你是一位拥有20年经验的资深 Python 架构师...”）
- **R (Rule & Context)**：规则与背景（例如：“由于新加入的实习生较多，我们需要重写代码规范...”）
- **I (Instruction)**：指令/任务（例如：“请输出一份 Python Restful API 开发的规范文档...”）
- **S (Style)**：风格（例如：“语言专业客观，采用分点论述，必要处包含代码示例...”）
- **P (Perferred Format)**：期望格式（例如：“以 Markdown 格式输出，包含目录和三个主要章节...”）
- **E (Example)**：示例（如果是Few-shot，可以在这里提供示范）。

---

## 3. 进阶提示词技巧 (Advanced Techniques)

随着任务复杂度的提升，基础的 Instruction 不够用时，需要引入以下高阶范式：

### 3.1 零样本与少样本提示 (Zero-shot & Few-shot Prompting)
- **Zero-shot**：仅提供任务描述，不给例子。（适用于简单任务和强大的基础模型，如 GPT-4, Claude 3.5 Sonnet）。
- **Few-shot**：在 Prompt 中塞入 2~5 个 (Input, Output) 的成对示例。
  - *原理*：利用 In-context Learning（上下文学习），让模型隐式学习输出的分布特征和格式约束。极大地提高输出结构的一致性。

### 3.2 推理策略入口

CoT、ToT 与 GoT 的完整机制见本页下文“CoT、ToT、GoT”。内置推理模型与显式提示分开理解；质量和时延取舍见“推理质量与时延的工程权衡”。

### 3.4 结构化输出能力 (Structured Output)

在业务流中调用 LLM，通常要求 JSON 或特定 Schema。应先了解接口能保证到哪一层：

JSON 前缀预填、停止词或 few-shot 可能帮助特定模型，但 API 未必支持，不能作为通用保证。原生严格 Schema 可以约束结构，仍需业务校验；简短理由字段按任务需要设置。[结构化输出文档](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses)

## 4. 常见陷阱与避坑指南

1. **幻觉陷阱 (Hallucination)**
   - **症状**：模型在一本正经地胡说八道。
   - **对策**：加入“知识库外拦截指令”（例如，“如果你不确定，请不要猜测，直接指出缺乏信息”）。
2. **负面指令悖论 (Negative Constraints)**
   - **症状**：告诉模型“不要输出 A”，结果它偏偏输出了 A（类似“不要想一头粉色的大象”）。
   - **对策**：将负面指令转化为正面指令。例如：将“不要输出除代码以外的废话”改为“**只**输出纯代码和必要的代码注释”。
3. **指令丢失 (Lost in the Middle)**
   - **症状**：在几千字的超长 Prompt 中，模型忽略了中间写的要求。
   - **对策**：把最核心、最强制的指令前置（写在第一段）或后置（写在最后一段，模型“记忆”最深刻的位置）；利用 `<important>` 标签包裹。

## 5. 总结：优质 Prompt 设计流
一个成熟的 Prompt 调试流应该是：

**写出初版** → **测试边界 Case** → **发现模型不听话的地方** → **补充 Few-shot 或更严格的约束条件** → **固化模板（存入代码或 Prompt 库）**。

## CoT、ToT、GoT

### CoT (Chain of Thought)

显式 CoT 提示通过输出中间步骤组织推导，可能改善某些多步任务；效果依模型与任务而定。常见方式包括：

- **Zero-shot**：直接在 Prompt 后增加一句话，如 "Let's think step by step"。
- **Few-shot**：在 Prompt 中给模型几个带有推理步骤的例子。

#### 应用场景

CoT 常用于多步计算、逻辑推导和代码分析；不要求路径唯一，也不能保证消除跳步或计算错误。

- **数学与科学计算**：
  在解决初高中数学应用题（如 GSM8K 数据集）时，CoT 能防止模型直接给出一个错误的数字。它会先列方程，再逐步求解。
- **代码逻辑解释**：
  当你给模型一段复杂的 Python 代码并询问其运行结果时，CoT 会让模型模拟解释器的行为，一行行追踪变量的变化，而不是凭感觉猜测输出。
- **简单常识推理**：
  例如判断“金字塔能否装进行李箱”，模型需要通过 CoT 先检索金字塔的大小，再检索行李箱的大小，最后进行对比。

#### 具体的实现方式

对于大部分模型，属于提示词策略；**一部分模型使用强化学习（RL）将这个思考过程内化在权重中**，成为了模型的原生能力，如 DeepSeek-R1、OpenAI o1 等。

#### CoT 可能如何帮助多步任务

1. **概率空间收敛**：本质上大模型是尝试预测下一个 Token 的概率分布。在 CoT 中，相当于引入了中间变量，每步推理都能为下一步 Token 预测提供更强的上下文约束。
2. **激活模型的慢思考模式**：模型有更多计算资源用于推理。
3. **强化注意力锚定**：在 CoT 的过程中，自注意力会更关注自己推理出的一些步骤信息，避免关键信息丢失。同时，如果 CoT 中有矛盾出现，也会有自我纠错的能力。
4. **从检索模式切换为推理模式**。

#### 局限

CoT 的收益依任务与模型而定，也可能产生错误或不忠实的解释。如果：
1. **起始步骤错误**：第一步就错了，后面会引发“幻觉级联”（Hallucination Cascade），错得更离谱。
2. **知识盲区**：模型根本不知道某个核心事实，它会一本正经地进行错误的推导。

RAG 可提供外部证据，CoT 可组织多步推导，但检索可能错误，推理也可能错误，两者均不构成事实和逻辑保证。

CoT/ToT/GoT 是组织推理与搜索过程的不同思路，不应将“把完整思维链写进输出”当成所有推理模型的统一要求。内置推理模型的提示与预算设置详见 [[01_大模型/03_推理与接口/01_提示词与推理策略]]。[官方推理提示建议](https://developers.openai.com/api/docs/guides/reasoning-best-practices)

### ToT (Tree of Thought)

CoT 为线性，一步有误，则后续都会有问题，ToT 就是为了解决这个问题。这是 **Agent 的设计范式**。

#### 工作流程

- **思维分解**：将问题分解为多个中间步骤（Thought Units）。
- **生成候选**：在每一步，模型会生成多个可能的下一步方案（分叉）。
- **状态评估**：由模型充当“评价者”，判断当前的各个分支哪个更有前途（可行、可能、不可能）。
- **搜索算法**：利用 DFS、BFS 来寻找最优解。如果发现当前路径死路一条，模型可以回溯到上一个节点重新选择。

#### 应用场景

ToT 适用于**有多个潜在解、需要反复尝试和评估**的任务。它本质上是给 LLM 增加了“后悔药”和“全局观”。

- **创意写作与剧本构思**：
  在写小说时，作者可以利用 ToT 让模型生成三个不同的情节走向（分支 A、B、C），然后评估哪个情节逻辑最通顺、最吸引人，选定后再继续向下延伸。
- **复杂的任务规划**：
  比如“策划一场去西藏的旅游”。ToT 可以同时考虑“自驾”、“飞行”和“火车”三条树状路径，并根据预算和时间节点剔除不合理的路径。

---

### GoT (Graph of Thoughts) - 思维图

核心逻辑：**非线性网络与知识聚合**

GoT 是对 ToT 的进一步升华，它认为人类的思维不只是分叉的树，还可以是错综复杂的有向图（DAG）。这是 **Agent 的设计范式**。

#### 工作方式

- **节点与边**：每个思维是一个节点，边表示推理关系。
- **变换操作**：
    - **聚合（Aggregation）**：将多个不同的思维节点合并成一个更完善的结论。
    - **精炼（Refinement）**：对某个思维节点进行迭代修正。
    - **循环（Looping）**：虽然通常是无环图，但在某些设计中允许对同一思维进行循环打磨。

**核心优势**：它可以处理具有复杂依赖关系的问题，支持不同推理路径之间的信息交换和优势互补。

#### 应用场景

- **长文档摘要与信息整合**：如果要总结一本 300 页的书，GoT 可以先分章节总结（生成节点），然后将相关的章节总结进行合并（Aggregation），最后通过对比和去重，精炼出（Refinement）全书的核心观点。
- **复杂系统架构设计**：在设计一个微服务架构时，模型可以先生成存储方案和通信方案，然后将这两个节点连接起来，观察它们是否兼容。如果不兼容，则返回修改其中一个节点，直到整张图逻辑自洽。
- **新药发现或材料科学**：研究人员可以利用 GoT 让模型组合不同的化学分子式。节点 A 是某种特性，节点 B 是另一种特性，通过图的合并操作，探索是否存在某种新的组合能同时满足两者的优势。

## 推理质量与时延的工程权衡

### 先区分显式 CoT、模型推理与结构约束

SFT 可以学习行为和风格，原生严格 Schema 或约束解码则控制生成结构。JSON 可解析、Schema 合法和业务正确是不同层次；内置推理模型也通常无需额外要求“逐步思考”。理由摘要字段按业务需要设置，不是必选项。[结构化输出文档](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses)、[推理提示建议](https://developers.openai.com/api/docs/guides/reasoning-best-practices)

见 [[01_大模型/03_推理与接口/02_结构化输出与校验]]、[[01_大模型/03_推理与接口/01_提示词与推理策略]]。

推理强度/预算与最终回答长度分别控制不同部分；模型 API 的参数名和支持范围不同，不应默认所有服务都支持同一个 thinking_budget。[推理接口文档](https://developers.openai.com/api/docs/guides/reasoning)

这是精度-延迟的经典 tradeoff，有以下几种应对策略：

### 策略 1：Adaptive CoT（按难度决定是否开启）

不是所有问题都需要 CoT。对问题做难度分类：
- 简单问题（意图明确、参数直接）：直接输出答案，不开 CoT
- 复杂问题（多步推理、歧义消解）：才触发 CoT

实现方式：在 Agent 的路由节点加一个轻量分类器（或用 LLM 的 `thinking_budget` 参数），根据问题复杂度动态分配推理 token 上限。

### 策略 2：Budget Forcing（给推理设置 token 预算）

在支持预算或推理强度设置的模型上，按接口控制推理开销；max_tokens 可能限制总输出并引发截断，不等于通用的独立思考预算。强制结束符也需要模型与服务支持，不能保证截断后得到有效答案。

### 策略 3：思维链蒸馏

用带完整 CoT 的大模型输出，训练小模型让其"内化"推理过程。训练好的小模型推理时可以直接给出答案，无需显式输出长思维链。是否减少显式推理、保留多少准确率与速度收益，需要按训练目标与任务实测。

### 策略 4：并行推理取最快

对同一问题并发发起多条推理路径，取最先完成的高置信答案。适合对延迟极敏感的场景，但会增加计算成本。

### 策略 5：Speculative Decoding 加速 CoT token 生成

结合 MTP 或草稿模型，加快 CoT token 的生成速度，在不减少推理步骤的前提下降低端到端延迟。

**在我们系统中的做法**：Adaptive CoT——Guardrail 节点（安全判断，快速）不用 CoT；结果判定节点（根因分析，需要推理）才用 CoT，并对 thinking token 设置上限（1024 token）。

## 消息角色与 Prompt 的组织

消息角色与 Prompt 的字符串组织是不同层次。System（或提供方的 developer）承载应用指令，user 承载用户请求，tool/工具结果 Item 承载执行反馈；具体接口结构见 [[03_Agent系统/03_Function-Calling与消息协议#消息结构与调用关联]]。

RAG 内容可以作为有明确来源边界的数据注入，不能因为它是动态内容就当作更高优先级指令。对话摘要也应标明是历史数据。工具返回保留工具角色与调用 ID，不统一改成 user。

前缀缓存取决于实际序列前缀及服务支持范围，不简单由消息角色决定。固定指令在前、动态输入在后通常有利于复用，但仍需按部署配置确认。
