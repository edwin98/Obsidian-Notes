# 提示词与推理策略

提示词的角色、输入边界、示例和推理策略在此维护。结构化解码见 [[01_大模型/03_推理与接口/02_结构化输出与校验]]；项目专用模板在各项目专题维护。

Prompt Engineering（提示词工程）是通过精心设计和优化输入文本（Prompt），以引导大语言模型（LLM）生成高质量、符合预期输出的一门技术。以下从核心原则、经典框架到进阶策略进行全面总结。

---

## 1. 核心设计原则 (The Golden Rules)

无论使用什么模型，优秀的 Prompt 都应遵循以下三大基本原则：

1. **清晰明确 (Clarity & Specificity)**
   - **错误示范**：“写一篇关于AI的文章。”
   - **正确示范**：“写一篇 800 字的科普文章，面向初中生解答通用人工智能（AGI）是什么，要求语言风趣幽默，并举三个生活中的例子。”
   - **要点**：避免模糊的形容词，明确字数、风格、受众和具体包含的要素。

2. **提供充足上下文 (Context is King)**
   - 单次调用只看到输入上下文；持久记忆需要应用保存并选择性注入。长上下文不等于自动具备跨会话记忆。
   - 告诉模型“你是谁”、“面临什么问题”、“有哪些前置条件”。例如赋予它专家角色（Role-playing）。

3. **结构化与分隔符 (Use Separators and Structures)**
   - 使用 Markdown 标记、XML 标签（如 `<context>`, `<instructions>`, `<output_format>`）或引号（`"""`），将指令、背景数据和输出要求严格隔开。
   - 这有助于明确输入边界，但不能单独保证事实正确或消除指令遗忘。

---

## 2. 经典的 Prompt 结构框架

为了系统化地编写长篇 Prompt，业界总结了多个有效框架，最常用的是 **CRISPE** 和 **BROKE** 框架：

### CRISPE 框架（最通用）
- **C (Capacity & Role)**：能力与角色（例如：“你是一位拥有20年经验的资深 Python 架构师...”）
- **R (Rule & Context)**：规则与背景（例如：“由于新加入的实习生较多，我们需要重写代码规范...”）
- **I (Instruction)**：指令/任务（例如：“请输出一份 Python Restful API 开发的规范文档...”）
- **S (Style)**：风格（例如：“语言专业客观，采用分点论述，必要处包含代码示例...”）
- **P (Perferred Format)**：期望格式（例如：“以 Markdown 格式输出，包含目录和三个主要章节...”）
- **E (Example)**：示例（如果是Few-shot，可以在这里提供示范）。

---

## 3. 进阶提示词技巧 (Advanced Techniques)

随着任务复杂度的提升，基础的 Instruction 不够用时，需要引入以下高阶范式：

### 3.1 零样本与少样本提示 (Zero-shot & Few-shot Prompting)
- **Zero-shot**：仅提供任务描述，不给例子。（适用于简单任务和强大的基础模型，如 GPT-4, Claude 3.5 Sonnet）。
- **Few-shot**：在 Prompt 中塞入 2~5 个 (Input, Output) 的成对示例。
  - *原理*：利用 In-context Learning（上下文学习），让模型隐式学习输出的分布特征和格式约束。极大地提高输出结构的一致性。

### 3.2 推理策略入口

CoT、ToT 与 GoT 的完整机制见本页下文“CoT、ToT、GoT”。内置推理模型与显式提示分开理解；质量和时延取舍见“推理质量与时延的工程权衡”。

### 3.4 结构化输出能力 (Structured Output)

在业务流中调用 LLM，通常要求 JSON 或特定 Schema。应先了解接口能保证到哪一层：

JSON 前缀预填、停止词或 few-shot 可能帮助特定模型，但 API 未必支持，不能作为通用保证。原生严格 Schema 可以约束结构，仍需业务校验；简短理由字段按任务需要设置。[结构化输出文档](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses)

详见 [[01_大模型/03_推理与接口/02_结构化输出与校验]]。

## 4. 常见陷阱与避坑指南

1. **幻觉陷阱 (Hallucination)**
   - **症状**：模型在一本正经地胡说八道。
   - **对策**：加入“知识库外拦截指令”（例如，“如果你不确定，请不要猜测，直接指出缺乏信息”）。
2. **负面指令悖论 (Negative Constraints)**
   - **症状**：告诉模型“不要输出 A”，结果它偏偏输出了 A（类似“不要想一头粉色的大象”）。
   - **对策**：将负面指令转化为正面指令。例如：将“不要输出除代码以外的废话”改为“**只**输出纯代码和必要的代码注释”。
3. **指令丢失 (Lost in the Middle)**
   - **症状**：在几千字的超长 Prompt 中，模型忽略了中间写的要求。
   - **对策**：把最核心、最强制的指令前置（写在第一段）或后置（写在最后一段，模型“记忆”最深刻的位置）；利用 `<important>` 标签包裹。

## 5. 总结：优质 Prompt 设计流
一个成熟的 Prompt 调试流应该是：

**写出初版** → **测试边界 Case** → **发现模型不听话的地方** → **补充 Few-shot 或更严格的约束条件** → **固化模板（存入代码或 Prompt 库）**。

## CoT、ToT、GoT

### CoT (Chain of Thought)

显式 CoT 提示通过输出中间步骤组织推导，可能改善某些多步任务；效果依模型与任务而定。常见方式包括：

- **Zero-shot**：直接在 Prompt 后增加一句话，如 "Let's think step by step"。
- **Few-shot**：在 Prompt 中给模型几个带有推理步骤的例子。

#### 应用场景

CoT 常用于多步计算、逻辑推导和代码分析；不要求路径唯一，也不能保证消除跳步或计算错误。

- **数学与科学计算**：
  在解决初高中数学应用题（如 GSM8K 数据集）时，CoT 可以引导模型先列方程、再逐步求解，便于检查中间步骤；仍可能算错。
- **代码逻辑解释**：
  当你给模型一段复杂的 Python 代码并询问其运行结果时，可要求逐步追踪变量变化；模型的文字推演仍需与实际执行结果核对。
- **简单常识推理**：
  例如判断“某个模型摆件能否装进行李箱”，可以分解为获取双方尺寸、考虑摆放方向、比较空间限制；检索或测量需要外部信息，CoT 本身不执行检索。

#### 具体的实现方式

显式 CoT 可以通过提示词引导；现代推理模型还会通过后训练学习推理行为。需要分别理解“能力如何训练出来”“推理时如何执行”和“接口展示什么”，具体见下一节。

#### 现代模型如何实现思维链

**不只是加一句 “Let's think step by step”。** 这句话是经典的 Zero-shot CoT 提示：在推理时引导已有模型输出中间步骤，不会更新模型权重，也不等于训练出了推理能力。[Zero-shot CoT 原论文](https://arxiv.org/abs/2205.11916)

| 层次 | 主要机制 | 改变什么 |
|---|---|---|
| 提示词 | 逐步思考指令、带推导的 few-shot 示例 | 本次输入与生成路径 |
| 后训练 | 推理轨迹 SFT、可验证奖励 RL、蒸馏等 | 模型权重与生成行为 |
| 推理执行 | 生成额外推理 token，再生成答案 | 本次计算量与上下文 |
| 接口控制 | 思考开关、推理强度或预算、推理内容解析与展示 | 如何触发、约束和呈现推理 |

**一、训练阶段：让模型学会组织和改进推理。** 以公开的 DeepSeek-R1 报告为例：

1. **冷启动 SFT**：使用高质量长推理样本，让基座学习较可读的推导方式和回答格式。
2. **面向推理的 RL**：对同一问题采样回答，利用数学答案校验、代码测试等反馈优化策略，提高有效解题路径的概率。GRPO 是一种训练算法，不是运行时的“思考开关”。
3. **拒绝采样与再次 SFT**：筛选生成的高质量轨迹，结合其他任务数据训练，进一步改善推理与通用回答能力。
4. **进一步对齐或蒸馏**：完整 R1 还进行通用场景 RL；另外，可用教师模型的推理轨迹通过 SFT 训练较小模型，学生不一定需要复制教师的全部 RL 流程。

这是一条公开训练路线，不是所有模型的统一配方。**R1-Zero 与 R1 要区分**：R1-Zero 从预训练基座直接进行 RL，没有先做冷启动 SFT；它仍有训练模板与格式约束，并非完全没有提示或先验结构。[DeepSeek-R1 技术报告，第 2 节](https://arxiv.org/html/2501.12948v1)

**二、推理阶段：训练好的模型仍可能逐 token 生成推理过程。** 对上述文本推理模型，可用下面的简化流程理解：

```text
问题 + 对话模板 + 思考模式设置
                ↓
生成推理 token：拆解问题、尝试方案、检查中间结果
                ↓
到达相应模式的推理结束边界
                ↓
生成最终答案
```

推理 token 作为前缀参与后续生成，因此能给多步任务提供额外计算步骤。这不要求增加一个独立的“思维链神经网络”。**“能力学进权重”不等于“运行时不再生成思维链”**；也不能仅凭回答简短判断推理计算少。

**三、模式控制依赖训练、模板和服务实现。** 以 2025 年发布的原始 Qwen3 混合思考模型为例，官方公开了长 CoT 冷启动、推理 RL、思考模式融合和通用 RL 的训练流程。其 Transformers 示例通过 chat template 的 `enable_thinking` 控制思考模式，并解析 `</think>` 边界区分推理内容和答案；在支持的模式下，`/think`、`/no_think` 还可提供软切换。[Qwen3 官方训练与使用说明](https://qwenlm.github.io/blog/qwen3/)

这些控制方式基于对应模型已经学到的行为。给任意模型套上 `<think>` 标签，或在不支持的 API 中增加同名参数，并不会自动获得同等推理能力。不同型号可能固定为思考或非思考模式，参数需按具体版本核对。

**四、可见内容与实际推理要分开。** 有些服务返回推理文本，有些隐藏推理或只返回摘要；例如 Claude 的 thinking 文档说明，展示内容可能是推理摘要。最终回答中的解释、接口的思考摘要和完整生成轨迹不能直接画等号。[Claude thinking 文档](https://platform.claude.com/docs/en/build-with-claude/thinking)

即使拿到完整文本轨迹，它也不保证忠实解释所有影响答案的因素；是否推理正确，仍应通过答案验证、工具结果和测试判断。[CoT 忠实性研究](https://arxiv.org/abs/2505.05410)

**使用时怎么做**：普通指令模型可比较“直接回答”和“提供关键推导”的实际效果；内置推理模型优先使用其支持的模式或预算控制，提示中明确任务、条件、验证标准和需要的解释即可。思考预算与答案长度应分开理解，不能把长篇输出直接当作能力更强。

训练算法见 [[01_大模型/02_训练与对齐/02_偏好对齐算法_PPO_DPO_GRPO]]；质量、时延与预算的取舍见本页 [[01_大模型/03_推理与接口/01_提示词与推理策略#推理质量与时延的工程权衡]]。

#### 如何实现不同的推理强度（低中高）

**一句话**：低/中/高通常不是三个不同的模型，也不只是把 `max_tokens` 调小。它一般由三层共同实现：**接口参数 → 写入模型能识别的控制信号；训练 → 让模型学会按信号调整思考长度和深度；推理执行 → 用预算上限或强制结束兜底**。

| 层次   | 做法                                         | 作用                    |
| ---- | ------------------------------------------ | --------------------- |
| 接口映射 | 服务把 `effort=low` 等参数翻译成模板里的控制信号，或换成对应的内部配置 | 让同一个模型知道“这次该想多少”      |
| 训练   | 条件化 SFT、带长度或成本惩罚的 RL、自适应思考训练               | 让档位与推理长度、准确率形成稳定的单调关系 |
| 推理执行 | 思考 token 上限、budget forcing、并行采样或投票         | 硬性控制成本；部分最高档可能叠加更多计算  |

**一、接口层：把档位变成模型看得见的信号。** 开放权重的 gpt-oss 是一个透明的例子：在系统消息里写 `Reasoning: low / medium / high`，模型在训练时已学过不同设置对应的推理长度，所以同一份权重可以输出不同长度的思维链。[gpt-oss 模型卡](https://arxiv.org/abs/2508.10925) 闭源 API 的内部映射不公开，但对外参数类似：

| 服务（截至 2026-10）   | 参数                                 | 档位                                                 | 备注                                                                          |
| ---------------- | ---------------------------------- | -------------------------------------------------- | --------------------------------------------------------------------------- |
| OpenAI Responses | `reasoning.effort`                 | none / minimal / low / medium / high / xhigh / max | 支持的值和默认值因型号而异；推理 token 按输出计费，`max_output_tokens` 同时限制推理和可见输出                |
| Claude           | `output_config.effort`             | low / medium / high / xhigh / max                  | 影响全部输出，包括文本、工具调用和 thinking；它是行为信号，不是严格的 token 预算；在自适应 thinking 下也控制思考的频率和深度 |
| Gemini           | `thinking_level`                   | minimal / low / medium / high（按型号）                 | 默认动态思考，会按请求复杂度自行调整                                                          |
| DeepSeek V4      | `reasoning_effort`，或 `thinking` 开关 | low / high / max                                   | 请求 medium 实际按 high 处理，xhigh 按 high，ultra 按 max                              |

DeepSeek 的映射表说明：**对外档位数量不等于模型内部真实的档位数量**，服务方可以把多个档位合并。

来源：[OpenAI 推理指南](https://developers.openai.com/api/docs/guides/reasoning)、[Claude effort 文档](https://platform.claude.com/docs/en/build-with-claude/effort)、[Gemini thinking 文档](https://ai.google.dev/gemini-api/docs/thinking)、[DeepSeek 思考模式文档](https://api-docs.deepseek.com/guides/thinking_mode)

**二、训练层：让模型学会“按档位分配思考量”。** 只在提示里写“少想一点”，没有经过训练的模型往往不稳定。常见的公开思路：

1. **条件化 SFT**：同一道题采样多条推理轨迹，按长度或深度分桶，标上 low/medium/high 的控制前缀再做 SFT，让模型把信号和推理长度关联起来。
2. **带长度约束的 RL**：L1（LCPO）在提示中给出目标长度，奖励 = 答案正确性 − α·|实际长度 − 目标长度|，训练后模型能较好地遵守长度要求。[L1 论文](https://arxiv.org/abs/2503.04697) Kimi k1.5 在 RL 中加入长度惩罚，并用 long2short 方法把长推理压缩成短推理。[Kimi k1.5 报告](https://arxiv.org/abs/2501.12599) 不同档位可以对应不同的目标长度或惩罚系数。
3. **自适应思考**：在同一档位内，简单题少想、难题多想。档位设定的是倾向或上限，不是固定的 token 数。

**三、推理执行层：不改权重也能控制，或作为兜底。**

- **Budget forcing**：s1 在思考达到预算时强制插入思考结束标记，让模型直接给出答案；想让它多想时，就把结束标记换成 “Wait”，让推理继续。[s1 论文](https://arxiv.org/abs/2501.19393) 这种方法简单，但强行截断可能让答案质量明显下降。
- **硬上限**：例如 thinking 预算或 `max_output_tokens`。超出时可能直接截断，甚至没有可见答案。
- **加宽计算**：多路采样后投票或择优（self-consistency、best-of-n），是“想得更长”之外的另一个维度。部分服务的最高档或 pro 模式可能使用这类方法，但具体实现以官方说明为准。

```text
请求 effort=low
      ↓ 服务层映射
对话模板注入控制信号（如 "Reasoning: low"）+ 可选思考 token 上限
      ↓ 模型（训练时学过档位 ↔ 推理长度/深度的对应关系）
较短的推理 token → 思考结束边界 → 最终答案
      ↓ 兜底
超出预算：强制结束思考 / 截断
```

**如果自己给开源模型做档位**：①对每道题采样多条轨迹，按长度分桶并加控制前缀，做 SFT；②RL 奖励中加入与档位相关的长度项；③推理时用 budget forcing 设置硬上限；④评估时画出每个档位的“准确率–平均推理 token”曲线，确认档位单调、高档确实有收益。

**注意**：
- 档位越高并不保证越准，可能出现过度思考，成本和延迟也会上升，应以评测结果选档。
- 推理强度与最终回答长度是两回事。
- 不同服务的参数名和取值不能混用；在不支持的模型上传同名参数不会自动生效。

**面试回答要点**：推理强度 = 推理时计算量的可控旋钮。实现上分三层：①API 参数映射成模板里的控制信号；②后训练（条件化 SFT 加长度感知 RL）让模型学会按信号调节思考长度，并在档内按难度自适应；③推理时用 token 预算或 budget forcing 做硬约束。高档有时还会叠加并行采样。最后用准确率–token 曲线评估和选择档位。

#### CoT 可能如何帮助多步任务

1. **保留中间结果**：已生成步骤成为后续 token 的上下文，模型可继续利用方程、变量和子结论。
2. **增加推理时计算**：生成更多推理 token 意味着执行更多解码步骤，但收益取决于任务与模型，并非越长越好。
3. **提供检查机会**：模型可以比较候选路径、检查矛盾并修正先前步骤；是否真的纠错需要验证，不能由“让我检查一下”等措辞推断。

#### 局限

CoT 的收益依任务与模型而定，也可能产生错误或不忠实的解释。如果：
1. **起始步骤错误**：第一步就错了，后面会引发“幻觉级联”（Hallucination Cascade），错得更离谱。
2. **知识盲区**：模型根本不知道某个核心事实，它会一本正经地进行错误的推导。

RAG 可提供外部证据，CoT 可组织多步推导，但检索可能错误，推理也可能错误，两者均不构成事实和逻辑保证。

---

CoT/ToT/GoT 是组织推理与搜索过程的不同思路，不应将“把完整思维链写进输出”当成所有推理模型的统一要求。内置推理模型的实现见本页 [[01_大模型/03_推理与接口/01_提示词与推理策略#现代模型如何实现思维链]]；预算设置见“推理质量与时延的工程权衡”。

### ToT (Tree of Thought)

CoT 为线性，一步有误，则后续都会有问题，ToT 就是为了解决这个问题。这是 **Agent 的设计范式**。

#### 工作流程

- **思维分解**：将问题分解为多个中间步骤（Thought Units）。
- **生成候选**：在每一步，模型会生成多个可能的下一步方案（分叉）。
- **状态评估**：由模型充当“评价者”，判断当前的各个分支哪个更有前途（可行、可能、不可能）。
- **搜索算法**：利用 DFS、BFS 来寻找最优解。如果发现当前路径死路一条，模型可以回溯到上一个节点重新选择。

#### 应用场景

ToT 适用于**有多个潜在解、需要反复尝试和评估**的任务。它本质上是给 LLM 增加了“后悔药”和“全局观”。

- **创意写作与剧本构思**：
  在写小说时，作者可以利用 ToT 让模型生成三个不同的情节走向（分支 A、B、C），然后评估哪个情节逻辑最通顺、最吸引人，选定后再继续向下延伸。
- **复杂的任务规划**：
  比如“策划一场去西藏的旅游”。ToT 可以同时考虑“自驾”、“飞行”和“火车”三条树状路径，并根据预算和时间节点剔除不合理的路径。

---

### GoT (Graph of Thoughts) - 思维图

核心逻辑：**非线性网络与知识聚合**

GoT 是对 ToT 的进一步升华，它认为人类的思维不只是分叉的树，还可以是错综复杂的有向图（DAG）。这是 **Agent 的设计范式**。

#### 工作方式

- **节点与边**：每个思维是一个节点，边表示推理关系。
- **变换操作**：
    - **聚合（Aggregation）**：将多个不同的思维节点合并成一个更完善的结论。
    - **精炼（Refinement）**：对某个思维节点进行迭代修正。
    - **循环（Looping）**：虽然通常是无环图，但在某些设计中允许对同一思维进行循环打磨。

**核心优势**：它可以处理具有复杂依赖关系的问题，支持不同推理路径之间的信息交换和优势互补。

#### 应用场景

- **长文档摘要与信息整合**：如果要总结一本 300 页的书，GoT 可以先分章节总结（生成节点），然后将相关的章节总结进行合并（Aggregation），最后通过对比和去重，精炼出（Refinement）全书的核心观点。
- **复杂系统架构设计**：在设计一个微服务架构时，模型可以先生成存储方案和通信方案，然后将这两个节点连接起来，观察它们是否兼容。如果不兼容，则返回修改其中一个节点，直到整张图逻辑自洽。
- **新药发现或材料科学**：研究人员可以利用 GoT 让模型组合不同的化学分子式。节点 A 是某种特性，节点 B 是另一种特性，通过图的合并操作，探索是否存在某种新的组合能同时满足两者的优势。

## 推理质量与时延的工程权衡

### 先区分显式 CoT、模型推理与结构约束

SFT 可以学习行为和风格，原生严格 Schema 或约束解码则控制生成结构。JSON 可解析、Schema 合法和业务正确是不同层次；内置推理模型也通常无需额外要求“逐步思考”。理由摘要字段按业务需要设置，不是必选项。[结构化输出文档](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses)、[推理提示建议](https://developers.openai.com/api/docs/guides/reasoning-best-practices)

见 [[01_大模型/03_推理与接口/02_结构化输出与校验]]、[[01_大模型/03_推理与接口/01_提示词与推理策略]]。

推理强度/预算与最终回答长度分别控制不同部分；模型 API 的参数名和支持范围不同，不应默认所有服务都支持同一个 thinking_budget。[推理接口文档](https://developers.openai.com/api/docs/guides/reasoning)

这是精度-延迟的经典 tradeoff，有以下几种应对策略：

### 策略 1：Adaptive CoT（按难度决定是否开启）

不是所有问题都需要 CoT。对问题做难度分类：
- 简单问题（意图明确、参数直接）：直接输出答案，不开 CoT
- 复杂问题（多步推理、歧义消解）：才触发 CoT

实现方式：在 Agent 的路由节点加一个轻量分类器（或用 LLM 的 `thinking_budget` 参数），根据问题复杂度动态分配推理 token 上限。

### 策略 2：Budget Forcing（给推理设置 token 预算）

在支持预算或推理强度设置的模型上，按接口控制推理开销；max_tokens 可能限制总输出并引发截断，不等于通用的独立思考预算。强制结束符也需要模型与服务支持，不能保证截断后得到有效答案。

### 策略 3：思维链蒸馏

用带完整 CoT 的大模型输出，训练小模型让其"内化"推理过程。训练好的小模型推理时可以直接给出答案，无需显式输出长思维链。是否减少显式推理、保留多少准确率与速度收益，需要按训练目标与任务实测。

### 策略 4：并行推理取最快

对同一问题并发发起多条推理路径，取最先完成的高置信答案。适合对延迟极敏感的场景，但会增加计算成本。

### 策略 5：Speculative Decoding 加速 CoT token 生成

结合 MTP 或草稿模型，加快 CoT token 的生成速度，在不减少推理步骤的前提下降低端到端延迟。

**在我们系统中的做法**：Adaptive CoT——Guardrail 节点（安全判断，快速）不用 CoT；结果判定节点（根因分析，需要推理）才用 CoT，并对 thinking token 设置上限（1024 token）。

## 消息角色与 Prompt 的组织

消息角色与 Prompt 的字符串组织是不同层次。System（或提供方的 developer）承载应用指令，user 承载用户请求，tool/工具结果 Item 承载执行反馈；具体接口结构见 [[03_Agent系统/03_Function-Calling与消息协议#为什么需要好几种编号]]。

RAG 内容可以作为有明确来源边界的数据注入，不能因为它是动态内容就当作更高优先级指令。对话摘要也应标明是历史数据。工具返回保留工具角色与调用 ID，不统一改成 user。

前缀缓存取决于实际序列前缀及服务支持范围，不简单由消息角色决定。固定指令在前、动态输入在后通常有利于复用，但仍需按部署配置确认。
