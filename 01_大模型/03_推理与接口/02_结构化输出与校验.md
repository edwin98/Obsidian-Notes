# 大模型输出结构化数据的技术解析

在AI应用落地的真实工程场景中（如开发Agent、数据提取、API对接），我们往往不能依赖大模型输出模糊的自然语言文本。系统通常需要 **JSON、XML 或特定代码对象**这样可以被机器明确解析的结构化数据。

大模型通过预测下一个 token（Next-token Prediction）生成内容，不能仅凭自然语言指令就保证输出符合指定结构。本文介绍结构化输出的方法、常见失败原因和处理方案。

---

## 一、 如何让模型输出结构化数据？

常见方法包括提示词约束、模型接口原生支持和解码层约束。它们作用的层次不同，也可以组合使用：

### 1. 提示词与预处理方式 (Prompt Engineering)
最基础的方式是直接在 System Prompt 中强调输出格式，并提供示例。

*   **做法**：在提示词中写明 `请严格输出JSON格式，不要包含任何其他多余文本，格式如下: {"name": "...", "age": ...}`，并提供 Few-Shot（少样本样例）。
*   **优点**：对所有模型通用，不需要额外的API支持。
*   **缺点**：非常不稳定。模型经常会在 JSON 外面加上“好的，这是你要的数据：…”或者使用 Markdown 代码块包裹，导致代码解析直接抛出 `JSONDecodeError`。

### 2. 模型原生方式 (Native Support)

原生接口的保证需要按层次区分：

| 层次             | 保证什么             | 不保证什么             |
| -------------- | ---------------- | ----------------- |
| JSON 格式合法      | 可以按 JSON 解析      | 字段和类型符合目标 Schema。 |
| JSON Schema 合法 | 满足受支持的字段、类型和结构约束 | 数值、事实、权限与业务关系正确。  |
| 业务校验通过         | 满足应用定义的业务规则      | 未被规则覆盖的事实天然可信。    |

OpenAI 原生 Structured Outputs 提供严格 JSON Schema 路径。Responses 的用户输出通过 `text.format` 配置，工具参数通过工具定义配置；JSON mode 与严格 Schema 不能混为一谈。还应分别识别拒绝、截断和 incomplete 状态，不把所有异常都归为 JSON 解析失败。[官方文档](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses)

Function Calling 表达调用意图，应用负责校验并执行工具。工具参数可以采用严格 JSON Schema，但不等于模型返回调用时动作已完成。API 原生支持也可能依赖约束解码，两者不是互斥分类。

Responses 与 Chat Completions 的结构化配置位置不同；本地“OpenAI 兼容接口”不代表实现全部原生约束。[Responses 迁移文档](https://developers.openai.com/api/docs/guides/migrate-to-responses)

### 3. 框架限制/解码层强约束模式 (Constrained Decoding)
自托管推理可通过解码层约束结构；应先确认模型、后端与受支持的 Schema 子集。OpenAI 原生严格 Structured Outputs 也提供结构约束，并非只有第三方框架才能做到。

*   **原理解析（深入浅出）**：
    大模型生成文本的最后一步，是输出一个包含词表中所有 token 概率的分布（Logits）。
    比如模型想输出一个布尔值，下一刻的概率分布可能是：`{"true": 0.8, "false": 0.15, "yes": 0.05}`。
    约束解码在生成下一个 token 前应用格式规则，将 Pydantic 类或 JSON Schema 转换为**有限状态机（FSM）或上下文无关文法（CFG）**等约束表示。
    每生成一个 token，框架都会检查它是否符合当前语法和结构约束，并**屏蔽不允许出现的 token**，使其不会被选中。
    例如，当前结构只允许结束对象时，其他不符合规则的 token 会被排除。约束解码能限制受支持的语法与结构，但不能保证业务含义正确；拒绝、截断和运行异常仍需处理。
*   **代表框架**：
    *   **Instructor (Python)**：基于 Pydantic 的封装库，可结合 Tool Calling 返回经过类型校验的 Python 对象。
    *   **Outlines / SGLang**：基于正则表达式与文法控制的高性能解码约束框架。
    *   **LangChain Output Parsers**：偏向上层封装，提供 `PydanticOutputParser` 等解析器；重试和修复需要单独配置或组合，解析器本身不等于约束解码。

## 二、 失败的原因分析：为什么依然会出错？

即使使用原生支持或约束框架，结构化输出仍可能失败，常见原因如下：

1.  **Schema 设计过于复杂或嵌套过深**
    *   模型的能力有限。如果你让模型阅读一篇文章，并输出一个包含七八层嵌套、几十个字段的庞大 JSON 树，复杂抽取任务可能出现内容遗漏或错误填值；严格 Schema 约束结构，不能保证每个字段内容准确。
2.  **指令与强制输出格式存在冲突**
    *   *举例*：如果你的 Prompt 里写着：“请仔细推理每一步并解释原因，最后输出 JSON”，但是你的 JSON Schema 里却**没有专门预留“reasoning（推理）”这个字段**。
    *   提示中要求解释、Schema 却不允许解释，会造成需求冲突。普通文本生成可能混入多余文字；严格模式仍应按允许的结构输出。内置推理模型不要求公开完整思维链，可将业务需要的简短理由显式纳入 Schema。
3.  **输出省略与 Token 截断**
    *   当需要生成的 JSON 数组太长（如提取网页中的所有商品清单），可能触发 `max_tokens` 限制。由于达到了最大输出长度，JSON 的生成戛然而止（比如停在 `{"items": [{"name"...`），导致完整的 JSON **没有闭合**。
    *   在没有严格结构约束时，模型可能直接输出 `[...此处省略 50 个元素]` 等说明文字，导致 JSON 解析失败。
4.  **特殊字符转义错误**
    *   提取的文本中本身包含没有正确转义的引号（`"`）或回车符（`\n`）。例如模型输出了：`{"comment": "他说："你好""}`，这里的双引号引发了格式错误。

## 三、 失败的处理方式（工程化兜底与修复）

任何生产环境都不应建立在“相信大模型永远输出正确代码”的假设上。标准的大模型工程系统必须具备以下兜底机制：

### 1. 引入“容错与半启发式解析” (Fuzzy Parsing)
模型输出可能包含额外文字或格式错误，可以根据失败类型增加预处理：
*   **正则提取**：使用正则表达式截取 \```json 和 \``` 之间的特定内容。
*   **容错解析库**：`json-repair` 等库可通过启发式规则尝试补全缺失括号、修正部分转义错误。但修复结果可能与原意不同，不能恢复被截断的未知内容，仍需验证关键字段。

### 2. 重试机制与自我纠错 (Self-Correction & Retry)
程序抛出 `ValidationError`（Pydantic）或 `JSONDecodeError` 时，应捕获异常并进入预定的重试或失败处理流程。
*   **操作**：捕获异常，并把异常信息反馈给大模型。
*   **话术举例**：“你刚才输出的数据导致了这样的报错：`Expecting value: line 1 column 1`。发生错误的内容是 `[之前的错乱输出]`。请分析并修复它，严格返回正确的结构。”
*   重试次数与收益应通过日志测量，并设置最大次数和失败路径。截断先检查 finish_reason/输出预算；关键字段不可仅靠启发式修复后直接执行。

### 3. 可选的理由摘要字段

可审计的简短理由、证据引用或校验说明，可以在业务需要时加入 Schema；并不要求模型公开完整内部推理，也不是可靠输出的必要条件。内置推理模型通常无需额外要求“逐步思考”。[推理模型提示建议](https://developers.openai.com/api/docs/guides/reasoning-best-practices)

如业务需要可审阅解释，可在 Schema 中增加简短的 `rationale_summary`，但不应强制所有输出暴露完整思维链，也不保证把它放第一位就能提高准确率。结构化输出约束字段、类型和格式，不能保证事实、权限或业务语义正确；仍需独立校验。

```json
{
  "rationale_summary": "简要列出依据与来源",
  "final_answer": "..."
}
```

### 4. 退化与降级策略 (Fallback)
*   **如果重试了 3 次还是失败怎么办？**
*   根据业务规则选择默认值（Default Values）、人工审核或预先定义的正则抽取方案。默认值和规则匹配结果同样需要校验；无法可靠处理时，应明确返回失败。

---

## 总结

结构化输出应结合提供方原生 Schema 或解码约束，控制 Schema 复杂度，并区分格式、结构与业务正确性。理由摘要字段按业务需要设置，不要求公开完整内部思维链；拒绝、截断、解析失败和业务校验失败应分别处理。接口配置应以相应提供方和版本为准，详见 [[03_Agent系统/03_Function-Calling与消息协议]]。
