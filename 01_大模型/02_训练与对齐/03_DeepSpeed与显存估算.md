# DeepSpeed 与模型微调显存估算技术解析

在大型语言模型（LLM）的训练和微调中，显存（VRAM）往往是限制模型规模、上下文长度和批量大小的关键因素。DeepSpeed 提供的 **ZeRO（Zero Redundancy Optimizer，零冗余优化器）**通过切分模型状态，减少数据并行训练中的重复存储，从而降低每张显卡的显存需求。

本文先拆解训练显存的组成，再介绍 ZeRO 的三个阶段，最后比较全参数微调、LoRA 和 QLoRA 的显存开销。估算的重点是明确：**存储哪些状态、采用什么精度、如何分片，以及状态驻留在哪里。**

> **统一估算口径**：本文以参数量恰好为 $\Phi=7\times10^9$ 的稠密模型为例，使用十进制单位：$1\text{ GB}=10^9$ 字节，$1\text{ MB}=10^6$ 字节。监控工具可能使用 GiB，$1\text{ GiB}=2^{30}$ 字节，因此 14 GB 约等于 13.0 GiB。模型名称中的“7B”通常是近似值，实际估算应使用真实参数量。

## 1. 大模型训练显存占用拆解

训练显存主要由两部分构成：**模型状态**，以及**激活、通信缓冲和临时工作空间等运行时开销**。只计算模型权重，通常会明显低估训练所需显存。

### 1.1 模型状态：参数、梯度与优化器状态

为了便于推导，先采用一种经典的混合精度 Adam/AdamW 配置：用于计算的权重和梯度以 FP16/BF16 存储，另保留 FP32 主权重及两份 FP32 优化器状态。

| 组成 | 存储精度 | 每参数占用 | 总占用 | 作用 |
| ---- | ---- | ---- | ---- | ---- |
| 模型参数 | FP16/BF16 | 2 字节 | $2\Phi$ 字节 | 参与前向与反向计算 |
| 梯度 | FP16/BF16 | 2 字节 | $2\Phi$ 字节 | 保存反向传播得到的参数梯度 |
| 主权重（Master Weights） | FP32 | 4 字节 | $4\Phi$ 字节 | 用较高精度累积参数更新 |
| Adam 一阶矩估计 | FP32 | 4 字节 | $4\Phi$ 字节 | 跟踪梯度的一阶矩，即动量 |
| Adam 二阶矩估计 | FP32 | 4 字节 | $4\Phi$ 字节 | 跟踪梯度平方的滑动平均 |

FP32 主权重有助于保留低精度权重难以表示的微小更新。下文在介绍 ZeRO 时，将主权重与 Adam 的两份矩估计合并计入“优化器状态”，共占 $12\Phi$ 字节。

该配置下的模型状态合计为：

$$
M_{\text{states}}=2\Phi+2\Phi+12\Phi=16\Phi\ \text{字节}
$$

对于 7B 模型，模型状态约为 $16\times7=112$ GB，尚未计入激活等运行时开销，因此一张 80 GB 显卡无法容纳这一配置的完整训练状态。

**16 字节/参数是特定配置下的估算值。** 实际实现可能采用 FP32 梯度累积、不单独保存 FP32 主权重，或使用低精度优化器状态，不能将上述系数直接套用于所有 BF16 训练。DeepSpeed 的实际显存估算器也会根据实现计入不同的状态与缓冲开销，详见[官方显存估算文档](https://deepspeed.readthedocs.io/en/latest/memory.html)。

### 1.2 激活与其他运行时开销

**激活值（Activations）**是前向传播产生、反向传播求导时需要使用的中间结果。其大小与单卡微批量大小（micro-batch size）、序列长度、层数、隐藏维度及算子实现有关。

- **微批量越大、序列越长，激活通常越多**。常规注意力若显式保存注意力矩阵，还会出现随序列长度平方增长的开销。
- **梯度检查点（Gradient Checkpointing，也称激活重计算）**只保存部分中间结果，在反向传播时重新计算其余部分，以额外计算换取显存节省。
- **FlashAttention**通过改进注意力计算与数据读写，避免完整保存大尺寸注意力矩阵，但不会消除模型其他部分的激活。详见[FlashAttention 原始论文](https://arxiv.org/abs/2205.14135)。

此外，还需考虑通信缓冲区、算子工作空间、CUDA 上下文，以及内存分配器的缓存与碎片。可将峰值显存近似拆为：

$$
M_{\text{peak}}\approx M_{\text{states}}+M_{\text{activations}}+M_{\text{temporary}}+M_{\text{runtime}}
$$

各项应按同一时刻的实际驻留情况计算，不同阶段的独立峰值未必同时发生。理论拆账用于判断量级，最终容量仍需通过完整训练步骤验证。

## 2. DeepSpeed ZeRO 的三个阶段

传统**数据并行（Data Parallelism，DP）**在每张显卡上保存完整模型状态，各卡处理不同数据，再同步梯度。ZeRO 的核心思想是将这些重复状态分片，由多张卡共同保存。[ZeRO 官方教程](https://www.deepspeed.ai/tutorials/zero/)将这一过程分为三个递进阶段。

以下令 $N$ 为 **ZeRO 数据并行组内的 GPU 数量**。若同时使用张量并行或流水线并行，$N$ 不一定等于集群总卡数。所有公式沿用前文的 16 字节/参数配置，暂不计入 offload 和运行时额外开销。

### 2.1 ZeRO-1：切分优化器状态

将 FP32 主权重和 Adam 的两份矩估计切分成 $N$ 份，每张卡只维护并更新自己负责的部分；低精度参数和梯度仍保留完整副本。

$$
M_{\text{ZeRO-1}}=2\Phi+2\Phi+\frac{12\Phi}{N}
=4\Phi+\frac{12\Phi}{N}
$$

它优先消除了占用最大的优化器状态冗余。不过，即使增加卡数，每卡完整参数与梯度的 $4\Phi$ 开销仍然存在。

### 2.2 ZeRO-2：进一步切分梯度

在 ZeRO-1 的基础上，对用于更新参数的梯度也进行分片，每张卡只保留自己负责的梯度分片；低精度模型参数仍在各卡完整保存。

$$
M_{\text{ZeRO-2}}=2\Phi+\frac{2\Phi+12\Phi}{N}
=2\Phi+\frac{14\Phi}{N}
$$

梯度通常通过 Reduce-Scatter 等操作完成归约与分发。其显存节省随数据并行卡数增加，但完整权重的 $2\Phi$ 开销仍是下限。通信量与性能还取决于通信组织、分桶和重叠配置，不宜简单断言与普通 DP 完全相同。

### 2.3 ZeRO-3：进一步切分模型参数

在 ZeRO-2 的基础上，再将低精度模型参数分片。执行某个模块的前向或反向计算时，通过 All-Gather 等通信操作收集所需参数，之后按策略释放或保留。

$$
M_{\text{ZeRO-3}}\approx\frac{2\Phi+2\Phi+12\Phi}{N}
=\frac{16\Phi}{N}
$$

这是**理想分片后的常驻模型状态**。实际峰值还包括模块参数聚合、预取缓冲和部分持久保留的参数，因此不会严格等于 $16\Phi/N$。ZeRO-3 进一步降低了每卡状态占用，也增加了参数收集所需的通信。[ZeRO 论文](https://arxiv.org/abs/1910.02054)给出了这些阶段的设计与分析。

以 7B 模型、8 卡为例，可以得到以下理论对比：

| 方式 | 优化器状态分片 | 梯度分片 | 参数分片 | 每卡模型状态 |
| ---- | ---- | ---- | ---- | ---- |
| 普通 DP | 否 | 否 | 否 | 112 GB |
| ZeRO-1 | 是 | 否 | 否 | 38.5 GB |
| ZeRO-2 | 是 | 是 | 否 | 26.25 GB |
| ZeRO-3 | 是 | 是 | 是 | 14 GB |

表中均未计入激活和临时缓冲。ZeRO 阶段越高，分片范围越大，但训练速度不一定越快；应结合显存容量、互联带宽和实际吞吐选择。

### 2.4 Offload：将部分状态迁移到 CPU 或 NVMe

**分片解决“由哪张卡保存”，offload 解决“保存在哪类设备上”。** ZeRO-Offload 可将优化器状态、梯度相关存储与优化器计算迁移到 CPU；ZeRO-3 的 ZeRO-Infinity 还支持更广泛的 CPU/NVMe 状态卸载。NVMe 用于存储和搬运状态，本身不执行优化器计算。[ZeRO-Offload 官方教程](https://www.deepspeed.ai/tutorials/zero-offload/)

Offload 能降低 GPU 常驻显存需求，但会增加系统内存需求、数据传输和 CPU 计算成本。实际效果取决于卸载对象、传输带宽及计算通信重叠程度，不能只根据 GPU 上剩余的权重大小判断能否训练。

## 3. 不同微调方式的显存估算与技术细节

ZeRO、LoRA 和量化作用于不同环节：**ZeRO 切分模型状态，LoRA 减少可训练参数，量化降低权重存储位宽。** 它们可以在受支持的实现中组合使用，但不能直接把各自的节省比例相乘。

### 3.1 全参数微调（Full Parameter Fine-Tuning）

全参数微调会更新模型的全部 $\Phi$ 个参数。因此，在精度与优化器配置相同时，其模型状态开销与同规模预训练相近。

- **单卡、不分片也不卸载**：按前述配置，7B 模型状态约为 112 GB，还需要额外显存容纳激活等开销。
- **单卡、使用 CPU offload**：若仅把 $12\Phi$ 的优化器相关状态迁出 GPU，参数与梯度仍驻留 GPU，则该简化拆账得到 $4\Phi=28$ GB；但这并非所有 ZeRO-Offload 配置的固定值。经典 ZeRO-2 CPU offload 还会处理梯度卸载，官方估算器中的 GPU 常驻模型状态项可按 $2\Phi=14$ GB 估算，仍需另加激活与临时缓冲。
- **8 卡、使用 ZeRO-3 且不卸载**：理想常驻模型状态为 $112/8=14$ GB/卡。24 GB 或 32 GB 显卡是否足够，还取决于序列长度、微批量大小和参数聚合峰值。

上述 offload 口径可与[DeepSpeed 显存估算文档](https://deepspeed.readthedocs.io/en/latest/memory.html)对照；CPU 侧容量也应单独核算。

### 3.2 LoRA：减少需要训练的参数

**LoRA（Low-Rank Adaptation，低秩适配）**冻结基座模型权重，在选定的线性层引入可训练的低秩增量。对于 $W_0\in\mathbb{R}^{d_{\text{out}}\times d_{\text{in}}}$，可写为：

$$
W=W_0+\frac{\alpha}{r}BA
$$

其中 $A\in\mathbb{R}^{r\times d_{\text{in}}}$，$B\in\mathbb{R}^{d_{\text{out}}\times r}$，$r$ 为秩，$\alpha$ 为缩放超参数。单个目标矩阵新增参数量为 $r(d_{\text{in}}+d_{\text{out}})$，通常远小于原矩阵参数量。目标层可以包括注意力投影层，也可以包括 MLP 等线性层。[LoRA 原始论文](https://arxiv.org/abs/2106.09685)

令全部 LoRA 参数量为 $\theta$。若冻结基座以 FP16/BF16 常驻单卡，LoRA 部分沿用前述混合精度状态配置，则：

$$
M_{\text{LoRA, states}}\approx2\Phi+16\theta
$$

以 $\theta=0.002\Phi$ 为例，7B 模型新增约 1400 万参数：

1. **冻结基座权重**：约 14 GB，无需为其保存参数梯度、FP32 主权重和 Adam 状态。
2. **LoRA 可训练状态**：约 $16\theta=224$ MB。
3. **模型状态合计**：约 **14.224 GB**。实际适配器精度或优化器不同，这一数值也会变化。

**冻结基座并不意味着无需反向传播。** 为了更新分布在模型各层的适配器，仍需沿计算图传播梯度，并保存或重计算必要的激活。因此，LoRA 的训练峰值可能明显高于 14 GB。

ZeRO-1/2 主要分片较小的可训练状态，对冻结基座权重的节省有限；ZeRO-3 则可在受支持的配置中进一步分片基座参数。单张 24 GB 显卡能否完成某个 7B LoRA 任务，仍需结合序列长度、微批量和重计算配置验证。

### 3.3 QLoRA：进一步压缩冻结基座

**QLoRA（Quantized LoRA）**在低比特量化的冻结基座上训练 LoRA 适配器。其经典方案包括 NF4、双重量化和分页优化器。[QLoRA 原始论文](https://arxiv.org/abs/2305.14314)

1. **4-bit 基座权重**：若理想地将全部基座参数按 4 bit 保存，原始权重载荷为 $0.5\Phi$ 字节，7B 对应 3.5 GB。但实际模型还包含量化尺度等元数据，部分模块也可能保留较高精度。
2. **高精度适配器**：LoRA 参数、梯度与优化器状态仍需另行存储，不能一起按 4 bit 计算。
3. **双重量化（Double Quantization）**：对量化常数再次量化，进一步压缩元数据。原论文配置下平均约节省 0.37 bit/参数，节省的是原本的元数据开销，并非将 4-bit 权重本体变成 3.63 bit。
4. **分页优化器（Paged Optimizer）**：利用统一内存分页管理优化器状态，缓解显存峰值；它不会自动解决所有激活或算子工作空间超限问题。

更完整的状态估算应写为：

$$
M_{\text{QLoRA, states}}\approx M_{\text{quantized base}}+M_{\text{adapter states}}
$$

其中，$M_{\text{quantized base}}$ 应分别统计量化权重载荷、量化元数据及未量化模块。若仍以 $\theta=0.002\Phi$ 和 $16\theta$ 的适配器状态为例，即使忽略元数据，并将全部基座理想地按 4 bit 计算，合计也约为 **3.724 GB**，因此不宜把“3.5～4 GB”当作所有 7B QLoRA 任务的固定总占用。

**存储精度与计算精度需要区分。** 基座以 4 bit 存储，不代表整个训练过程都以 4 bit 计算；计算时按算子需要反量化，并常用 BF16/FP16 完成运算，具体行为由配置和内核决定。相关参数见[Transformers 的 bitsandbytes 文档](https://huggingface.co/docs/transformers/quantization/bitsandbytes)。

QLoRA 可降低在消费级显卡上微调 7B 乃至更大模型的显存门槛，但 13B/14B 模型是否能装下，仍需计入激活、适配器、量化元数据和临时工作空间，不能仅凭 7 GB 左右的理想权重载荷判断。

### 3.4 实际估算与验证顺序

1. **确定配置**：记录真实参数量、可训练参数量、各类状态精度、ZeRO 数据并行度，以及 offload 对象。
2. **计算模型状态**：分别汇总基座权重、可训练参数、梯度和优化器状态，再按实际分片与驻留位置计算每卡占用。
3. **以目标长度试跑**：从较小微批量开始，启用所需的重计算或高效注意力，运行包含前向、反向和优化器更新的完整步骤；部分优化器状态可能到首次更新时才分配。
4. **观察峰值并调整**：同时关注张量实际分配显存、分配器保留显存与整卡占用，逐步调整微批量或序列长度，并验证保存检查点时的额外峰值。

梯度累积可以在较小微批量下保持较大的有效全局批量。在普通数据并行中，$B_{\text{global}}=B_{\text{micro}}\times N\times K$，其中 $K$ 为累积步数；降低微批量通常有助于减少激活，但不会按相同比例减少模型状态。

对于 MoE，权重存储应按实际驻留的专家参数统计，不能用“每 token 激活参数量”替代总参数量。关联笔记：[[01_大模型/01_模型结构/03_MoE混合专家模型]]、[[01_大模型/02_训练与对齐/01_SFT与参数高效微调]]。

## 总结

下表比较单卡、不分片、不卸载时的模型状态量级，均不包含激活和其他运行时开销。LoRA 与 QLoRA 均沿用 $\theta=0.002\Phi$、适配器状态占用 $16\theta$ 字节的示例配置。

| 微调策略 | 可训练参数 | 7B 模型状态估算 | 常见配套工具 | 适用场景 |
| ---- | ---- | ---- | ---- | ---- |
| 全参数微调 | 全部基座参数 | 约 112 GB，采用本文 16 字节/参数配置 | DeepSpeed ZeRO、CPU/NVMe offload | 需要更新全部权重，且计算资源充足 |
| LoRA | 低秩适配器参数 | 约 14.224 GB，假设 $\theta=0.002\Phi$ | PEFT 等适配器工具，按需结合 ZeRO | 领域适配、指令微调，以及多任务适配器管理 |
| QLoRA | 低秩适配器参数 | 理想化计算约 3.724 GB 起，另加量化元数据与未量化模块差额 | bitsandbytes 等量化工具与 PEFT | 显存受限的微调实验与任务适配 |

判断显存是否足够时，应先明确模型状态的估算前提，再补上目标长度和微批量下的运行时峰值。梯度检查点与 FlashAttention 等技术能进一步降低部分开销，但最终仍应以实际训练配置的测量结果为准。

## 4B 模型的训练与推理显存示例

**4B 表示约 40 亿参数，不代表模型固定占用 4 GB 显存。** 以下按恰好 $4\times10^9$ 参数估算；模型参数包含输入 Embedding 等模块，不能重复加算。Embedding 的参数表与输出形状见 [[01_大模型/01_模型结构/01_Transformer与生成机制#Embedding 层：从 Token ID 到向量]]。

### 模型参数占用

以 Qwen3-4B（实际约 4B 参数）为例：

| 精度 | 参数占用 |
|------|---------|
| BF16 / FP16 | 4B × 2 bytes = **8 GB** |
| INT8 量化 | 4B × 1 byte = **4 GB** |
| INT4 量化 | 4B × 0.5 byte = **2 GB** |

### 推理显存快速估算

按单条请求、约 2K～4K 上下文、权重全部驻留 GPU 估算，以下运行显存仅作容量规划参考，并非特定模型的实测结果：

| 精度 | 理想权重载荷 | 运行显存粗估 |
| ---- | ---- | ---- |
| 4-bit 量化 | 2 GB | 4～6 GB |
| 8-bit 量化 | 4 GB | 6～8 GB |
| FP16 / BF16 | 8 GB | 10～14 GB |
| FP32 | 16 GB | 18～24 GB |

运行时还需加上 KV Cache、计算缓冲与框架开销；量化模型还包含尺度等元数据，部分模块可能保留高精度。上下文长度、并发、注意力结构和推理框架都会改变结果，KV Cache 的拆账见下文 [[#KV Cache 占多大]]。

### 训练显存快速估算

LoRA 与 QLoRA 按微批量为 1、约 1K～2K 序列，并开启梯度检查点等节省显存措施估算；全参数训练按常规混合精度 AdamW、无分片且无卸载估算：

| 方式 | 显存粗估 | 主要区别 |
| ---- | ---- | ---- |
| QLoRA，4-bit 冻结基座 | 6～12 GB | 压缩基座权重，只更新适配器 |
| LoRA，FP16/BF16 冻结基座 | 12～24 GB | 基座仍按半精度驻留，只更新适配器 |
| 全参数训练 | 常需预留约 80～100 GB 或更多 | 为全部参数维护梯度和优化器状态 |

这些范围是经验性容量预算，不是最低需求或可运行保证。常规全参数训练的模型状态按每参数 16～18 字节估算，4B 对应约 **64～72 GB**，还需加激活与临时缓冲。16 与 18 的差异可来自梯度保存精度等实现选择，见 [Hugging Face 训练显存说明](https://huggingface.co/docs/transformers/v4.38.0/model_memory_anatomy)。通过重计算、低精度优化器、分片或卸载，实际 GPU 需求可以降低；同配置下，从头预训练与全量微调的模型状态开销相近，计算总量则取决于训练 token 数等因素。

### 全参数微调的总显存

```
参数（BF16）：    8 GB
梯度：            8 GB   （与参数同精度）
Adam 相关状态：  48 GB   （FP32 主权重 + 两个 FP32 动量项，各 16 GB）
激活值（batch=4, seq=2048）：约 4~8 GB（示例估计，需实测）

静态参数/梯度/状态：64 GB；加上上述激活约 68~72 GB，尚未含额外缓冲
```

### LoRA 微调的总显存

```
冻结参数（BF16，不存梯度）：8 GB
LoRA 适配层参数（rank=16，约 0.1% 参数量）：~0.01 GB
LoRA 梯度 + Adam：~0.03 GB
激活值：4~8 GB

LoRA 微调合计：约 12~16 GB → 单卡 A30/A100 可以跑
```

### MoE 与混合注意力的显存边界

标准注意力层保存历史 KV，Gated DeltaNet 等循环层维护不同状态。按全注意力模型的公式乘全部层数会混淆两类开销；MoE 也要区分总参数驻留与每 token 激活参数。新架构更需要按层类型、精度和分片拆账。[Qwen3.5 模型卡](https://huggingface.co/Qwen/Qwen3.5-397B-A17B)

见 [[01_大模型/01_模型结构/03_MoE混合专家模型]]、[[01_大模型/02_训练与对齐/03_DeepSpeed与显存估算]]。

### KV Cache 占多大

KV Cache 的计算公式（推理时）：

```
KV Cache = 2 × num_layers × num_kv_heads × head_dim × seq_len × batch_size × bytes_per_element
```

以 Qwen3-4B 为例（约 36 层，GQA num_kv_heads=8，head_dim=128）：

| 场景 | KV Cache 大小 |
|------|--------------|
| batch=1, seq=2048, FP16 | 2 × 36 × 8 × 128 × 2048 × 1 × 2 ≈ **0.29 GB** |
| batch=8, seq=2048, FP16 | 约 **2.3 GB** |
| batch=8, seq=8192, FP16 | 约 **9.2 GB** |

**结论**：常规 teacher-forcing SFT 通常设 `use_cache=False`，反向传播所需激活与生成用 KV Cache 是不同概念。推理 KV Cache 随序列长度和 batch size 线性增长；包含在线生成的 RL 则需另算 rollout 缓存。上面的 GB 使用十进制单位，训练显存估计依赖是否保留 FP32 主权重等实现条件。
