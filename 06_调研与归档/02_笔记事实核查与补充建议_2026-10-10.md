## 一、模型基础与训练

### 1. MoE 参数量推导存在直接矛盾

位置：[MoE 笔记第 50 行](../01_大模型/01_模型结构/03_MoE混合专家模型.md)。

原文假设每个专家大小为标准 FFN 的 `1/N`，随后得出总参数为标准模型的 `N` 倍，二者不能同时成立。

设标准 FFN 参数量为 P、每个专家参数量为 E，则 MoE 专家总参数为 NE，每个 token 激活的专家参数为 kE。若 E=P/N，总专家参数为 P，激活参数为 kP/N；若 E=P，总专家参数才为 NP。完整模型还须加上共享 Attention、Embedding 等参数，不能直接用专家数推导整模倍率。

同文件第 78 行将 DeepSeek-MoE 归为 Top-2 也需要修正：DeepSeekMoE 16B 每层有 64 个路由专家，激活其中 6 个，另有 2 个共享专家。[DeepSeekMoE 原论文第 5.1 节](https://arxiv.org/html/2401.06066v1)。

### 2. KTO 损失公式写错

位置：[对齐算法笔记第 197 行](../01_大模型/02_训练与对齐/02_偏好对齐算法_PPO_DPO_GRPO.md)。

原公式只有统一方向的 `log sigmoid` 项，没有体现正负样本相反的优化方向，不能作为标准 KTO 公式使用。

可按原论文定义：令 r=log(πθ/πref)，z 为 KL 基准，则好样本效用为 λD·σ(β(r−z))，坏样本效用为 λU·σ(β(z−r))，损失为 E[λy−v(x,y)]。实现还要说明 KL 估计及停止对 z 反向传播。[KTO 原论文第 4.1 节](https://arxiv.org/html/2402.01306v4#S4.SS1)。

### 3. GRPO 的提出时间错误

位置：[对齐算法笔记第 100 行](../01_大模型/02_训练与对齐/02_偏好对齐算法_PPO_DPO_GRPO.md)。

“2024 年底提出”应改为“在 2024 年 2 月的 DeepSeekMath 论文中提出，随后用于 DeepSeek-R1”。论文首次提交日期是 2024-02-05。[DeepSeekMath 原论文](https://arxiv.org/abs/2402.03300)。

### 4. 可验证奖励不能消除 Reward Hacking

位置：[对齐算法笔记第 148 行](../01_大模型/02_训练与对齐/02_偏好对齐算法_PPO_DPO_GRPO.md)、[问题列表第 625 行](../05_面试与算法/00_面试导航.md)。

“完全避免”“风险为零”不成立。模型仍可能利用验证器漏洞、测试覆盖不足或环境缺陷取得高分。建议改为“减少对学习型奖励模型的依赖，但仍需防范验证器被利用”。已有针对代码 RLVR 的原始研究直接展示了此问题。[CATCH 研究论文](https://arxiv.org/abs/2609.39533)。

另外，[问题列表第 621 行](../05_面试与算法/00_面试导航.md)把正式 R1 流程简化为“冷启动 SFT + 推理 RL”两阶段，遗漏了拒绝采样与第二轮 SFT、面向全场景的后续 RL；这是前半段流程，不能作为完整训练流程。[DeepSeek-R1 原论文](https://arxiv.org/html/2501.12948v1)。

### 5. 4B 模型的 Adam 状态少算了 16 GB

位置：[面试答案第 1004 行](../05_面试与算法/00_面试导航.md)。

按文内“FP32 主权重 + 两个 FP32 动量项”的假设，每项都是 4B×4 bytes=16 GB，三项合计应为 **48 GB**，不是 32 GB。参数 8 GB + 梯度 8 GB + 三项状态 48 GB = **64 GB**；沿用文中 4～8 GB 激活估计，总量应为 **68～72 GB**。

若具体实现没有独立 FP32 主权重，必须明确写出这个不同假设。16 bytes/参数也只是某种状态配置的估算；实际峰值还取决于梯度精度、最大层聚合、通信缓冲等。[DeepSpeed 显存估算文档](https://deepspeed.readthedocs.io/en/latest/memory.html)。

### 6. 常规 SFT 不应写成“训练时 KV Cache 占比很小”

位置：[面试答案第 1037 行](../05_面试与算法/00_面试导航.md)。

通常的 teacher-forcing SFT 会关闭生成用的 KV Cache，尤其在启用梯度检查点时；需要为反向传播保存的激活与推理 KV Cache 是不同概念。建议将“训练显存”和“自回归推理显存”分开说明。包含在线生成的 RL 流水线则另算 rollout 阶段缓存。[Transformers 训练参数源码](https://github.com/huggingface/transformers/blob/main/src/transformers/training_args.py)。

该段 Qwen3-4B 的 36 层、8 个 KV heads、head_dim=128 与官方配置一致，不需要修改。[模型配置](https://huggingface.co/Qwen/Qwen3-4B/blob/main/config.json)。

### 7. Qwen3 没有笔记所说的独立 Embedding 后 RMSNorm

位置：[面试答案第 1181 行](../05_面试与算法/00_面试导航.md)。

标准 Qwen3 实现将 token embedding 直接作为 decoder 隐状态输入，没有在两者之间另加独立 RMSNorm。第一个 block 的 input_layernorm 属于该 block 的 Pre-Norm。建议补充 Attention 内的 Q/K Norm、block 内两处 Pre-RMSNorm，以及最后的输出 RMSNorm；不要把 block 的第一处 norm 描述成额外 embedding norm。[Transformers Qwen3 源码](https://github.com/huggingface/transformers/blob/main/src/transformers/models/qwen3/modeling_qwen3.py)。本地安装版本也呈现相同结构。

### 8. KV Cache 的复杂度需要区分单步与完整生成

位置：[问题列表第 454 行](../05_面试与算法/00_面试导航.md)。

“推理复杂度从 O(n²) 降为 O(n)”缺少统计范围。在标准全注意力下，缓存后的一个解码步仍需关注已有 t 个位置，其 Attention 成本随 t 线性增长；生成 n 个 token 的这部分累计成本仍为 O(n²)。若每一步都重算整个前缀，累计 Attention 成本可达到 O(n³)。以上忽略固定模型维度，并将 prefill 单独计入。

同文件第 440 行也应区分位置机制：RoPE 作用于 Attention 的 Q/K，ALiBi 加在注意力分数上，都不是通用的“Embedding 查表后相加”。可对照 Qwen3 的 Q/K 旋转实现。[Qwen3 源码](https://github.com/huggingface/transformers/blob/main/src/transformers/models/qwen3/modeling_qwen3.py)。

### 9. YaRN 注意力温度公式少乘了一个缩放因子

位置：[杂项技术第 323 行](../01_大模型/00_大模型导航.md)。

按原论文记号，logits 应为 QKᵀ/(t√d)，而不是 QKᵀ·√(1/t)/√d。√(1/t) 是分别施加在 Q 与 K 上的因子，二者点积后得到 1/t。原论文推荐的拟合关系为 √(1/t)=0.1 ln(s)+1。[YaRN 原论文第 3.4 节](https://arxiv.org/html/2309.00071v2)。

### 10. vLLM 技术名称及性能结论需要修正

位置：[vLLM 笔记第 32 行](../01_大模型/03_推理与接口/03_vLLM与推理优化.md)、第 46～47 行。

正式名称是 **PagedAttention**，不是 PageAttention，文件名、标题和标签也可统一修正。分页并没有完全消除内部碎片：最后一个未填满的 block 仍有浪费。接近零的是 KV Cache 管理中的浪费，不能解释为整张 GPU 显存利用率接近 100%。

2～4 倍吞吐提升是原论文指定模型、负载和 FasterTransformer/Orca 基线下的结果，不是所有部署的固定收益。[PagedAttention 原论文](https://arxiv.org/abs/2309.06180)。

### 11. LIMA 的结论被扩张成了普遍定律

位置：[SFT 笔记第 76 行](../01_大模型/02_训练与对齐/01_SFT与参数高效微调.md)、第 79～81 行。

1000 条是精心筛选构建的 prompt/response，不能统称为“1000 条人工手写”。LIMA 支持经过充分预训练的模型上少量高质量数据能够有效对齐的假说，不能证明“SFT 不能学习新知识”或“知识只由预训练决定”。建议保留结论的实验范围，并将知识注入能力作为需要独立评测的问题。[LIMA 原论文](https://arxiv.org/abs/2305.11206)。

## 二、RAG 检索、微调与评测

### 12. Cross-Encoder 重排不等于文档去重

位置：[RAG 概要第 699 行](../02_RAG系统/00_项目总览.md)。

普通 Cross-Encoder 独立评估每个 query-document pair，不比较候选文档之间的冗余。两个重复且相关的文档可能同时得高分，阈值截断也可能把它们同时保留。因此“Reranker 完全覆盖 MMR 的价值”没有依据。

可以决定不用 MMR，但应基于重复率、证据覆盖和延迟的实测。可选方案包括 chunk/parent ID 去重、文本近重复去重，或重排后的 MMR。[CrossEncoder 官方接口](https://sbert.net/docs/package_reference/cross_encoder/model.html)。

### 13. 梯度累积、GradCache、跨卡负样本是不同机制

位置：[Embedding 微调第 289 行](../02_RAG系统/07_检索模型微调总览与协同部署.md)、第 291～298 行、第 357～363 行；[面试答案第 109 行](../05_面试与算法/00_面试导航.md)。

普通梯度累积只累积各微批独立 loss 的梯度，不会自动构造跨微批的对比分母。DDP 默认同步梯度，也不会自动把其他卡的正文档变成当前卡的负样本。

若每卡缓存 512 个样本，双卡还须在 loss 中执行 embeddings all-gather，才可能构成 1024 个正文档的联合候选池。“batch=64、分块=16、双卡”本身推不出 1024。GradCache 的主要作用是避免保存整个大批次的激活图，“代价是显存翻倍”也不是一般规律。[Sentence Transformers 损失文档](https://www.sbert.net/docs/package_reference/sentence_transformer/losses.html)。

### 14. GTE 多维输出的机制与调用接口混淆

位置：[Embedding 微调第 387 行](../02_RAG系统/07_检索模型微调总览与协同部署.md)、[RAG 概要第 1004 行](../02_RAG系统/00_项目总览.md)。

gte-multilingual-base 支持弹性维度，因此使用 384/768 维本身是合理的。但标准 SentenceTransformer.encode 的维度参数是 `truncate_dim`，不是示例中的 `output_dim`。除非使用自定义封装，示例应修订。

截断嵌套向量也不等于“两个投影头”。若领域微调后继续用 384 维，应评测该维度或采用多维训练目标，不能默认低维质量必然保留。截断减少向量存储和检索成本，不代表 Transformer 编码计算量减半。[GTE 官方模型卡](https://huggingface.co/Alibaba-NLP/gte-multilingual-base)、[SentenceTransformer 接口](https://www.sbert.net/docs/package_reference/sentence_transformer/model.html)。

### 15. Listwise Loss 并不要求全参数训练

位置：[Reranker 微调第 636 行](../02_RAG系统/07_检索模型微调总览与协同部署.md)、第 638～640 行。

“LoRA 仅在高层 K/Q 插入”“Listwise 梯度要求更新全部层”都不是方法本身的限制。LoRA 可插入多个层和不同线性模块；冻结权重不等于阻止反向传播计算到达可训练 adapter。Listwise 是损失组织方式，完全可以与 LoRA 结合。

建议将全量微调选型依据写为“在当前模型与数据上的对照实验效果更好、资源可承受”，而不是不可兼容的理论要求。[LoRA 原论文](https://arxiv.org/abs/2106.09685)。

### 16. DeepEval 示例缺少必需参考答案

位置：[RAG 评测第 269 行](../02_RAG系统/11_RAG评测系统.md)。

示例创建的 LLMTestCase 未提供 `expected_output`，却执行 ContextualRecallMetric；该指标需要 input、retrieval_context 和 expected_output。本地已安装版本的 required_params 也明确列出了这些字段。

另外，actual_output 来自本次执行，而 retrieval_context 来自预存 sample，二者可能不对应。应从同一次 RAG 执行收集回答和最终实际上下文，再送入评测。[DeepEval Contextual Recall 文档](https://deepeval.com/docs/metrics-contextual-recall)。

### 17. RAGAS Faithfulness 调用次数不能按“每个声明一次”推算

位置：[RAG 评测第 305 行](../02_RAG系统/11_RAG评测系统.md)、第 370～381 行。

本地安装的 Faithfulness 实现先提取声明，再将声明列表交给 NLI prompt；并没有对每个声明单独发起一次 LLM 调用。具体次数受版本、重试和实现影响，不应固定成“6 个声明=6 次 Judge 请求”。据此计算的评测时长需要重算，并以 trace 为准。

可直接对照本地 [声明判断调用](../.venv/Lib/site-packages/ragas/metrics/_faithfulness.py)及[主评测流程](../.venv/Lib/site-packages/ragas/metrics/_faithfulness.py)。指标含义参见 [RAGAS 官方说明](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/)。

## 三、Agent 与工程基础设施

### 18. 降级后 HITL 阈值调整方向写反

位置：[Agent 全景报告第 496 行](../03_Agent系统/00_项目总览.md)。

既然规则是 confidence < threshold 时转人工，要触发更多 HITL，就应提高阈值，而不是降低阈值。这个结论可以直接从笔记自身的路由规则推出。建议改为“模型降级后提高人工审核阈值，并收窄可调用工具”。

### 19. recursion_limit 触发异常，不会自动挂起转人工

位置：[Agent 概要第 259 行](../03_Agent系统/00_项目总览.md)、[全景报告第 253 行](../03_Agent系统/00_项目总览.md)。

LangGraph 的限制按 super-step 计数，不等于工具调用次数，也不严格等于节点数；并行节点可处于同一 super-step。达到限制会产生 GraphRecursionError，业务若要保存状态、设置 SUSPENDED、告警或交给 HITL，需要自行处理。[Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)、[递归限制错误文档](https://docs.langchain.com/oss/python/langgraph/errors/GRAPH_RECURSION_LIMIT)。

### 20. HITL 恢复接口与资源释放描述不准确

位置：[Agent 技术报告第 382 行](../03_Agent系统/00_项目总览.md)、[全景报告第 672 行](../03_Agent系统/00_项目总览.md)。

标准编译图没有这里描述的通用 `.resume()` 方法。动态 interrupt 通常通过 invoke/stream 传入 Command(resume=...) 恢复；静态 interrupt_before 的恢复方式不同，需要分开讲。

暂停不等于进程终止，更不会自动卸载独立 vLLM 服务里的模型显存。建议写“暂停任务执行，不长期占用业务执行槽位；模型服务资源由服务端管理”。动态 interrupt 恢复还会重跑所在节点，其前置副作用须可幂等。[LangGraph Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)。

### 21. add_messages 并非只追加、绝不覆盖

位置：[LangGraph 笔记第 83 行](../04_工程与框架/12_LangGraph.md)。

没有相同 ID 时通常追加；若新消息 ID 与已有消息相同，会更新已有消息。建议改为“按消息 ID 合并，通常追加，也支持更新既有消息”。[add_messages 官方说明](https://reference.langchain.com/python/langgraph/graph/message/add_messages)。

### 22. Pydantic 的 extra='forbid' 不是类型严格模式

位置：[Pydantic 笔记第 65 行](../04_工程与框架/02_Pydantic.md)。

extra='forbid' 禁止额外字段；限制类型转换应使用 strict=True 等严格校验配置。Pydantic 本身抛 ValidationError，HTTP 422 是 FastAPI 请求校验的响应处理。第 52 行的 update_forward_refs 是旧接口，V2 应使用 model_rebuild。

另需限定 frozen=True：它限制字段重新赋值，不会自动把内部 list/dict 变成深层不可变结构。[严格模式文档](https://docs.pydantic.dev/latest/concepts/strict_mode/)。

### 23. Celery 默认 ACK 时机写反

位置：[Celery 笔记第 79 行](../04_工程与框架/06_Celery.md)。

默认是在任务执行前确认，而不是执行完成后。延后确认要显式启用 acks_late；子进程被终止时，即使启用它，也可能确认消息。若需 worker lost 后重投，还要评估 task_reject_on_worker_lost 并保证幂等。

第 83 行“集群重启恢复断点”也应限定为消息重新执行；任务函数中途的执行进度需自行持久化。[Celery 官方任务文档](https://docs.celeryq.dev/en/stable/userguide/tasks.html)。

### 24. Kafka 的 acks='all' 不等于所有副本 fsync 落盘

位置：[Kafka 笔记第 37 行](../04_工程与框架/05_Kafka.md)、第 76 行。

acks='all' 等待的是当前 ISR 中副本的确认，不是所有配置副本，也不意味着各副本在确认前完成磁盘 fsync。副本策略、min.insync.replicas 和刷盘策略需要分别说明。[aiokafka ACK 说明](https://aiokafka.readthedocs.io/en/stable/api.html)、[Kafka 文件系统与刷盘文档](https://kafka.apache.org/38/operations/hardware-and-os/)。

该示例第 39 行还有接口错误：AIOKafkaProducer 的参数为 max_batch_size，不是 batch_size。[aiokafka 接口](https://aiokafka.readthedocs.io/en/stable/api.html)。

### 25. run_in_executor 默认使用线程池

位置：[FastAPI 笔记第 58 行](../04_工程与框架/03_FastAPI.md)。

只有显式传入 ProcessPoolExecutor 才是进程池；executor=None 使用默认线程池。阻塞网络 I/O 通常可交给线程池，纯 Python CPU 密集任务再评估进程池。[Python 官方文档](https://docs.python.org/3/library/asyncio-eventloop.html#asyncio.loop.run_in_executor)。

### 26. 笔记宣称的 T-Test / KS-Test 与示例代码不符

位置：[Agent 全景报告第 322 行](../03_Agent系统/00_项目总览.md)、[nodes.py 第 57 行](../03_Agent系统/code/nodes.py)、[第 76 行](../03_Agent系统/code/nodes.py)、[第 491 行](../03_Agent系统/code/nodes.py)。

_ks_test_uniform 只计算超出上下界的比例，不是 KS 检验。_ttest_ind 实际按单样本统计量做正态近似；调用处 sample=[pass_rate] 只有一个数，函数直接返回 p=1，未执行有效显著性检验。

这意味着示例不能支撑“已完成 T-Test/KS-Test 双重校验”的描述。应标为演示或实现真正的检验：保留样本与样本量，区分单样本、配对或独立样本；KS 应比较经验分布。没有显著差异也不能直接证明等效。[SciPy 单样本 t 检验](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.ttest_1samp.html)、[两样本 KS 检验](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.ks_2samp.html)。

### 27. Elasticsearch 的“严格字面匹配”与分词要求写得过于绝对

位置：[Elasticsearch 笔记第 62 行](../04_工程与框架/08_Elasticsearch.md)、第 83 行。

索引与搜索 analyzer 需要兼容，但可以不同，例如搜索时同义词和 autocomplete。match 查询经过分词、归一化及可能的同义词处理，不保证“字面对不上绝不召回”；当前示例还是 operator='or'。型号和版本严格匹配应设计 keyword/term 等专用字段与规则。[search_analyzer 官方文档](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/search-analyzer)、[文本分析文档](https://www.elastic.co/guide/en/elasticsearch/reference/current/analysis.html)。

第 71 行 FST 定位词条“复杂度 O(1)”也应删除：词长和 posting list 的访问不能省略成常数级全文检索。

### 28. Milvus 段落混淆线性成本、度量和异步接口

位置：[Milvus 笔记第 7 行](../04_工程与框架/09_Milvus.md)、第 45～57 行。

固定维度 d 下暴力计算 n 个向量距离是 O(nd)，随向量数线性增长，不是“指数爆炸”。单位归一化后，IP、COSINE 和平方 L2 的排序可相互对应：平方 L2=2−2·内积；不能说换了度量就必然无意义，但阈值要转换。

示例 Collection.search 是普通同步调用，注释不应称其为异步。应采用相应异步客户端，或由上层显式把阻塞调用移出事件循环。

## 五、值得补充的内容

1. **指标的证据与统计口径。** 93% 准确率、96.8% 阻断率、14 小时训练、1 秒重排等数字，应附样本量、评测集版本、模型和提示词版本、日期及实验日志。当前 [train_dpo.py 第 332 行](../03_Agent系统/code/training/train_dpo.py)直接打印“预期效果”中的固定数字，不能作为实测证据。已通过测试集的 100% 阻断，也不等于所有未来输入都能阻断；“生产要求”与“观测结果”应分开记录。

2. **Recall@K 与 Hit@K。** [RAG 评测第 129 行](../02_RAG系统/11_RAG评测系统.md)写“正确 Chunk 是否出现”，多相关答案场景下实际更像 Hit@K。若相关集合 G 含多个 chunk，Recall@K 应计算 |TopK∩G|/|G|；Hit@K 只判断交集是否非空。Faithfulness 测上下文支持程度，也不能单独证明上下文本身真实或版本正确。

3. **置信度的可解释性与校准。** 明确 confidence_score 来自模型自报、规则综合还是概率校准。0.65 不能直接解释为“65% 正确概率”。补充按区间统计的实际错误率、风险与自动处理覆盖率、校准集和阈值更新记录；增加阈值反向调整的回归检查。

4. **文档版本更新与删除。** [面试答案第 23 行](../05_面试与算法/00_面试导航.md)把 doc_id upsert 描述为“同一文件只有一个向量”，与多 chunk 索引不符。建议区分 doc_id、doc_version、chunk_id，说明旧 chunk 的清理、父子文档版本一致性，以及 ES/Milvus 更新未完成时的切换策略。

5. **权限应覆盖整条读取路径。** [RAG 概要第 435 行](../02_RAG系统/00_项目总览.md)把 Thread ID 描述为天然多租户安全隔离，结论过强。应补充服务端校验 thread 与当前用户/租户的归属关系、checkpoint 访问控制、父文档二次取回与缓存的权限校验。若启用结果缓存，key 还须包含影响结果的权限、会话和知识库版本信息。

6. **SFT 的损失掩码与训练数据隔离。** 在 SFT 笔记中补充 token 级交叉熵、assistant-only loss、工具结果是否参与 loss、chat template 与截断策略。数据按源文档、同一用例的变体和时间分组划分，避免将同一问题的改写或 HITL 派生样本跨到训练集和测试集。

7. **结构化输出的三层校验。** [结构化输出笔记第 79 行](../01_大模型/03_推理与接口/02_结构化输出与校验.md)“永远把第一个字段设为 thought”应改为可选实验策略。JSON 可解析、满足 Schema、业务值真实有效是三件不同的事；解释文本或置信度字段不保证正确。补充截断/拒绝/不完整输出的处理，并把启发式修复后的结果重新做业务校验。

8. **MCP 的协议边界。** [杂项技术第 466 行](../01_大模型/00_大模型导航.md)“API 无状态、无上下文感知”不是 API 的定义。MCP 的远程传输也应补充 Streamable HTTP，旧 HTTP+SSE 不能代表所有当前远程实现；会话状态与资源管理取决于传输和服务实现。[MCP 传输规范](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports)。

上述明确错误已修订。后续需实际数据确认的事项：Reranker 最终 checkpoint 与损失配置、Embedding 逻辑 batch 与跨卡聚合、生产缓存启用状态，以及历史指标/训练耗时的日志证据。
