# 从测试执行到异常调查：Agent 系统升级对照方案

> 本文独立比较原来的“集中执行测试”定位与建议的新定位，供集中阅读和决定改造范围。本文不修改其他设计文档，不代表新增能力已经实现，也没有查阅项目代码或运行真实测试。
>
> 对照依据为现有项目总览、工具设计、状态管理、安全恢复、评测和模型训练文档。原文档中已有异常补查与原因分析设计，因此这里比较的是两种业务重心，不把旧系统描述成完全没有分析能力的脚本平台。生产实现情况仍以 [[03_Agent系统/01_项目事实与实现状态]] 及实际记录为准。
>
> 贯穿全文的故障、实验编号、版本名、次数和结果均为讲解示例。它们不代表现场事实、实测收益或通用通信验收标准。

**建议的新定位：保留按需测试，增加持续的异常调查。工程师既可以说“帮我测这个功能”，也可以说“这里有个问题，帮我复现、缩小范围，并验证修复”。**

原来主要交付一份测试结果。新方案进一步交付可复现的步骤、经过实验支持的问题范围、原因证据，以及修复前后的对照材料。

## 1. 先用一张表看全局变化

| 比较方面 | 原定位：集中执行测试 | 新定位：按需测试与异常调查 |
| --- | --- | --- |
| 业务目标 | 少花人工完成测试并形成结果 | 同时减少异常复现、条件筛选、证据整理和修复验证中的人工 |
| 用户输入 | 测试对象、场景、参数和要求 | 既接受明确测试要求，也接受不完整的异常描述 |
| 起点 | 已知要测什么 | 可能只知道某种现象，还不知道怎样测才能重现 |
| 主流程 | 查询用例、执行、采集、判定、报告 | 理解现象、构造场景、多轮实验、简化复现、验证解释、验证修复 |
| 一轮执行后的处理 | 主要判断是否完成、是否通过 | 判断本轮结果说明什么，以及下一轮还需要验证什么 |
| 测试计划 | 执行前大体可以确定 | 保留初始方向，根据证据调整后续实验 |
| LLM 的主要作用 | 理解要求、匹配用例、填写参数、解释结果 | 在此基础上组织调查，提出和检验原因假设，选择有区分作用的实验 |
| 固定脚本的作用 | 主要执行手段 | 继续执行每项具体测试，成为调查中的可靠操作能力 |
| 任务单位 | 一次测试请求或一批用例 | 一个调查任务可以包含多个实验，每个实验包含多次测试运行 |
| 关键记录 | 用例、会话、指标、日志、结论 | 额外记录实验目的、改变条件、对照关系、有效性、证据及假设变化 |
| 记忆重点 | 当前步骤、已用工具、执行结果 | 当前调查目标、最新条件、已排除解释、待验证问题和剩余预算 |
| 知识库用途 | 提供测试用例和判定依据 | 额外提供历史复现经验、触发条件、修复背景及适用边界 |
| 原因分析 | 可以给出日志解释或疑似原因 | 需要组织后续实验，区分支持证据、反对证据和尚未确认的解释 |
| 结果形态 | 通过、不通过、无法判定等 | 同时交付测试结论、调查进展、原因确认程度和环境恢复状态 |
| 结束条件 | 本批测试完成或异常退出 | 达到调查目标、证据已足够、预算用尽、需要补充信息或等待修复 |
| 人工参与 | 配置任务、审核风险、处理异常 | 额外提供关键现场信息、确认重要方案、检查代码和处理超出能力的部分 |
| 模型训练 | 学正确调用工具、遵循参数和处理返回 | 增加如何选实验、处理反证、避免无效重复和保持调查条件的训练 |
| 评测重点 | 执行正确率、判定正确性、耗时 | 额外看复现有效性、问题范围缩小、证据可靠性、人工投入和实验成本 |
| 主要收益 | 少做重复测试操作 | 少做持续推动调查的人工操作和材料整理 |
| 主要代价 | 工具集成、稳定执行、并发与恢复 | 额外增加实验记录、环境一致性、调查质量评估和成本控制 |

这个变化会影响系统的业务模型与评测标准。界面上多一个“分析”按钮，或者让模型在报告末尾多写几段建议，都不足以完成升级。

## 2. 原定位的价值与边界

### 2.1 原系统解决了什么

原系统可以接收：“请验证这个版本在指定条件下的切换表现。”

随后查询用例和规则，组织执行，收集数据，对比要求和历史版本，形成报告。已有文档还设计了异常补查、人工介入、异步任务控制和恢复能力。

这些能力可以减少人工启动脚本、等待结果、收集日志和制作报告的工作，尤其适合例行检查、版本回归和局点验收。

### 2.2 原定位下的人工仍然在哪里

出现失败后，工程师通常还需要回答：

1. 这次失败是否属于有效的产品异常，还是测试环境没有准备好？
2. 用户反馈中的问题，实验室能否重现？
3. 哪些条件是必要的，哪些只是恰好同时出现？
4. 新旧版本的差异是否来自软件本身，还是来自不同配置？
5. 日志中的某个报错是原因、后果，还是无关事件？
6. 开发人员需要怎样的复现材料才能开始排查？
7. 修复以后，怎样证明原问题改善，而且没有引入其他明显问题？

如果系统只给出一次失败报告，这些问题仍由人逐项推动。新方案选择把这一部分作为重点。

### 2.3 哪些地方继续使用固定流程

已经成熟的步骤应继续由程序执行，例如设备就绪检查、业务监测启动、任务状态查询、明确规则比较、重复请求去重、清理和资源释放。

如果一种故障的调查步骤也已经稳定，可以把它整理成固定流程供复用。LLM 主要承担描述不一致、材料分散、后续步骤依赖新证据、难以事先穷举全部分支的工作。

## 3. 新系统的业务范围：两种入口，共用执行基础

### 3.1 入口一：按需测试

用户：“验证当前版本在指定负载下，下载速度是否满足项目要求。”

流程为：明确对象与要求 → 找到适用用例和规则 → 检查环境 → 执行 → 采集 → 判定 → 清理 → 报告。

测试正常且任务完成，就结束。测试异常时先保存结果；是否继续调查，取决于用户任务范围、现有授权、可用资源和调查预算。不能因为出现一个异常，就自动启动不限时的大规模实验。

### 3.2 入口二：异常调查

用户：“升级后，移动过程中视频偶尔卡住，帮我查一下。”

流程为：明确现象 → 整理已知条件 → 构造复现场景 → 多轮对照 → 找触发条件 → 简化步骤 → 验证原因 → 等待或取得修复版本 → 验证修复和相关影响。

不是每项任务都必须完成所有阶段。用户可能只需要稳定复现，或者只需要核查某个原因。任务开始时需要明确本次做到哪一步。

### 3.3 两种入口之间的关系

| 当前情形 | 建议处理 |
| --- | --- |
| 明确测试要求，尚无异常 | 走按需测试流程 |
| 明确测试失败，只需报告 | 交付结果和证据，结束 |
| 测试失败，允许继续调查 | 关联原测试记录，创建或进入调查任务 |
| 用户直接反馈异常 | 从异常调查入口开始 |
| 先有调查，随后要专项测试 | 将专项测试作为调查中的一个实验 |
| 已有修复版本，只需复核 | 从已保存的复现方案开始验证 |

从测试转入调查时，保留原始用例、数据和运行身份。调查不能改写原测试的结果，以免事后看不清最初发生了什么。

### 3.4 任务开始时约定的内容

至少包含调查对象、当前目标、允许环境、可用工具、可变条件、禁止动作、时间与实验次数上限、交付物，以及哪些情况下交给人。

可参考这样的说明：“仅在实验环境中尝试复现，最多安排约定数量的实验，允许调整已登记的负载和移动场景参数；本轮目标是找到可重复的触发条件，暂不修改设备软件。”

## 4. 贯穿例子：升级后，移动视频偶尔卡顿

### 4.1 用户原始反馈

“软件升级后，手机坐车经过几个基站时，视频偶尔卡住。平时没问题，常规测试也通过了。”

这里的“卡住”可能来自视频服务、终端、测试设备、网络环境或产品缺陷。系统不能直接认定是基站间切换的问题。

### 4.2 系统先整理事实和未知项

| 内容 | 示例记录 |
| --- | --- |
| 已知现象 | 视频在移动过程中偶尔停顿 |
| 用户提供的时间关系 | 升级之后观察到；这一点尚不证明升级导致异常 |
| 需要核实的对象 | 终端、基站、软件版本、配置、业务服务 |
| 需要补充的记录 | 卡顿时间、移动路径、业务观测、设备事件 |
| 初始调查目标 | 在实验环境中复现，并寻找必要条件 |
| 初始候选解释 | 高负载影响、连续切换影响、业务服务异常、终端因素 |

能通过资产、配置和运行记录查询的信息，先由工具查询；确实无法获得且影响实验设计的信息，再由用户补充。用户不记得某个条件时，将其标为未知，可以在约定范围内探索，不能伪装成已确认事实。

### 4.3 从业务现象建立观测

在测试动作发生前启动业务监测，覆盖动作前后完整时间窗口。单看“设备切换成功”不能回答视频是否卡顿；单看播放器画面也不一定能判断网络中断。

可用观测由现有工具能力决定，例如业务停顿区间、数据传输间隔、设备事件和错误记录。异常规则需要来自本项目已确认的业务要求。没有适用规则时，先交付观测事实，并确认要使用的判断标准。

### 4.4 安排第一组对照实验

下表仅演示结果如何影响决策。“一次运行”指从约定初始状态开始、执行一段固定动作序列、完成业务观测并收尾；异常次数按出现约定异常的运行计数。每行的 20 次只是示意的初筛安排，不是足以证明任何结论的统一样本量。

| 实验编号 | 版本 | 负载 | 动作序列 | 异常运行数 / 有效运行数 | 初步解释 |
| --- | --- | --- | --- | --- | --- |
| EXP-01 | 新版本 | 普通 | 固定的连续切换序列 | 0 / 20 | 在此范围内暂未观察到异常 |
| EXP-02 | 新版本 | 高负载 | 单次切换 | 0 / 20 | 高负载加单次切换尚未触发 |
| EXP-03 | 新版本 | 高负载 | 与 EXP-01 相同的连续切换序列 | 6 / 20 | 该组合值得继续调查 |
| EXP-04 | 旧版本 | 高负载 | 与 EXP-03 相同的连续切换序列 | 0 / 20 | 新旧版本可能存在差异，需重复验证并排除环境差异 |

各组固定拓扑、终端配置、业务来源、观测规则与其他可控制条件。实际试验应检查执行顺序、资源残留和时间变化是否影响结果；需要时交错运行新旧版本的对照组，并记录无法固定的条件。

这些结果支持“优先调查新版本、高负载、连续切换这一组合”。它们尚不足以证明新版本必然是原因，更不能凭 0 / 20 宣称旧版本永远没有问题。

### 4.5 根据结果调整方向

在得到上述结果后，继续穷举所有频段和设备型号未必划算。优先检查：

1. 该组合能否在新的有效运行中再次触发。
2. 连续切换需要怎样的顺序和间隔。
3. 哪些背景业务可以删除。
4. 成功和失败时，业务、设备与资源记录有何共同差异。

如果补充实验发现旧版本也出现相似异常，就更新记录，重新检查公共环境因素，不能为了坚持最初解释而忽略新证据。

### 4.6 得到更简洁的复现步骤

假设删减实验后发现：多种背景业务可以去掉，较长等待也不是必要条件；保留规定高负载和短间隔的两次切换后，仍能重复出现同类异常。

可交付的复现方案是：

1. 加载指定新版本和已记录的配置。
2. 将环境准备到记录中的负载范围，启动业务监测。
3. 按固定路径和间隔执行两次切换。
4. 按同一异常规则检查业务停顿，并收集两侧设备记录。
5. 保存结果，清理本轮状态，确认下一轮起点满足要求。

这称为“当前已验证的简化复现方案”。如果没有穷尽全部删减组合，不宣称已经找到全局最少步骤。

### 4.7 提出并验证原因假设

假设工具进一步观察到：异常运行中，旧连接相关资源没有按预期释放，后续处理出现等待。

LLM 可以提出“连续切换后的资源释放存在异常”这一假设。随后需要对照新旧版本、成功与失败运行、资源变化与业务停顿的时间关系，检查证据是否一致。

如果测试平台支持经批准的相关控制动作，可以进一步设计干预实验；不支持时，应明确缺少这一验证能力。开发人员结合实现和代码确认具体缺陷后，系统再记录确认依据。

### 4.8 验证修复

取得修复版本后，在相同条件和同一异常规则下重跑复现方案，对照原异常版本，并覆盖相关邻近条件。

同时检查业务停顿、完成时长、吞吐量和资源使用等相关指标，避免只看原异常是否消失。修复若只是延长等待时间，还需要检查等待变长是否违反要求。

### 4.9 最终交付

| 原定位的主要交付 | 新方案增加的交付 |
| --- | --- |
| 哪些测试通过、哪些失败 | 从用户描述到实验场景的转换依据 |
| 指标、日志和适用规则 | 已验证的触发条件与尚未覆盖条件 |
| 初步异常解释 | 简化复现步骤及独立复现结果 |
| 建议人工排查方向 | 原因假设、支持与反对证据、确认来源 |
| 测试执行记录 | 修复前后对照、相关影响、环境恢复记录 |

## 5. 六个调查阶段各自新增了什么

| 阶段 | LLM 负责 | 程序和工具负责 | 仍需人提供或确认 | 进入下一阶段的依据 |
| --- | --- | --- | --- | --- |
| 用户描述异常 | 整理现象、识别歧义和信息缺口 | 查询资产、版本和记录 | 无记录的现场信息、本次调查目标 | 对象和范围足以开始设计实验 |
| 转成复现场景 | 匹配用例，组织候选场景 | 检查参数、能力和执行前提 | 无法自动确定的关键条件 | 有可执行且可观测的方案 |
| 找到触发条件 | 选择对照方向，解读证据变化 | 控制条件、重复执行、统计和记录 | 工具无法覆盖的操作或信息 | 候选触发条件得到重复支持 |
| 缩减复现步骤 | 提出删减与恢复计划 | 按计划运行并检查环境一致性 | 必要时复核删减后的业务含义 | 新运行仍可复现同类异常 |
| 验证原因 | 提出竞争解释，安排区分实验 | 提供真实证据，执行允许的干预 | 开发侧确认、无法由工具验证的原因 | 达到本次约定的确认程度或明确证据缺口 |
| 检查修复及副作用 | 根据修复范围选择相关补测 | 执行修复前后对照，按规则判定 | 修复版本、重要业务标准 | 报告原问题与相关指标的验证情况 |

每个阶段可以暂停，也可以因为新证据回到前一阶段。阶段表示当前调查目的；具体仍可能调用多个测试和查询工具。

## 6. 调查中最重要的决策：下一次为什么要这样测

### 6.1 每个实验至少说明五件事

| 项目 | 示例 |
| --- | --- |
| 要回答的问题 | 连续切换是否比单次切换更容易触发异常？ |
| 当前依据 | 单次切换暂未异常，连续切换出现过异常 |
| 改变的条件 | 在相同准备状态下更换动作序列 |
| 保持的条件 | 版本、负载范围、终端、业务和判定方法 |
| 不同结果怎样影响后续 | 若两组相似则调整方向；若差异重复出现则继续检查序列与间隔 |

实验记录应在执行前保存目的和计划，执行后追加实际条件和结果。事先计划与实际执行不同的地方要显式记录。

### 6.2 怎样选择下一组实验

优先选择有望区分当前几个合理解释、工具确实支持、代价可以接受、影响范围较小的实验。相关因素较多时，可以先筛选，再对少数候选安排更严格的对照。

不必一开始实现复杂的自动搜索算法。首版允许 LLM 给出简短理由，程序检查实验是否可执行、是否超预算、是否与已有实验重复。

### 6.3 允许改变多个条件，但要解释用途

单独改变一个条件有助于解释差异，但所有问题都用单因素测试也不合理。有些异常由多个条件共同触发，初筛时可以测试几种组合。

区别在于实验目的：用于发现现象的组合探索，不能直接当作证明某一个条件导致异常的严格对照。需要确认时，再补充能够区分解释的实验。

### 6.4 遇到反证怎么办

把“高负载是必要条件”作为假设后，如果低负载也出现同类异常，应降低或撤销这一判断，检查原实验是否有未记录差异，并保留所有原始结果。

重新解释数据可以，删除不符合预期的有效数据不可以。工具失败、观测中断等无效运行需要按预定规则单独计数，并说明排除原因。

## 7. LLM 的作用怎样扩大，又怎样保持边界

### 7.1 新增价值来自哪些工作

| 工作 | 具体例子 | 固定程序继续承担的部分 |
| --- | --- | --- |
| 理解不完整描述 | 把“坐车卡视频”整理为移动、业务、负载等候选因素 | 查询可用信息，验证对象和范围 |
| 联合阅读材料 | 对照用户反馈、版本说明、历史缺陷与当前结果 | 检索、过滤、保留来源 |
| 选择调查方向 | 决定先比较版本，还是先排除业务服务异常 | 检查实验支持情况与成本 |
| 按证据调整计划 | 旧版本也失败后，转查公共环境因素 | 保存新旧计划与实验关系 |
| 组织竞争解释 | 资源未释放与消息延迟都可能解释现象 | 收集能区分解释的观测 |
| 设计后续验证 | 为两个解释安排不同预期的实验 | 执行与计算，检查有效性 |
| 组织交付材料 | 把多轮记录整理成可复核的问题说明 | 校验引用与结构化结论 |

### 7.2 什么事情不需要每次调用 LLM

任务轮询、等待回调、设备锁检查、重复请求去重、指标计算、已确认门限比较、固定清理流程，都可以由程序完成。明确的故障排查步骤也可以作为已审核方案直接复用。

LLM 不需要逐条阅读所有原始日志。解析工具先提取事件、计数和可定位片段，模型在证据不足时再查询细节。这样可以同时控制成本和减少遗漏。

### 7.3 为什么不说“只有 LLM 才能实现”

针对有限故障编写全部调查分支，理论上也能自动化。LLM 的合理价值是降低处理多样文字描述、跨资料关联和变化调查路线的人工与规则维护成本。

这项价值需要对照评测。某一类任务若固定流程更便宜、更可靠，就继续使用固定流程。任务复杂也不自动意味着必须换更大模型，模型规模应由实际质量、时延和资源要求共同决定。

### 7.4 怎样证明模型参与了实质工作

每次计划变更保存简短、可核查的依据，例如：“旧版本也出现异常，当前证据不支持只查版本差异，下一步核对业务服务和共享环境。”

检查模型是否真正使用了新证据，是否安排了能区分解释的实验，是否减少了人工接手。报告写得流畅、工具调用次数多，都不能单独证明价值。

## 8. 整体架构：增加调查管理，复用测试执行

### 8.1 建议分成三个层次

| 层次 | 回答的问题 | 主要职责 |
| --- | --- | --- |
| 调查管理 | 下一组实验要验证什么？ | 维护目标、条件、原因假设、计划与预算，决定继续、等待或交接 |
| 实验管理 | 这一组实验怎样可靠运行并比较？ | 固定实验条件，安排重复运行，管理对照关系，检查数据是否可比 |
| 测试与工具执行 | 具体动作怎样完成？ | 调用原有脚本、采集数据、查询任务、计算指标、清理环境 |

按需测试可以直接使用实验管理和执行层，不必先建立原因假设。调查任务则循环安排实验，复用同一执行基础。

这是职责划分，不要求立即拆成三个独立服务。首版可以在现有应用中增加模块和数据表，以减少集成成本。

### 8.2 新流程中的主要业务节点

| 节点 | 输入 | 输出 |
| --- | --- | --- |
| 接收任务 | 测试要求或异常描述 | 任务类型、对象、目标、范围 |
| 补充事实 | 缺失项、已有资料 | 已知事实、仍缺信息、来源 |
| 提出实验 | 当前问题、历史结果、可用能力 | 实验目的、条件、对照、预算估计 |
| 检查实验 | 实验计划与允许范围 | 可执行、需修改、需澄清或需审核 |
| 执行与观测 | 已检查的计划 | 任务状态、实际条件、原始证据 |
| 清理与复核 | 本轮动作和初始状态 | 恢复结果、残留事项 |
| 评价本轮 | 结果、条件、规则、恢复记录 | 有效性、测试结论、对当前问题的意义 |
| 更新调查 | 本轮评价与历史实验 | 假设变化、证据缺口、下一步 |
| 交付或等待 | 已完成工作与停止依据 | 阶段报告、待处理事项、恢复入口 |

本轮评价前后可以按需补取只读证据。环境清理的具体顺序服从用例和平台约束；需要保留某种状态用于诊断时，应有明确的保留时限和收尾责任。

### 8.3 原有组件怎样继续使用

| 现有文档中的组件或设计 | 建议沿用方式 | 新增要求 |
| --- | --- | --- |
| LangGraph 等流程编排 | 保存节点进度，组织执行与等待 | 表达调查、实验、测试之间的关系和业务返回分支 |
| FastAPI 等接口层 | 接收任务、查询结果、提交补充信息 | 增加调查进展和实验记录查询 |
| Celery 等后台任务机制 | 承担长时间测试与数据处理 | 分离模型决策等待、实验等待和外部修复等待 |
| 数据库与 checkpoint | 保存任务、运行和恢复状态 | 增加不可随意覆盖的实验与证据记录 |
| 对象或文件存储 | 保存原始日志和报告 | 按任务、实验、运行关联，保留版本与校验信息 |
| 搜索与知识库 | 检索用例、规范和历史缺陷 | 支持按设备、版本、触发条件和确认状态过滤 |
| 推理服务 | 提供模型调用 | 区分计划、解释与报告等调用，分别记录成本和效果 |
| 追踪与监控 | 记录工具和模型调用 | 能查看从一次调查到各实验和证据的完整关联 |

这些是对现有设计的复用建议，不意味着表中全部组件已经完成生产接入。新定位本身不要求先更换框架、向量数据库或推理平台。

### 8.4 首版是否需要多个 Agent

建议先使用一个负责调查决策的 Agent，配合明确的实验管理和执行工具。

多组独立实验可以由普通任务调度并发执行，不必每组配置一个 Agent。只有日志、业务记录等分析工作确实可以独立进行，且并行后的质量和成本更合适时，再考虑拆分分析角色。

无论是否使用多个 Agent，都必须共享明确的实验条件和证据引用，不能让各个角色各自假定不同版本或对象。

## 9. 数据模型：从一次请求，扩展到完整调查记录

### 9.1 先分清几个对象

| 对象 | 含义 | 贯穿例子 |
| --- | --- | --- |
| 测试请求 | 用户要求完成的一次测试任务 | 验证指定负载下的切换表现 |
| 调查任务 | 为一个异常收集、比较和验证证据的工作记录 | 调查升级后的移动视频卡顿 |
| 实验 | 为回答一个明确问题而设计的一组运行 | 对比新旧版本在同条件下的异常情况 |
| 测试运行 | 一次具体执行，从准备、动作到观测和收尾 | 在新版本上运行一段固定切换序列 |
| 证据 | 原始数据或可追溯的计算结果 | 业务停顿区间、事件日志、配置快照 |
| 原因假设 | 当前待检验的一种解释 | 连续切换后资源释放异常 |
| 报告 | 对某个时间点状态的可阅读整理 | 复现报告、调查阶段报告、修复验证报告 |

一个调查任务可以包含多个实验，一个实验可以包含多次运行。一条原因假设可能使用多个实验的证据，同一次实验也可能影响多个假设。

用户会话只是交互入口，不应直接代替调查身份。一个用户可能在同一聊天中讨论两个问题；同一个调查也可能隔天从新的交互入口继续。

### 9.2 调查任务需要保存什么

调查身份、原始反馈、相关对象、当前目标、最新有效约束、调查阶段、计划版本、已完成实验、原因假设及状态、证据缺口、资源预算、等待原因、交接信息和结束依据。

用户说“只验证能否复现，暂不继续查原因”时，应更新任务目标，并保留这一变更记录。

### 9.3 每个实验需要保存什么

| 字段类别 | 应保存的内容 |
| --- | --- |
| 身份与关联 | 实验编号、所属调查、计划版本、对照实验或对照组 |
| 目的 | 要回答的问题、相关原因假设、不同结果对应的下一步 |
| 条件 | 对象、版本、拓扑、配置、业务、负载、动作序列、观测窗口 |
| 设计 | 改变的条件、保持的条件、重复安排、执行顺序、停止规则 |
| 可执行性 | 工具能力检查、权限、资源需求、预计耗时 |
| 实际执行 | 每次运行、实际条件、环境偏差、开始结束时间 |
| 结果 | 有效与无效运行数、异常数、指标、证据引用 |
| 解释 | 这次结果支持什么、不支持什么、还不能判断什么 |
| 收尾 | 清理状态、资源释放、恢复复核、残留事项 |

计划由模型提出，实际执行条件和结果由执行系统记录。模型可以解释和引用记录，不能凭自然语言报告替代真实运行数据。

### 9.4 每个原因假设需要保存什么

简短描述、提出时的证据、可以观察到的预期、需要的验证方式、支持证据、反对证据、替代解释、当前状态及其变更理由。

可以使用“待验证、获得部分支持、证据冲突、在已测范围内不支持、经指定方式确认”等状态。避免用模型自报的一个分数替代全部证据。

### 9.5 版本和历史怎样保存

计划修改后新增版本，实际实验记录保留原样。报告修订也保留来源数据版本。新证据改变结论时，增加修订说明，原报告不应被静默覆盖。

已有结果能否复用，需要检查对象、配置、软件、规则和观测范围是否适用，不能只因为标题相似就复用。

## 10. 实验可靠性：新方案最需要补强的工程基础

### 10.1 先定义“出现了同一个异常”

“卡顿”不能一会儿按吞吐下降判断，一会儿按播放器缓冲判断。调查开始时应固定当前使用的异常识别方法、必要观测和适用范围。

更换异常识别规则后，旧原始数据可以按新规则重新计算时，记录重算过程；无法重算时，不能把新旧异常次数直接混在一起比较。

### 10.2 初始状态要可核查

设备状态、配置、资源、业务、日志采集和测试任务都要在运行前检查。若上一次实验留下资源占用，下一次异常可能来自残留，导致错误归因。

独立运行之间按实验计划恢复。一次运行内部如果要研究连续操作的累积影响，则保留这段操作中的状态，不能在每个动作后都清空，从而消除原本要观察的问题。

### 10.3 记录“目标条件”与“实际条件”的差别

设定高负载，不代表整个观测窗口都实际处于同一负载。需要保存实际范围和变化。未能保持要求时，判断该运行是否仍适用于本次比较，并给出理由。

物理设备、环境背景和时间变化无法完全固定时，应如实记录。模型不能通过一句“其他条件不变”掩盖工具没有测量或控制的条件。

### 10.4 重复执行与偶发异常

少量运行可以用于初筛，重要判断需要独立复核。反复使用同一设备且环境状态关联时，也不能直接假定每次运行完全独立。

实验次数与停止规则应尽量在执行前确定；预算允许扩展时，应记录扩展理由。不要“测到出现一次差异就停”，再把该差异当成稳定结论。

统计计算由工具完成，并说明样本、前提和不确定性。没有必要把每次调查都套进同一种统计检验；两个汇总百分比也不足以自动生成可靠的显著性结论。

### 10.5 有效性和产品结果分别记录

| 情形 | 实验有效性 | 产品结论 |
| --- | --- | --- |
| 条件满足、监测完整，观察到违反要求 | 有效 | 不通过 |
| 条件满足、监测完整，在已测范围内满足要求 | 有效 | 按适用规则通过 |
| 业务监测没有覆盖异常窗口 | 不完整 | 对该业务要求无法判定 |
| 测试前设备未就绪，动作未执行 | 未开展或无效，说明具体原因 | 不能据此判产品失败 |
| 部分监测中断，但其他独立证据足以判某项不通过 | 部分有效，逐项说明 | 保留已被证实的失败项，其余无法判定 |

数据不完整不代表可以丢弃全部已取得证据；需要逐项说明哪些结论还能成立。

### 10.6 简化复现不是机械地删除步骤

删去业务监测，可能让异常无法观察；删去准备动作，可能让前置条件不成立。前者是失去观测，后者是改变实验，都不能直接解释为“问题不再出现”。

每次删减检查：前置条件是否满足、观测是否完整、异常是否同类、重复情况是否足以支持判断。最后使用新运行验证简化方案，不只在用于搜索的旧结果上得出结论。

## 11. 工具体系：哪些复用，哪些扩充

### 11.1 现有文档里的能力如何服务调查

| 原有工具能力 | 新方案中的用途 | 需要扩充或核实的地方 |
| --- | --- | --- |
| 用例查询 | 寻找复现场景、边界条件和已有动作模板 | 返回适用版本、可调参数、前置条件和观测要求 |
| 规范查询 | 确定业务异常和验收要求 | 明确规则版本、来源和冲突处理 |
| 资产与拓扑查询 | 明确反馈涉及的真实对象 | 区分记录信息与当前实时状态 |
| 状态与配置快照 | 固定运行前后条件，核对环境差异 | 明确快照完整性、时间与可恢复范围 |
| 仿真执行 | 在允许环境中组合条件、重复运行 | 实际可调范围、初始状态和运行证据 |
| 现场执行 | 执行经允许的现场验证 | 与仿真明确区分，不能混用结论 |
| 指标采集 | 收集每次运行的结果和变化过程 | 绑定运行、时间窗口、单位与缺失信息 |
| 业务监测 | 观察用户业务是否受影响 | 在动作前就绪，覆盖完整窗口 |
| 基线比较 | 比较版本、配置和实验条件 | 从单一旧版本对比扩展为任意适用对照；检查可比性 |
| 日志解析 | 提供事件、片段和候选解释 | 返回原始引用、时间误差、缺口；假设不写成事实 |
| 任务控制 | 查询、取消测试运行 | 取消受理与真正停止分别记录 |
| 环境恢复 | 保证下一次运行条件可信 | 恢复失败时阻止依赖该环境的后续实验 |
| 结果判定 | 执行明确的规则与证据检查 | 仅承担适用范围内的测试判定，不承担全部原因确认 |
| 报告生成 | 汇总实验、调查和修复材料 | 引用结构化事实，显示确认程度和未覆盖范围 |
| 集群调度 | 分配实验资源 | 资源互斥、额度、环境隔离与并发成本 |

### 11.2 建议新增的逻辑能力

| 逻辑能力 | 必要工作 | 首版实现选择 |
| --- | --- | --- |
| 实验记录与查询 | 保存目的、条件、运行和结果，按条件查找 | 可直接增加现有应用模块和数据库记录 |
| 条件差异比较 | 列出两组实验的实际差异与不可比较项 | 优先由程序比较结构化字段，LLM 辅助解释 |
| 调查计划检查 | 检查实验是否支持、超预算、重复或缺关键观测 | 程序规则为主，必要时增加人工审核 |
| 原因假设与证据关联 | 保存支持、反对和待补证据 | 使用普通记录和关系即可，无须先引入复杂图系统 |
| 修复版本登记与关联 | 将修复版本关联到问题和复现方案 | 先支持明确版本输入，后续再考虑外部系统连接 |

“新增逻辑能力”不等于必须新增独立服务或一个同名工具。哪些暴露给模型、哪些由运行程序自动执行，可以按最简实现决定。

### 11.3 工具的输入输出需要共同遵守的要求

设备、运行和证据身份来自真实来源；输出明确单位、时间、范围、缺失和状态。关键结果自动写入记录，不依赖模型复述。模型提交操作请求后，权限、范围和前置条件仍由执行器检查。

重复提交同一次运行应返回同一任务；计划中的另一次有效重复运行必须使用不同运行身份。不能因为共用一个去重键，把本来需要运行十次的实验实际只运行了一次。

工具描述还要说明能回答哪些问题、不能回答哪些问题。例如，只能返回事件摘要的工具不能证明具体代码分支出错；只能模拟有限条件的工具不能保证复现所有现场现象。

## 12. 知识库：从“怎么测”，扩展到“过去怎样查”

### 12.1 需要增加的资料类型

| 原有资料 | 新方案建议增加或重新整理的资料 |
| --- | --- |
| 测试规范、用例、历史缺陷 | 异常描述与实际触发条件的对应关系 |
| 测试步骤与预期结果 | 复现过程中的有效步骤和已经证明无关的步骤 |
| 缺陷结论 | 结论形成前的对照实验与反证 |
| 版本说明 | 修改范围、适用设备、修复背景和已知限制 |
| 专家确认用例 | 专家确认的调查方案和可复用复现方法 |
| 普通日志 | 常见现象的候选解释与区分方法，并附适用边界 |

一条历史经验最好能回答：“当时是什么条件，实际观察到了什么，怎样验证，最终由谁以什么依据确认？”只有“某报错通常是某原因”这样的短句容易导致误用。

### 12.2 历史相似不等于当前原因相同

检索结果必须检查版本、设备、配置、业务和环境是否适用。旧缺陷可以提供候选条件和验证方法，但不能作为当前故障已经确认的证据。

例如，旧案例中的卡顿由服务端异常引起，当前案例虽然描述相似，也应先检查本次服务记录。不能因为语义检索排名第一，就直接沿用原因和修复建议。

### 12.3 写入经验库的规则

区分未确认线索、经过有效实验支持的经验、开发侧确认的缺陷和已完成修复验证的案例。每条记录带来源、适用范围、确认方式和版本。

模型生成的猜测不能自动升级为可信经验；专家批准一次实验，也不等于批准了最终原因。经验更正、过期和撤回需要保留记录。

### 12.4 检索和模型微调分别解决什么

最新规则、版本限制、设备能力和具体历史案例通过检索获取。模型微调主要改善读到这些信息后怎样做决定。

把每个新缺陷都训练进模型不是首选。事实经常变化，放在带版本和来源的资料中更容易更新和复核。

## 13. 上下文与记忆：让模型持续围绕同一个问题工作

### 13.1 模型每轮最需要看到的内容

建议按稳定顺序提供：本次目标与允许范围、最新有效条件、当前调查阶段、少量关键实验结果、原因假设及反证、待补证据、可用工具和剩余预算。

完整日志和全部历史不必每次都发送。先提供可追溯摘要，模型需要细节时再查询原始记录。摘要是视图，原始证据是依据。

### 13.2 调查历史怎样压缩

必须保留重要条件、每个结论的适用范围、否定或冲突证据、实验有效性、来源引用和待办事项。不能只保留“目前最可能是资源问题”，却删掉“旧版本也发生过一次相似异常”的反证。

摘要更新后应检查引用是否仍有效。超出上下文容量时，优先按实验和假设检索历史，而不是随机截取近期消息。

### 13.3 用户中途补充要求

例如：“目标改成 C 到 D，其他条件不变。”系统需要更新对象，检查原用例、参数、证据和实验是否适用于新对象。当前已提交任务可能仍在运行，应核对能否取消并记录实际状态。

旧结果可以作为历史背景，但未经适用性检查不能用于新对象的结论。新要求不自动撤销已完成动作，也不能覆盖执行器的权限限制。

### 13.4 防止不同调查串用证据

按用户、项目、设备和调查范围检查访问权限。实验和证据引用都绑定归属。会话编号不能自动提供数据隔离，历史检索也要遵守访问范围。

不同任务的结果可以在满足权限和适用性检查后作为参考，但要显式关联来源，避免把其他环境的成功记录当成本次已完成测试。

## 14. 长时间运行、并发和等待方式

### 14.1 调查生命周期比测试运行更长

一次测试可能持续数分钟，一次调查可能跨多个工作日，并等待现场信息、资源或修复版本。调查记录可以持续存在，但不需要让模型请求、服务器线程和设备资源一直占用。

区分等待测试完成、等待可用设备、等待补充资料、等待人工决定、等待修复版本。不同等待原因有不同恢复条件。

### 14.2 建议保存的业务状态

| 状态 | 含义 | 恢复或结束条件 |
| --- | --- | --- |
| 信息整理中 | 正在确认对象与现场条件 | 足以安排实验，或明确需补信息 |
| 计划待执行 | 已有下一组实验 | 条件、权限、资源和预算允许 |
| 实验进行中 | 正在准备、执行或采集 | 任务完成、取消或失败 |
| 结果评估中 | 检查有效性并更新调查 | 决定继续、等待或交付 |
| 等待资料 | 缺少关键记录或条件 | 收到资料或到达约定等待处理点 |
| 等待审核 | 后续方案需要明确决定 | 审核结果到达 |
| 等待修复 | 已交付问题，等待指定版本 | 修复版本登记并通过适用性检查 |
| 已完成本轮目标 | 达到约定目标 | 可以在后续新阶段继续，不改写原阶段结论 |
| 已交接 | 自动调查到达能力或预算边界 | 人接手，或后续补齐条件后继续 |
| 已取消 | 用户要求结束 | 保存结果并完成清理 |

测试工具报错与调查业务等待分开记录。等待修复不是失败，也不应该触发不断重试。

### 14.3 并发前先检查实验是否互相影响

不同资源上的实验可以并发。共用设备、连接、流量源或配置时，需要判断是否互斥；否则一组实验可能改变另一组的负载，破坏比较。

不得把“多组同时开始”直接理解为节省时间而不影响结果。并发方式也是实验条件的一部分。

### 14.4 预算、取消与恢复的一致性

提交前预留实验资源和预算，结束后按实际消耗结算，避免并发任务同时看到剩余额度而超额执行。用户修改计划后，迟到结果仍保存到原实验，不能覆盖新计划状态。

恢复任务时查询真实运行状态，核对计划版本、实际配置和已完成动作。重复恢复不能重复触发同一个动作；真正需要再次实验时创建新的运行记录。

## 15. 结果体系：四种结论应当分别表达

### 15.1 测试结果

表达某次有效测试是否满足适用要求：通过、不通过、无法判定，或者因前置条件而未开展。具体名称与现有结果规则统一。

### 15.2 调查进展

表达系统已经推进到哪里：尚未复现、已复现、已缩小触发范围、已有简化方案、原因仍待验证、达到本轮目标、等待修复或已交接。

例如，“测试不通过，已稳定复现并形成步骤”可以是一项成功完成的复现任务。

### 15.3 原因确认程度

| 程度 | 可以怎样写 | 需要的依据 |
| --- | --- | --- |
| 现象相关 | 两类事件在这些记录中同时出现 | 可追溯观测，说明时间和样本范围 |
| 候选解释 | 怀疑连续切换后的资源处理异常 | 说明解释如何符合现象，以及还有哪些其他解释 |
| 获得实验支持 | 多组有效对照支持该解释 | 对照可比，重复结果和反证均有记录 |
| 在已测范围内不支持 | 预期差异没有出现，或反证更强 | 说明测试能力、覆盖范围和限制 |
| 经指定方式确认 | 开发侧结合代码与实验确认具体缺陷 | 记录确认人或来源、具体版本、证据和修复关联 |

是否允许系统自动使用“确认”一词，应由项目提前规定确认标准。没有代码和内部状态证据时，可以完成现象层定位，但通常不应保证定位到具体函数或代码行。

某次修复后现象未再出现，是重要证据；如果修复同时改变多处逻辑，仍不足以单独证明其中哪一处是原始原因。

### 15.4 环境恢复状态

表达已恢复、部分恢复、恢复失败、仍有保留状态或残留任务。报告生成成功、调查达到目标，都不能覆盖恢复失败。

系统需要同时显示上述结果。例如：“已找到简化复现步骤；原因待开发确认；本轮测试不通过；环境已恢复。”

### 15.5 不再依赖一个总置信度替代全部判断

模型可以提供辅助排序或建议，但是否继续、能否发布某种结论，要依据证据完整性、适用规则、确认标准和任务范围。

现有文档中的历史分数阈值不能直接解释为“原因正确的概率”，也不能单独作为确认根因或结束调查的依据。

## 16. 报告与界面：让工程师快速知道已经查到哪里

### 16.1 调查进展页面应优先展示什么

当前目标和对象、本轮正在验证的问题、关键实验对照、已经知道的事实、当前怀疑及反证、尚缺证据、下一步、剩余预算，以及是否需要人处理。

不要只展示“调用日志工具第七次”。工程师更需要知道“正在区分负载影响和连续切换影响，预计还需要两组已安排实验”。预计数量来自实际计划，计划调整后同步修改。

### 16.2 实验结果页应便于比较

按版本、配置、动作、实际负载、有效运行数、异常数、观测完整性和证据引用并列展示。不同条件以明确标记显示，而不是让人从两份长日志中寻找区别。

被取消、无效或数据不完整的运行仍可查询，但不与有效运行混为同一分母。无法直接比较的实验应说明原因。

### 16.3 建议的调查报告结构

| 部分 | 必要内容 |
| --- | --- |
| 用户现象与目标 | 用户描述、调查对象、本轮做到哪里 |
| 已确认事实 | 带原始引用的观测，避免混入猜测 |
| 复现情况 | 场景、次数、异常识别方法、范围与限制 |
| 简化复现步骤 | 准备、动作、观测、结果和清理方法 |
| 原因调查 | 候选解释、支持与反对证据、已排除范围 |
| 修复验证 | 版本、与原条件的对应关系、结果、相关影响 |
| 未完成事项 | 信息缺口、未覆盖条件、等待或交接原因 |
| 运行与恢复 | 实验索引、资源消耗、残留事项和恢复状态 |

报告可以由 LLM 帮助撰写，但数据表、版本、次数和测试判定应来自已保存记录。发布前校验引用存在、归属正确，关键数值和状态与原始结果一致。

### 16.4 不同阶段交付不同材料

找到触发条件后可以先交付阶段报告；开发接手时交付复现材料；修复完成后再交付验证报告。等待开发期间无须假装整个调查已经彻底结束。

## 17. 人与系统的分工：减少操作，也减少无效追问

### 17.1 哪些工作优先交给系统

查询记录、筛选用例、检查已知前提、准备参数、启动测试、等待、收集证据、做结构化比较、重复验证、整理材料，以及在约定范围内提出下一组实验。

### 17.2 人仍然承担什么

提供系统无法获得的现场事实，确认关键业务要求，决定超出原范围的实验，完成工具不支持的操作，检查具体实现与代码，交付修复，并确认重要缺陷结论。

目标是减少持续人工推动，而非承诺所有问题完全无人参与。一次有证据、问题明确的交接，比大量无依据的自动操作更有价值。

### 17.3 不要每改一个参数都找专家

首版可区分：按原样执行已审核用例；在已允许参数范围内进行变体和组合；引入新动作、新脚本或超出范围的操作。

前两类在任务授权和执行校验允许时可以自动推进；第三类按明确规则审核。与现有总览中“所有生成变体都需人工审核”的描述存在需要统一的地方，应在正式采用新设计时修订；在此之前不应默默视为原规则已改变。

### 17.4 人工交接应当一次给齐什么

当前目标、已经得到的结论与限制、已完成实验及理由、有效证据、尚未验证的解释、卡住的原因、建议下一步和环境状态。

例如：“已确认规定负载与连续切换组合能重复触发；缺少设备内部资源记录，无法继续区分两种解释；请提供指定日志权限，或由开发检查相关状态。”

## 18. 运行边界：重点防止调查扩大和证据被破坏

### 18.1 原有规则继续适用

动作前检查权限、资源、对象和参数；工具执行有真实状态；超时后先核查是否已执行；取消后确认停止；收尾恢复避免覆盖其他任务的合法变更。

### 18.2 新增需要控制的事项

| 风险 | 具体表现 | 建议控制 |
| --- | --- | --- |
| 调查无止境 | 反复变化参数，没有明确问题 | 每组实验必须有目的，设时间与次数上限 |
| 无效重复 | 相同条件和观测反复运行，没有说明重复价值 | 查询历史实验，允许有理由的复核，限制无理由重复 |
| 条件逐渐偏离 | 为了复现而改到不符合用户场景 | 持续核查固定约束，标记探索条件与原现场的差异 |
| 破坏关键证据 | 先清日志或重启，原始状态丢失 | 按方案先保存必要证据，再做允许的恢复动作 |
| 跨环境越界 | 在实验室未复现就自行转现场 | 明确环境范围，切换环境重新检查允许条件 |
| 恢复不完整 | 残留影响后续实验或其他任务 | 清理必经、恢复复核、冲突报告和资源隔离 |
| 外部材料夹带指令 | 日志或缺陷文本要求执行无关操作 | 外部内容仅作为数据，不能更改系统权限和任务目标 |
| 生成未经审核的代码 | 为支持新场景临时写脚本直接执行 | 首版使用已登记能力；新代码另走审查和验证流程 |

### 18.3 明确停止或交接条件

达到本轮目标；预算或期限已到；关键证据无法获取；工具不支持必要实验；继续操作超出允许范围；多轮没有新增有效信息；环境无法恢复；用户要求取消。

停止时写清本轮已取得价值。没有复现也可以交付排查过的条件和缺失信息，但不能把“未复现”写成“用户反馈不存在”。

### 18.4 业务限制与技术限制分开

现有编排中的循环步数、连续错误次数等技术上限仍然有用，但不等于调查预算。一次调查可能包含多次恢复和运行，整体实验数量、设备占用时间和费用需要独立累计。

## 19. 模型微调：从正确执行，扩展到正确调查

### 19.1 原有训练内容继续保留

工具选择、参数和真实身份引用、提交与完成的区分、指标单位、缺证据时的处理、最新约束保持和异常恢复，仍是基础能力。

新定位不意味着原有训练都无用，也不意味着必须重新训练一个模型。需要先用新任务评估现有模型，确定问题发生在哪些决策上。

### 19.2 新的主要困难是什么

模型可能理解每个工具，却不善于安排高价值实验。例如：

- 发现新旧版本差异后，直接声称新版本某模块有错，跳过可比性检查。
- 一次实验同时改版本、负载和拓扑，却只归因于版本。
- 反复运行同一个条件，没说明是为了独立复核还是没有新方向。
- 发现反证后仍重复原解释。
- 简化复现时删掉监测，误把“看不到异常”当成“异常消失”。
- 使用修复后的新规则计算结果，再与原规则下的数据直接比较。
- 在证据不足时给出确定原因，以便尽快结束任务。

这些都属于调查决策质量问题。先排除工具缺陷、状态丢失、描述不清和提示不完整，再判断微调是否值得。

### 19.3 训练数据从哪里来

| 来源 | 能提供什么 | 使用条件 |
| --- | --- | --- |
| 专家真实调查记录 | 在当时信息下怎样决定下一步 | 保留实际可见上下文、工具结果和专家依据 |
| 人工修正记录 | 哪个实验不合适，应该怎样改 | 修正后的后续结果必须重新取得或使用明确标注的合格模拟 |
| 经审核的模拟任务 | 覆盖低频条件、反证和工具缺失 | 模拟返回与假设规则一致，不能冒充现场事实 |
| 失败与中止任务 | 怎样识别能力边界并交接 | 不把合理停止一律标为差样本 |
| 普通按需测试 | 保留原来简单任务能力 | 与新调查样本一起评估，防止过度调查 |

数据不应只有成功找到原因的案例。未复现、证据冲突、原因被否定、需要开发确认、修复仍有副作用，都需要正确示范。

### 19.4 每个示范要教哪一种决定

| 当时情况 | 推荐示范 | 应避免的示范 |
| --- | --- | --- |
| 只有新版本数据 | 提出在相同条件下补测旧版本 | 直接认定新版本引入缺陷 |
| 两种原因都合理 | 选择可区分两种解释的观测或实验 | 两个都写“可能”，随后结束 |
| 新结果反对原解释 | 更新假设及下一步，保留反证 | 忽略结果或编造额外条件 |
| 工具无法读取必要状态 | 说明缺口，提出可行替代或交接 | 声称已经检查内部状态 |
| 达到预算上限 | 交付已知事实和未解决事项 | 自行继续大批量执行 |
| 原始需求只是单项测试 | 完成测试后按约定结束 | 为了表现自主性启动无关调查 |

### 19.5 监督微调可以怎样使用

监督微调，就是用“当时可见信息与专家确认的正确输出”继续训练模型。输出可以是合适的工具请求、简短实验计划、更新后的假设或合理交接。

既可以保存完整调查过程，也可以按决策点组织样本；按决策点拆分时必须保留做决定所需的上下文。不能让模型在计划实验时提前看到未来实验结果和最后确认的原因。

不需要为训练编造冗长的内心推演。保存本轮问题、选择理由、预期区分方式和证据引用，便于审核即可。

### 19.6 偏好训练什么时候有价值

在同一个可见上下文下，比较两个候选决定，例如：“补取能区分解释的记录”优于“再跑一遍完全相同且无复核目的的实验”；“承认证据不足”优于“给出无依据的确定原因”。

两种有效方案可能存在成本与覆盖差异，偏好必须说明依据。不能只因为一种路径最终碰巧找到答案，就认定它在当时必然更好。

偏好训练可作为可选阶段。监督微调已经达到要求，或偏好标注不可靠时，没有必要为了完整技术路线强行增加这一阶段。

### 19.7 模型训练与系统修改的边界

| 表现 | 优先处理方式 |
| --- | --- |
| 环境实际没有恢复，却被标记为就绪 | 修复执行和复核机制 |
| 计划中的最新条件没有进入模型输入 | 修复状态和上下文组织 |
| 历史资料版本错误 | 更新资料及过滤规则 |
| 指标计算错误或分母不一致 | 修复计算与数据定义 |
| 信息完整时仍反复遗漏对照、无视反证 | 改进提示与示范，必要时微调 |
| 总是过早确认原因，且正确示范不足 | 增加证据分层示范，必要时做偏好训练 |

### 19.8 怎样决定是否采用新模型

对比原模型、改进提示后的模型、监督微调模型和可选偏好训练模型，固定工具、资料、实验环境、预算和评测任务。

同时检查调查质量、实验成本、人工投入和按需测试能力。报告中更谨慎但总是交接，或更积极但安排大量无效实验，都不一定代表改善。

训练数据和最终测试按原始故障、实验模板、版本或任务来源分组隔离。不能把同一个故障换几个名字后分别放进训练与测试。

## 20. 评测体系：证明调查有用，而不只是回答合理

### 20.1 新增评测任务应覆盖哪些情况

| 任务类型 | 应检验的能力 |
| --- | --- |
| 描述模糊但资料可查 | 先查询已有信息，再问真正缺失的内容 |
| 多条件共同触发 | 能发现和验证组合，避免直接归因单个因素 |
| 偶发异常 | 安排合理复核，正确表达未观察到的含义 |
| 环境或工具故障 | 区分无效实验与产品异常 |
| 多种解释都成立 | 设计区分实验，不只列出可能性 |
| 新证据反对原假设 | 修正方向并保留反证 |
| 复现步骤冗长 | 简化后仍可在新运行中复现同类异常 |
| 缺少关键能力 | 识别边界，提出明确交接 |
| 修复带来其他影响 | 同时发现原问题改善和新问题 |
| 普通按需测试 | 不过度调查，原有执行质量不退化 |
| 预算或范围变化 | 按最新要求收窄或停止，完成清理 |
| 仿真与现场不同 | 限定结论范围，不冒充完成现场验证 |

### 20.2 怎样评估动态决策

只让模型读取一份完整调查记录并总结，主要测试阅读和报告能力，不能证明它会自主调查。

需要环境能根据真实选择返回对应结果。可以使用可控仿真、带条件的测试环境或经核验的交互式任务。评测答案应记录在独立评测侧，不能提前放进模型上下文。

回放历史记录有价值，但模型走出历史路径时，缺少对应结果就应标为覆盖限制。不能无论模型选什么实验，都返回同一段预设结果，再宣称其调查有效。

### 20.3 核心指标及口径

| 指标 | 建议定义 | 需要同时注意 |
| --- | --- | --- |
| 复现有效性 | 交付方案能否在独立有效运行中触发同类异常 | 同时报告运行条件、有效次数、异常次数和限制 |
| 触发条件验证质量 | 提出的条件是否经过适当对照和复核 | 不能只看是否猜中了评测答案 |
| 简化方案有效性 | 删除部分步骤后，仍满足前提并能复现 | 不要求找到唯一或全局最简方案 |
| 无依据确认比例 | 声称已确认原因但缺少规定证据的任务比例 | 需要明确判定标准和人工抽查 |
| 原因验证质量 | 能否支持、排除或区分合理解释 | 承认无法确认也可能是正确结果 |
| 修复验证覆盖 | 原问题、必要邻近条件及相关影响的检查情况 | 不以用例越多越好，要求相关且有依据 |
| 人工主动投入 | 人实际查询、配置、分析和整理所用时间 | 等待测试或等待修复的时间单列 |
| 人工接手负担 | 介入次数、每次工作量与原因 | 不能通过少问关键问题来虚假降低次数 |
| 实验成本 | 测试运行数、设备占用、计算和存储消耗 | 与质量一起比较，不能只奖励实验少 |
| 任务范围遵守 | 是否保持对象、环境、预算和用户目标 | 调查积极性不能覆盖越界 |
| 环境恢复质量 | 清理是否完成、残留是否明确报告 | 不能仅凭任务结束状态判定 |
| 按需测试保持 | 原测试任务的执行和判定是否退化 | 防止新模型只擅长长调查 |

### 20.4 对照组怎样安排

建议至少保留：现有脚本加人工调查；相同工具下的固定排查流程；未微调 Agent；可选微调 Agent。

对照时尽量统一信息权限、工具能力、预算和任务难度。新增仪表、日志或接口本身带来的收益，应与 LLM 决策带来的收益分别解释。

人工对照需要记录人员经验和熟悉程度。已经做过同一问题的人再次处理可能明显更快，可采用不同任务或合理分配，避免把熟悉度当成系统差异。

### 20.5 不以唯一轨迹作为正确答案

同一问题可能有多种合理调查路径。评测更应检查必要前提、真实证据、实验可比性、结论程度和资源成本。

标准轨迹可以帮助定位明显漏步，但调用顺序与专家不同不应自动判错。反之，完全复制顺序但使用错误对象或无效证据，也不能判成功。

### 20.6 明确本轮任务成功是什么

| 用户目标 | 可接受的成功结果 |
| --- | --- |
| 完成单项测试 | 按规则完成或有依据地说明无法判定，交付记录和恢复状态 |
| 找到复现方法 | 独立运行验证可复现，并清楚说明条件和范围 |
| 缩小问题范围 | 通过有效实验排除部分解释，形成可接手范围 |
| 验证某个原因 | 提供支持、不支持或无法确认的证据结论 |
| 验证修复 | 对照检查原问题和约定的相关影响 |
| 在有限预算内调查 | 充分利用约定资源，交付有依据的进展和缺口 |

达到预算后合理交接可以符合任务要求，但应与完成复现或确认原因分别统计，不能全部混成一个漂亮的“成功率”。

## 21. 成本与收益：重点比较减少的人工主动工作

### 21.1 成本会新增在哪里

模型决策与检索调用、额外对照实验、较多原始证据存储、实验记录和环境一致性建设、调查数据审核、评测环境，以及必要的模型训练。

其中设备占用和重复测试可能比模型调用更昂贵。减少输入文本固然有帮助，但选择有价值的实验往往更影响总体成本。

### 21.2 收益来自哪些人工工作

| 人工工作 | 可以自动承接的部分 |
| --- | --- |
| 理解用户反馈 | 整理已知信息、查询资料、提出关键缺口 |
| 准备实验 | 选择用例、检查条件、填写参数 |
| 推动执行 | 提交任务、等待、采集、恢复、安排后续 |
| 比较结果 | 对齐版本与条件，生成差异记录 |
| 整理复现材料 | 汇总步骤、证据、次数和限制 |
| 准备开发交接 | 查缺补漏，形成一次可接手的问题说明 |
| 验证修复 | 复用场景，选择相关补测，形成对照报告 |

不能简单把“系统运行八小时”算成“节省八个人工小时”。人工本来可能在测试运行时处理其他工作。

### 21.3 建议的成本记录方式

每个任务分别记录：人工主动时间、测试执行时间、排队时间、外部信息等待时间、修复等待时间、设备占用、模型消耗、存储消耗和失败重跑成本。

业务评估时比较“原流程人工与资源成本”和“新流程人工与资源成本”，在测试质量相当或更好的条件下判断是否划算。开发、维护、数据审核和训练投入作为周期性成本另列。

首版不预设节省比例。先用一小批真实、具有代表性的任务取得基线，再报告样本量、任务类型、平均值和差异范围。

### 21.4 控制成本的实际办法

固定轮询和计算不用 LLM；按证据缺口读取资料；日志先解析后按需展开；重复条件先查询历史；高代价实验先检查区分价值；不同调查之间只复用符合权限与适用性要求的证据。

模型可按任务采用不同配置，但不能在未经评测时把重要调查决策随意交给较弱模型。缓存也必须绑定数据与条件版本，不能拿过期结果节省调用。

## 22. 最大的困难，以及各自需要什么解决办法

### 22.1 模型提出的实验看似合理，实际没有区分作用

“再测一下高负载”可能只是重复已经知道的事实。要求每次明确要区分哪些解释、不同结果会怎样影响判断，并通过评测检查实验价值。

系统还需要看到已有实验，才能避免无意义重复。缺少历史查询能力时，单纯要求模型“不要重复”通常不够。

### 22.2 条件实际上不一致，比较却写得很确定

这是数据与执行基础问题。需要快照、实际条件记录、环境恢复、观测覆盖和可比性检查。模型不能靠推理补出从未记录的条件。

优先把可控制的实验室环境做好，通常比一开始支持各种现场环境更容易验证方案。

### 22.3 偶发异常让删减和原因判断变得困难

一次运行没异常，可能只是没有碰到。需要合理重复、独立复核、明确样本限制，并在预算内承认不确定性。

首版可以选择复现相对稳定的故障作为试点，随后逐步覆盖低频问题。不能只用简单故障评测，再宣称已经解决所有偶发异常。

### 22.4 长流程中，模型把早期猜测记成事实

通过假设与事实分开存储、保留反证、记录来源和每次状态变化来控制。上下文摘要也要保留不确定性。

微调可以改善处理方式，但首先要让系统提供正确且足够的上下文。

### 22.5 缺少专家数据，难以证明模型真的会调查

先收集少量高质量完整案例，关注关键分支与错误，而不是先追求大规模。记录专家当时知道什么、为什么选下一步、哪些结果改变了判断。

模拟数据补充覆盖，但真实任务独立评测仍然必要。数据生成得多不等于调查能力强。

### 22.6 自动化做得更多，却没有减少工程师工作

如果每个参数都要审批、报告冗长、复现材料不完整，模型调用再多也可能增加负担。

从人工主动时间、交接质量和有效实验比例评估。优先自动执行范围明确的动作，并把需要人的问题一次整理清楚。

### 22.7 系统始终无法确认最终原因

具体原因常需要内部状态或代码检查。先把可复现、范围清楚、证据齐全作为可交付目标，原因确认程度如实表达。

这并不妨碍产生显著价值：工程师从稳定复现和明确范围开始工作，通常比从一句模糊反馈开始更有准备。价值大小仍需实测。

## 23. 分阶段改造：每一步都能独立验证价值

### 23.1 阶段零：建立基线和记录基础

保持原执行流程，选定少量代表性异常，记录人工从反馈到复现材料的实际过程与耗时。梳理现有工具支持什么、能读什么、能改什么、能否恢复。

增加调查、实验和运行的关联记录，形成统一异常识别方式。此阶段模型可以辅助整理历史材料，但不应据此宣称已实现自主调查。

**阶段验收：一项异常的关键条件、运行、证据和人工投入能够完整追溯。**

### 23.2 阶段一：原测试失败后，自动补做有限对照

限定一种场景，例如实验环境中的切换异常。测试失败后，系统先检查前提和观测，再在允许范围内选择少量对照，生成阶段调查材料。

先不支持任意脚本生成、不修改产品代码、不承诺确认具体缺陷。保留普通按需测试原流程。

**阶段验收：在相同质量要求下，能减少人工组织补测与整理材料的工作，并且成本可控。**

### 23.3 阶段二：支持反馈驱动的多轮调查与步骤简化

根据上一轮证据选择下一轮，保存原因假设及反证，允许返回前一阶段，支持逐步删减并独立复核简化方案。

加入实验预算、无进展判断、条件适用性检查和中途要求更新。

**阶段验收：能在未见过的同类任务中，通过合理实验找到或缩小触发条件，交付可接手的复现材料。**

### 23.4 阶段三：原因验证与修复检查

扩展必要的内部观测或经允许的控制能力，完善原因确认标准；支持修复版本登记、原问题对照、相关条件和副作用检查。

**阶段验收：能够区分“怀疑原因”“实验支持”和“明确确认”，并发现已设计的修复无效或副作用案例。**

### 23.5 阶段四：按数据决定是否微调和扩大范围

收集前几阶段的模型决策错误和专家修正。先完善提示、工具和状态，再按评测决定是否训练。

逐步增加设备、故障类型、现场环境或独立分析角色。每增加一类能力，都保留原有任务回归检查和资源成本评估。

**阶段验收：扩大范围或训练后，整体质量与人工投入确有改善，原按需测试没有明显退化。**

### 23.6 推荐的第一版范围

| 建议先做 | 建议暂缓 |
| --- | --- |
| 一种明确业务场景、已登记工具、实验环境 | 全网、全设备、任意现场异常 |
| 用户直接报异常和测试失败转调查两个入口 | 自动受理所有运行告警并无限调查 |
| 条件明确的少量对照与复核 | 大规模无目的参数穷举 |
| 调查记录、证据、复现材料和交接 | 保证定位到代码行并自动修复上线 |
| 简单预算和可追溯停止规则 | 一开始构建复杂的多角色系统 |
| 原模型与改进提示对照评测 | 未评估需求就开展大规模训练 |

## 25. 实施前后的交付物与检查清单

### 25.1 设计阶段应明确的交付物

双入口流程；六阶段调查规则；任务与实验记录定义；工具能力清单；异常识别和实验有效性规则；预算与人工接手规则；结果与原因确认标准；评测集及人工基线方案。

### 25.2 第一版应能拿出来展示的材料

1. 一条普通按需测试，从请求到报告的完整记录。
2. 一条直接描述异常，从信息整理到复现材料的完整记录。
3. 一条测试失败后进入调查的完整记录。
4. 一条出现反证后调整方向的记录。
5. 一条数据不足或能力受限时，明确交接的记录。
6. 一条简化步骤后在新运行中复现的记录。
7. 一条取得修复版本后，比较原问题与相关影响的记录。
8. 一份与原流程比较人工时间、成本和结论质量的评测报告。

模拟演示和真实工具演示分别标注。只用模拟跑通流程，可以证明业务状态和交互设计，不等于证明现场调查有效。

### 25.3 业务与实验质量检查

- 是否支持按需测试正常结束，而不强制进入调查？
- 是否明确本轮只复现、缩小范围，还是验证原因？
- 每组实验是否有具体问题和结果解释方式？
- 是否区分目标条件和实际条件？
- 是否能查到每个结论对应的原始证据？
- 是否保存不支持当前解释的有效结果？
- 简化步骤后，是否仍满足前提并保留必要观测？
- 是否在新的有效运行中检查复现方案？
- 修复验证是否保持适用条件与原判定规则？
- 未覆盖范围和无法确认的原因是否明确表达？

### 25.4 系统与操作检查

- 调查、实验、运行和证据的归属是否清楚？
- 重复提交与真正的重复运行是否区分？
- 取消、恢复、中途修改和迟到结果是否能正确处理？
- 共享资源上的实验是否会相互干扰？
- 正常、失败、取消后是否都完成规定收尾？
- 达到整体调查预算后是否停止新增实验？
- 等待修复是否保存记录并释放不必要的资源？
- 外部资料是否只能提供信息，不能改变执行权限？
- 原按需测试能力是否通过回归评测？

## 26. 对外怎样解释新系统

### 26.1 项目的一句话定位

这是一个支持按需测试和异常调查的测试助手：既能执行明确测试，也能根据每轮结果安排后续实验，帮助复现问题、缩小范围和检查修复。

### 26.2 一段完整讲述

我们原来已经有脚本完成大量测试，但测试失败后，工程师仍要手动改条件、重跑、找日志和整理复现材料。

现在保留原来的按需测试能力，同时让 Agent 接手这段调查工作。例如，用户反馈升级后移动视频偶尔卡顿，系统先整理现场条件，再用现有工具比较新旧版本、负载和动作序列。根据结果逐步找到触发条件，删掉无关步骤，交付经过验证的复现方法。

之后它继续收集能区分原因的证据，交给开发人员确认具体缺陷；修复版本到达后，再检查原问题和相关业务影响。LLM 负责理解材料、组织实验和调整方向，脚本负责具体动作，程序负责计算、规则和权限检查。

项目价值通过人工主动投入、复现材料质量、调查效果和实验成本衡量，具体收益以实测为准。

### 26.3 常见追问怎样回答

| 追问 | 推荐回答 |
| --- | --- |
| 脚本不是已经能完成吗？ | 脚本继续完成每项动作，Agent 接手原本由人决定后续实验和整理证据的部分；稳定路线仍用固定流程。 |
| 为什么需要 LLM？ | 输入包含模糊反馈、多种材料和不断变化的结果，需要把信息转成下一步调查；价值用对照实验验证。 |
| 能直接找到根因吗？ | 可以复现、缩小范围并验证候选解释；具体代码缺陷取决于观测与开发侧确认能力。 |
| 最大困难是什么？ | 保证多轮实验条件可信、证据可比，并让模型根据反证更新计划，而不是过早下结论。 |
| 为什么要微调？ | 只有在工具、状态和提示完善后，模型仍持续犯调查决策错误时，才用专家记录训练；不把微调设为前提。 |
| 怎么保证不是模型编的？ | 关键数据来自工具记录，结论引用原始证据，测试判定按规则执行，原因程度单独标注并检查。 |
| 怎么减少人工？ | 自动查询、配置、运行、等待、比较和准备复现材料，人集中处理缺失事实、重要决定和具体修复。 |
| 无法复现怎么办？ | 交付已尝试条件和证据缺口，明确未复现范围；必要时补资料或交接，不宣称问题不存在。 |

## 27. 容易夸大的说法与更准确的表述

| 容易夸大的说法 | 更准确的表述 |
| --- | --- |
| Agent 能自动解决所有测试问题 | 在已支持工具、允许范围和预算内推进调查，必要时明确交接 |
| 用了 LLM，所以不需要 SOP | 固定步骤继续标准化，LLM 处理变化的描述与调查分支 |
| 日志报超时，所以根因就是等待时间太短 | 超时是观测事件，需要区分原因与后果并验证解释 |
| 一次没复现，说明这个条件无关 | 在本次有效运行中未观察到，需要结合重复和样本范围判断 |
| 找到了最小复现 | 找到了当前经过删减和独立验证的简化复现方案 |
| 新版本失败、旧版本正常，所以已经确定软件缺陷 | 在可比实验下存在版本差异，仍需检查其他差异与具体机制 |
| 修复后通过一次，说明彻底解决 | 在说明的条件与运行范围内完成验证，仍报告覆盖和限制 |
| 模型自信，原因就可以发布为确定 | 原因确认依据预先规定的证据标准 |
| 专家点了通过，模型就学会了 | 专家反馈先形成记录，审核后用于离线训练与发布 |
| 系统跑了多久，就节省多少人工时间 | 分开统计人工主动时间、自动执行和外部等待 |
| 新系统一定要更大模型或更多 Agent | 先用现有模型和单一调查决策流程，以评测决定是否扩展 |
| 文档有这个工具，所以现场能力已经具备 | 文档设计、教学演示、真实工具接入与生产效果分别核实 |

## 附录 B：最终交接材料示例

以下为示例措辞，假设已完成相应独立验证；真实报告只能写入实际取得的结果。

**调查对象：**指定新版本下的移动视频业务异常。

**本轮目标：**形成可重复的复现方案，缩小调查范围，暂不承担具体代码修复。

**已完成工作：**整理反馈与配置，在相同准备条件下比较版本、负载和动作序列；对候选触发组合进行独立复核；删减无关背景业务和等待步骤。

**当前复现方法：**加载记录中的版本和配置，准备规定负载，启动业务监测，按保存的路径与间隔连续切换，检查同一业务异常规则，收集关联记录并恢复环境。完整参数与次数见实验附件。

**当前范围：**在已测条件下，新版本的规定负载与连续切换组合能够重复触发同类异常；对照组结果与未覆盖条件分别列出。结论不外推到全部设备、负载和现场环境。

**原因状态：**发现与资源处理相关的候选线索，尚未完成具体缺陷确认；支持与反对证据见关联记录。

**需要开发侧完成：**核查指定时间窗口的内部状态与相关实现，确认候选解释；如交付修复版本，注明版本身份及修改范围。

**后续验证：**在同一复现条件和规则下对照异常版本、修复版本；补测相关邻近条件，并检查业务停顿、响应时间和资源表现。

**环境状态与成本：**按真实恢复结果和消耗填写，存在残留、恢复失败或数据缺口时明确列出。
