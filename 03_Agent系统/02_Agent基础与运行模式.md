# Agent 是怎样一步一步工作的

## 一、直观理解

主线定位：解释外层决策和内层执行怎样构成循环，以及何时停止。完整链路见 [系统运行全流程与交互拓扑](18_系统运行全流程与交互拓扑.md)。

用户说“升级后视频偶尔卡，帮我查查”，模型不会凭这句话就知道原因。它需要先取信息，安排测试，看到结果以后再决定下一步。

### 一轮工作其实很简单

以比较新旧版本为例：

1. 程序把用户要求、当前条件和已经知道的结果交给模型。
2. 模型提出：“先在相同条件下测旧版本，判断是否只有新版本异常。”
3. 程序检查这项测试能不能做，设备是否可用，参数是否正确。
4. 现有脚本执行，平台返回真实结果。
5. 程序保存结果，再交给模型。
6. 模型据此决定：继续比较负载、补查日志，还是已经可以给用户报告。

反复进行这几步，就是这里所说的 Agent 工作过程。

模型说“准备测试”不代表已经执行。只有工具真正返回了结果，系统才能说这次测试做过了。

### 为什么要把“跑测试”和“查问题”分开

跑一次测试时，步骤通常很明确：准备环境、启动监测、执行动作、收集数据、恢复环境。这些适合写成固定程序。

查问题时，下一步可能还不知道。新旧版本都失败，就可能要先检查共同环境；只有新版本失败，才更值得追版本差异。

所以，可以让外面的一层决定“下一组测什么”，里面的一层负责“把这一组测好”。原来的脚本继续使用，新增的是根据结果安排后续工作的能力。

普通按需测试只需要里面这一层。用户指定了要测什么，执行并报告即可。

### 每轮都要把哪些事告诉模型

最重要的是：用户到底想查到什么程度，最新测试条件是什么，已经做过哪些比较，哪些结果不支持当前猜测，还缺什么记录，以及最多还能跑多久、跑几次。

例如：

> “用户只要求复现。新版本高负载连续切换出现过异常，单次切换暂未出现；两组的实际负载是否一致还没检查。”

有了这些信息，模型才可能选择先核对负载，而不是直接宣布“连续切换有问题”。

完整日志可以放在文件里。先给模型相关摘要和文件位置，需要时再读细节。

### 哪些步骤不用模型参与

等待测试完成、计算成功率、比较明确门限、确认设备是否被别的任务占用，这些都由程序处理。

如果一个已知故障的排查方法已经固定，也可以直接用现成流程。模型主要负责那些需要读材料、理解新情况、选择路线的地方。

这样既便宜，也更容易检查对不对。

### 什么时候停下来

达到用户要求就可以停。用户只要复现方法，就不必继续查代码原因。

如果关键日志拿不到、工具做不了必要实验，或者已经用完约定次数，就把当前知道的内容整理出来，说明下一步需要谁做什么。

等待开发提供修复版时，保存记录即可，不需要让模型一直生成，也不需要无故占着测试设备。

### 是否需要多个 Agent

第一版一个负责安排调查的 Agent 就够了。多组互不影响的测试，可以由后台程序同时运行，不必每组再放一个模型。

以后如果不同类型日志的分析确实可以独立进行，再考虑分开。分工以后，各部分仍要使用同一份设备信息、版本和测试记录，否则很容易各说各的。

### 怎样把专家经验用起来

把常见问题的处理办法整理成说明，例如“移动视频卡顿先查哪些记录、哪些结果值得比较”。模型遇到适合的任务时读取，再根据本次结果调整。

成熟的步骤可以逐渐写成脚本。系统越成熟，重复工作反而越应该交给普通程序。

工具如何调用，见 [消息与调用](03_Function-Calling与消息协议.md)；要记住哪些信息，见 [记忆与任务记录](05_记忆与上下文管理.md)。

## 二、详细技术拆解

### 控制循环中保存什么

把第 t 轮已经确认的状态记为 `S_t`，模型提出的计划记为 `A_t`，工具实际结果记为 `O_t`。程序执行的是：

```text
A_t = planner(S_t)
通过检查后：O_t = executor(A_t)
S_(t+1) = 保存真实结果并更新当前判断(S_t, A_t, O_t)
```

这里的状态不是模型隐藏的思考过程，而是程序能检查的任务类型、条件、实验摘要、假设、预算与停止依据。`reason` 只需说明可核查的决策理由，例如“旧版本也异常，因此先检查共同环境”。

可以把决策输出限定为 `EXPERIMENT`、`REPORT`、`HANDOFF`、`WAIT`，分别表示提出一组实验、请求交付、请求交接和等待。前三类用于推进或交付，WAIT 让业务状态记录等待原因并结束本轮调度。即使模型选择报告，程序仍检查任务是否真的完成：调查尚无独立复核，就不能登记为成功复现。

### ReAct、预先规划和反思怎样用于本项目

| 方法 | 通俗含义 | 在当前系统怎样落地 |
| --- | --- | --- |
| ReAct | 做一步，看结果，再决定 | 每次只提交一组 `ExperimentPlan`，运行后再选择 |
| Plan-and-Execute | 先安排，再执行 | 可以先列调查路线，但每组执行前重查条件；不一次下发全部探索动作 |
| Reflection | 检查刚才判断哪里不成立 | 读到反证后修订假设，并保存修改理由 |
| 多分支搜索 | 同时考虑多个解释 | 先列候选解释，挑能区分它们的比较；不要求首版建立思维树 |

这些是设计方式，不是装上一个框架就自动得到的能力。学习时可以先用规则计划器，再换 LLM。二者共用记录和执行检查，便于比较模型是否带来额外收益。

### 一次 `step()` 应怎样设计

任务服务先读取 READY 任务，记住 `task_version` 和 `plan_version`，再在事务外调用计划器。这样模型等待不会长期持有数据库锁。

计划返回后，服务重新加锁读取任务。如果用户已经修改或暂停，就不提交旧计划；否则校验计划、预留运行次数、登记实验和执行前快照，然后释放锁执行。

每次运行结束写回真实 `RunRecord`，在下一次运行前再次检查任务状态和计划版本。实验完成后计算摘要、更新复现或假设，再回到 READY，或进入错误、暂停、取消、完成、交接状态。

这就是“外层灵活，内层固定”的具体实现方式。可以用普通 Python 服务写出循环，也可以用 LangGraph 表达节点与返回分支；框架不改变这些业务约束。

### 单 Agent、并发执行和多 Agent 的区别

一个模型可以安排多组实验；后台并发执行不等于多个 Agent。只有确实需要独立模型上下文、独立职责和结果汇合时，才是多 Agent 协作。

例如，协议日志和业务服务日志可以独立分析，但汇合时必须对齐 `run_id`、终端标识、时间窗和时钟误差。分析者返回证据引用与不确定性，最终结论仍经过同一任务规则检查。首版先使用单 Agent，能更清楚地观察每次决策的依据。

### 哪些等待不属于模型循环

测试排队、等设备、等资料和等修复都应保存原因并返回控制权，事件到来后再推进。模型上下文窗口、业务状态存储和后台调度是三件事：上下文装不下可以按需检索，数据库保存状态，调度器负责何时继续。

等待任务不会自动释放常驻推理服务的显存；避免长模型请求，是减少无效计算和连接占用，不能据此宣称 GPU 已卸载。
