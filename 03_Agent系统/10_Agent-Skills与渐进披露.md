# 怎样把专家排查方法写成 Skill

## 一、直观理解

主线定位：把适用的专家方法读入模型上下文，指导本轮实验选择。完整链路见 [系统运行全流程与交互拓扑](18_系统运行全流程与交互拓扑.md)。

这里的 Skill，可以先理解成一份给 Agent 看的工作说明。

例如，专家知道查“移动视频卡顿”通常要先确认哪些信息、看哪些记录、怎样区分设备和服务问题。把这些经验写清楚，模型遇到合适任务时再读，就不必每次从零开始。

### 一份说明应该写什么

先写适合什么问题，以及什么情况下不适用。

然后写需要哪些信息和工具、常见的几种解释、建议比较什么、怎样看结果、什么时候需要停下来找人。

最后给出报告应该包含什么，并附上资料来源和版本。

它不应只写“先读日志，再找根因”。更实用的写法是：

> “如果设备切换记录正常，但业务发生停顿，核对是否同一终端、同一时间；再检查业务恢复是否晚于设备连接完成。”

### 为什么不要一次把所有说明都塞给模型

设备、故障和版本多了，说明会越来越长。全部放进去，既花钱，也容易用错。

可以先给一个简短目录。模型发现当前问题适合“移动业务异常”这一项，再读取正文，需要时继续查相关资料。

这就是按需加载。原来叫“渐进披露”，在这里实际做的就是先看目录，再读相关部分。

### 可以先整理哪些说明

先选最常用的几种：普通测试准备、移动业务异常、偶发问题复核、复现步骤简化、原因检查、修复验证。

一项调查可能先用复现说明，后用简化说明，等修复来了再用验证说明。不需要每份说明都配一个独立 Agent。

如果某段步骤已经完全固定，也可以写进程序，直接执行。

### 说明、资料和工具怎么配合

说明告诉模型怎样开展工作；资料提供事实、规则和历史记录；工具负责真的查询和操作。

写了“运行测试”不代表获得运行权限。说明中附带脚本，也不表示脚本可以直接执行，仍需按应用规则检查。

用户只要求读报告时，模型不能因为读到一份排查说明，就自行启动测试。

### 读了说明，也要根据结果调整

历史方法是参考。当前结果不支持原来的猜测，就换方向；设备版本不适用，就找其他办法。

例如以前的卡顿由资源问题引起，这次仍要检查本次记录，不能照抄原因。说明里最好写出哪些情况会否定原来的方向。

### 文档怎样保存

可以用 SKILL.md 保存正文，旁边放参考资料、例子和已经验证的脚本。实际宿主是否自动发现和加载，需要实现时确认。

记录每份说明的版本、来源和适用设备。修改时保留原因，已开始的调查也记下当时读的是哪一版。

从外部取得说明时先审查。里面的文字不能要求跳过权限、隐藏失败结果或删除不符合猜测的数据。

### 怎么知道这些说明有帮助

让模型分别在没有说明、只有资料检索、有说明三种条件下处理相近任务。

看实验安排有没有更合理，追问和人工接手有没有减少，是否仍能识别不适用情况。输入变短只是附带收益，不能为了省内容删掉关键要求。

第一版少写几份、认真验证，通常比一下建一个庞大目录更容易检查效果。

具体实验怎样安排，见 [复现与实验](12_异常复现与实验设计.md)；资料怎样管理，见 [知识库](16_知识库与经验沉淀.md)。

## 二、详细技术拆解

### Skill、RAG、工具与工作流怎样分工

| 组成 | 解决什么 | 移动视频卡顿的例子 |
| --- | --- | --- |
| Skill | 遇到这类问题怎样开展工作 | 先核对业务观测，再比较版本与连续动作 |
| RAG | 取回当前需要的资料 | 检索适用版本说明和历史缺陷 |
| Tool | 提供可执行能力 | 启动监测、跑仿真、取日志 |
| Workflow | 保证固定步骤和状态 | 监测就绪后才执行，异常也进入收尾 |

一份 Skill 可以调用 RAG 工具，也可以指导选择实验；固定流程仍由程序强制执行。不能把一个 Python 类、一个复合函数和一个文件式 Skill 都叫成同一种机制。

### 文件结构与正文示例

文件式 Skill 至少含 `SKILL.md`，可附带参考资料、脚本和资源。名称、描述用于发现，正文用于指导实际任务。[Agent Skills 格式规范](https://agentskills.io/specification)

```text
mobility-outage-investigation/
  SKILL.md
  references/
    observation-rules.md
    example-investigations.md
  scripts/
    summarize_events.py
  assets/
    reproduction-report.md
```

下面是拟议 Skill 正文的教学示例，不表示把本页写成 Markdown 就已经接入宿主：

~~~markdown
---
name: mobility-outage-investigation
description: 调查移动或连续切换期间的业务停顿，适用于有业务监测与实验执行能力的实验室任务。
---

# 移动业务停顿调查

先读取当前任务目标、固定条件、已完成实验和剩余预算。
确认业务观测能覆盖动作前后，并记录同类异常的判断规则。

如果只有新版本记录，优先考虑同条件旧版本对照。
如果多个条件同时变化，先把结果当作初筛线索，再安排可区分解释的对照。
找到可复现场景后，逐项简化并使用新的运行独立复核。

低负载也出现同类异常时，修订“高负载是必要条件”的假设。
缺少内部状态时，交付复现与日志线索，不确认代码原因。
达到用户目标或预算边界时，整理材料并停止新增实验。

需要具体观测定义时，再读 references/observation-rules.md。
输出包含条件、步骤、有效运行数、异常数、证据、限制和恢复状态。
~~~

实用的 Skill 不只列正向步骤，还写何时不适用、什么结果会否定当前方向，以及达到什么条件应交付或交接。

### 渐进披露的实际调用过程

宿主先扫描元数据，向模型提供可用方法目录。命中“移动业务停顿”后读取正文；需要具体判定方法时，再读对应参考文件，而不是一开始加载全部历史案例。

正文可以要求按编号取证据，读取失败时应说明缺什么。只有路径没有真正读取内容，不能声称已经按该参考完成判断。

触发方式、缓存与压缩行为由宿主决定。不能统一假设 Skill 执行后自动从上下文消失，也不能把所有 Skill 等同于一个斜杠命令。

### 版本、适用范围与上下文预算

登记 `skill_id`、内容版本或哈希、适用设备与版本、依赖工具及资料来源，任务记录本次实际加载版本。新任务使用更新版本，旧任务需要升级时保存变更原因。

只加载当前阶段相关内容：复现阶段用复现方法，修复阶段再取验证方法。大日志先用程序提事件与窗口，长参考资料通过标题和关键词定位，不能仅靠增加上下文长度解决信息过载。

附带脚本按工具能力处理。说明文档不自动赋予文件、网络或设备权限；运行结果也应引用到实际任务。外部 Skill 中要求隐藏失败或忽略当前约束的文字不能成为新的授权来源。

### 如何验证 Skill 真有帮助

保持模型、工具与任务基本一致，分别测试无 Skill、仅资料检索、加入 Skill 三种条件。比较有效实验比例、约束保持、合理反证处理、人工接手和资源开销。

同时安排“不适用”样本：换设备版本、缺关键监测、用户只读。好的方法说明应帮助模型识别这些边界，而不是让所有任务沿同一套路继续执行。
