# 一句话怎样变成一次工具调用

## 一、直观理解

主线定位：连接模型候选与实际工具调用，明确消息、编号和结果如何对应。完整链路见 [系统运行全流程与交互拓扑](18_系统运行全流程与交互拓扑.md)。

用户说：

> “帮我比较新旧版本，看看是不是升级后才出现卡顿。”

模型不能自己去操作设备。它要先告诉程序想调用哪个工具、传什么参数。程序检查以后，才真正调用测试平台。

这种“模型提出工具名和参数”的做法，就是 Function Calling，也就是工具调用。

### 先看一次完整过程

模型知道要做版本比较以后，先请求查询可用测试用例。查询工具返回实际用例编号和使用条件。

模型选择其中一个，提出新旧版本的测试计划。程序检查设备、配置、监测和允许次数，登记这组测试。

随后程序调用执行工具。测试平台返回任务编号，表示已经排队。程序继续等待，直到平台报告执行结束，再采集数据、恢复环境。

最后，模型看到真实结果，才决定继续查什么或怎样给用户解释。

这里最容易混淆的是：**提交成功，只说明平台收到了任务；执行结束，也不一定说明产品测试通过。**

### 用户的每条消息都从同一个地方进来

新建测试、修改要求、查询进度和取消任务，都可以使用同一个消息接口。

收到消息时，至少要知道消息内容、当前聊天、可能关联的任务，以及是否带了附件。程序还要确认是谁发的、能访问哪个项目。

同一条消息因为网络原因发送两次，不能启动两份测试。因此每条消息需要一个编号，用于判断是否已经处理。

用户在消息里写“我是管理员”，不能代替真实登录权限。

### 为什么需要好几种编号

它们分别回答不同问题：

| 编号 | 表示什么 |
| --- | --- |
| task_id | 用户安排的一项工作 |
| issue_id | 正在调查的一个异常问题 |
| test_case_id | 一条测试用例 |
| experiment_id | 为回答一个问题安排的一组测试 |
| run_id | 一次实际运行 |
| session_id | 外部平台返回的任务编号 |
| tool_call_id | 模型这次调用和工具回复的对应编号 |
| evidence_id | 一份日志、样本或计算结果 |

例如，调查“移动视频卡顿”可能包含新旧版本比较、高低负载比较等多组测试。每组又会重复运行。因此不能只用一个聊天编号把所有结果混在一起。

这些编号由程序和实际工具生成。模型使用已经得到的编号，不能随便编一个。

### 工具返回时，要把事情说清楚

一次执行工具最好能告诉程序：有没有接受请求，现在是在排队还是运行，实际使用了什么参数，结果到哪里查询。

执行失败也要说明：动作有没有发生，能不能重试，需不需要先查状态。

例如，提交请求超时了，平台可能已经开始执行。程序应先用本次运行编号查平台，不能马上再提交一次。

常规等待和轮询由程序完成，不需要每隔几秒问模型“现在怎么办”。

### 用户中途改要求怎么办

用户说“目标改成 C 到 D”，程序保存新要求，并给计划增加一个版本号。

旧测试如果稍后才返回，仍然记在旧计划里。它可以作为历史资料，但不能直接用于判断 C 到 D。

模型正在写的新计划，如果基于旧要求，也要在执行前拦下来重新检查。这样可以避免文字里已经改了，后台却还按旧条件跑。

### 暂停和取消也要等真实状态

暂停时先不安排新测试，当前动作按可行方式暂停或结束。取消时通知平台停止，再查询是否真的停下。

如果动作不能撤销，就说明已经发生了什么。测试停止以后，还要检查测试流量、监测和配置是否需要恢复。

不能因为模型回复了“已停止”，就认为设备已经恢复好了。

## 二、详细技术拆解

### 给实现者：接口可以先保持简单

可以用 POST /tasks/messages 接收用户消息，包含 message_id、conversation_id、text、附件和可选的 target_task_id。修改已有任务时，可带 expected_task_version，检查用户操作的是否仍是当前版本。

这只是建议的项目接口。外部测试平台的回调另行验证，不能让普通用户伪造一条“执行完成”。

模型接口的具体消息格式，由实际使用的模型服务适配。无论用哪家接口，都应保留每次请求与回复的对应关系，避免把甲任务的返回接到乙任务上。

工具需要提供哪些信息，见 [工具设计](04_工具设计与完整调用示例.md)；消息怎样理解，见 [统一入口](11_统一入口与意图识别.md)。

### 工具定义、调用请求与返回消息

以下采用常见的消息式工具接口讲解。它是一种接口适配示例，不要求当前系统绑定某一家模型服务。工具的 Python 实现留在应用端，模型看到的是名称、描述和参数约束。

先向模型提供查询工具的定义：

```json
{
  "type": "function",
  "function": {
    "name": "Test_Case_Query",
    "description": "查询适用于指定现象和频段的已登记用例，返回编号、前置条件和规则来源。不提交测试。",
    "parameters": {
      "type": "object",
      "properties": {
        "scenario": {"type": "string", "description": "要验证的现象，如移动业务停顿"},
        "band": {"type": "string", "description": "已确认频段，如 n78"}
      },
      "required": ["scenario", "band"],
      "additionalProperties": false
    }
  }
}
```

模型据此生成调用请求。下面的编号均为教学示例：

```json
{
  "role": "assistant",
  "content": null,
  "tool_calls": [
    {
      "id": "call-query-01",
      "type": "function",
      "function": {
        "name": "Test_Case_Query",
        "arguments": "{\"scenario\":\"移动业务停顿\",\"band\":\"n78\"}"
      }
    }
  ]
}
```

应用解析 `arguments`，检查工具是否注册、参数是否合法、用户是否可访问对应资料，才运行查询。随后把真实返回加到历史：

```json
{
  "role": "tool",
  "tool_call_id": "call-query-01",
  "content": "{\"status\":\"completed\",\"cases\":[{\"test_case_id\":\"TC-MOB-01\",\"rule_id\":\"BUSINESS-R1\",\"requires\":[\"business_monitor\",\"device_ready\"]}]}"
}
```

模型下一次调用时，同时看到先前请求和对应结果，才能使用 `TC-MOB-01`。在这个消息接口中，`arguments` 是 JSON 字符串；解析后才是对象。不能把流式返回中的半段参数交给执行器。

调用消息中的 `tool_call_id` 与业务的 `run_id` 不是同一个东西。一次“提交运行”与后续“查询状态”有不同调用 ID，却指向同一运行。其他模型协议可能使用不同消息结构，应由适配层转换，不能直接混用字段。

### 结构化输出与 Function Calling 的区别

Function Calling 表达“调用哪个工具”；结构化输出表达“返回符合约定的对象”。两者都可以借助 schema，但业务语义不同。

当前系统适合让模型返回两类结构：入口返回 `IntentDecision`，调查返回 `PlanDecision`。应用拿到 `EXPERIMENT` 后登记实验，再由固定流程调用脚本。也可以把“提出实验”封装成一个工具，但不能因模型选择了它就跳过计划检查。

因此有两种合理组织方式：

| 方式 | 模型输出 | 应用职责 | 适用情况 |
| --- | --- | --- | --- |
| 工具循环 | 查询、读日志等工具调用 | 执行并回传每次结果 | 需要按需取资料与证据 |
| 计划循环 | 下一组实验或交付决定 | 校验计划并执行固定工作流 | 长测试、需要严格管理资源与收尾 |

当前系统可以组合两者：模型先用只读工具补材料，再返回实验计划；动作执行由实验服务管理。schema 合法只证明结构可解析，不能证明用例适用、对照公平或动作有权限。

### 消息入口与并发修改的契约

教学接口可以这样设计：

```json
{
  "message_id": "msg-104",
  "conversation_id": "conv-01",
  "target_task_id": "task-01",
  "expected_task_version": 7,
  "text": "带宽改为40 MHz，其他不变",
  "attachments": []
}
```

身份和项目范围来自登录上下文，不能信任用户提交一个 `user_id` 就当作已授权。附件只传经过检查的引用，正文与日志都作为外部数据处理。

建议按“项目、会话、消息编号”保存去重记录。同一编号同一内容返回已处理结果；同一编号不同内容返回冲突。任务版本检查用于防止旧页面或旧模型结果覆盖新要求。

处理顺序是：读取任务版本 → 解释消息 → 重新检查版本 → 原子保存修改和消息处理结果。数据库事务中不要等待一次漫长模型生成。

### 外部执行结果怎样接回来

平台通知是另一类事件，至少包含 `event_id`、`run_id`、`session_id`、状态、发生时间和结果引用。接入层校验来源，再按事件 ID 去重；状态必须符合允许的流转。

迟到的完成事件写回所属运行，即使该运行已经属于旧计划，也不删除。当前报告只选择适用版本的结果，必要时再显式引用历史对照。

传输超时应返回可处理的错误，例如：

```json
{
  "code": "SUBMIT_STATUS_UNKNOWN",
  "run_id": "run-01",
  "side_effect": "unknown",
  "retryable": false,
  "next_action": "query_by_run_id"
}
```

这里的 `retryable=false` 指不能盲目重新提交动作；仍可以查询状态。网络重试、模型重试和业务上的另一次重复测试，必须分别设计。
