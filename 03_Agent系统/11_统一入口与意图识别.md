# 同一个入口，怎样听懂用户要做什么

## 一、直观理解

主线定位：把用户原话转成创建、修改、查询或控制候选，由任务服务采用合法变更。完整链路见 [系统运行全流程与交互拓扑](18_系统运行全流程与交互拓扑.md)。

可以把入口统一。用户只管描述要求，不需要先选择“测试”“调查”或“验证修复”。

系统收到一句话，先弄清两件事：**用户在说哪件事，现在想让我做什么。** 这一步就是意图识别。

### 先看几个具体例子

用户说：

> “帮我测一下这个版本的下载速度。”

系统就准备一项测试。先查设备、版本、用例和判断标准，信息够了就运行。

用户说：

> “升级后移动视频卡住，帮我查一下。”

系统要开始排查。先整理现象，再设计能重现问题的测试。

用户说：

> “这是修复版，按上次的方法再验证。”

系统要找到上次的问题和复现步骤，核对这次实际加载的版本，再开始验证。

这三种工作可以由同一个入口接收，只是后面的步骤不同。

### 还要听懂用户是在修改现有任务

下面几句话都不应该被当成新任务：

> “带宽改小，其他不变。”

表示修改当前测试。系统要保留设备、版本、环境等没被修改的要求，重新检查哪些旧结果还能用。

> “现在查到哪里了？”

表示查看进度。读已有记录回答即可，不能顺手再启动测试。

> “先别跑了，给我已有结果。”

表示停止安排新测试，再整理当前结果。已经提交的操作要查询状态，不能只停止回答文字，让后台继续跑。

> “继续上次的。”

表示恢复。先找到对应任务，检查设备、参数和剩余次数，再接着做。如果有几项任务都可能是“上次”，就需要确认。

### 一句话也可能包含先后关系

“先测，失败再查”不是同时执行测试和调查。系统应先测，确实失败后，再按用户允许的范围继续。

“先给我上次报告，再验证修复版”包含两件事，要按顺序处理。

“只看看日志，别跑测试”则明确限制了操作。即使模型认为补测有帮助，也只能先说明建议，不能直接运行。

### 缺信息时，哪些该问，哪些不用问

能自己查的先查。例如设备当前版本、已有配置和上次报告，通常不该再让用户抄一遍。

查不到但必须知道的才问。例如同名设备有两台，必须明确到底是哪一台。

用户本来就不知道的信息，可以变成探索条件。例如用户不清楚卡顿时负载多高，就在允许范围内比较普通和高负载，而不是卡在“请提供准确负载”这一步。

使用默认配置时，要说明默认值来自哪里。模型自己的猜测不能写成用户已经确认。

### 系统怎样实现这一步

先由程序读取当前任务和用户权限，再把相关信息交给模型。模型给出一份简短、固定格式的理解：

- 当前说的是哪项任务；
- 是新建、修改、查询，还是暂停、继续、取消；
- 是要测试、排查，还是验证修复；
- 哪些条件改变了，哪些继续保留；
- 还缺什么，先查资料还是问用户。

程序检查这份结果以后，才真正更新任务、安排测试。第一次可以直接用现有模型，不必马上单独训练一个意图分类模型。

对于明确的暂停、取消等请求，应优先处理，不要先花很久检索资料。

### 开始排查以后，还可以改变任务吗

可以。用户原来只要求测试，发现问题后又说“继续查”，系统可以接着调查。开发提供修复版本后，也可以进入验证。

但这不意味着旧报告可以覆盖掉。原来测了什么、结果怎样，要保留；新的要求和测试另行记录。

允许的操作也要继续遵守。用户说“只在实验室查”，后面一句“继续”不能被解释成允许操作现场设备。

### 怎样判断这部分做得好不好

不只看分类有没有选对，还要看是否产生了错误操作：查进度有没有误启动测试，改对象有没有用错旧结果，暂停后有没有继续新增实验。

这些比一张总体分类准确率更能说明入口是否可靠。具体测试方法见 [评测](07_Agent评测体系设计.md)。

## 二、详细技术拆解

### 给实现者保留的几个名字

内部可以用 TEST、INVESTIGATE、VERIFY_FIX 分别表示测试、调查、修复验证。它们只用于程序处理，用户不必学习这些名字。

用户操作可以记成有顺序的 message_actions，值为 CREATE、UPDATE、QUERY、PAUSE、RESUME、CANCEL。“先别跑，只给结果”就按暂停、查询处理。

知识咨询也可以只读回答。例如“这个参数是什么意思”，查资料解释即可，不需要创建测试。

### 理解结果应是可检查的对象

入口不能只输出“调查类，置信度 0.9”。程序需要知道关联哪项任务、做什么修改、哪些信息缺失以及是否允许执行。下面是建议的数据契约，字段名用于教学，不绑定框架。

```json
{
  "target_task_id": "task-01",
  "message_actions": ["UPDATE"],
  "task_type": "INVESTIGATE",
  "goal": "REPRODUCE",
  "condition_patch": {"bandwidth_mhz": 40},
  "read_only": false,
  "investigate_on_failure": null,
  "missing_fields": [],
  "reason": "用户只修改带宽，保留原目标及其他条件"
}
```

`null` 在这里表示本条消息没有改变失败后策略，不表示把原策略清空。实际接口要明确“字段未出现”“显式关闭”“清空”三种语义，不能混用默认值。

### 意图识别的推荐流水线

1. 根据会话和显式任务编号找候选任务，核对访问范围。存在多个合理目标时先澄清，不让模型随便选最近一项。
2. 优先识别明确的暂停、取消和查询，避免被句中的“测试”二字误导。
3. 向模型提供候选任务摘要、当前条件、可用能力与新消息，输出结构化理解。
4. 程序检查任务类型与目标是否兼容、修改字段是否合法、是否超出允许范围。
5. 重新检查任务版本，保存原始消息、解释结果与采用的修改，再决定是否推进。

明确控制命令可由规则快速处理，含否定或复合语义的表达仍要检查。例如“不要取消，继续查”和“取消上次报告里的那项建议”不能仅凭出现“取消”就结束活动任务。

### 条件更新必须是补丁，而不是重新猜一份任务

“带宽改为 40 MHz，其他不变”对应只含带宽的补丁。应用把它合并到原条件，再校验组合是否受支持。没有出现在补丁中的设备、环境、版本、目标和预算全部保留。

还要分清条件来源：用户显式指定、工具查询、项目默认和待探索因素。来源影响能否自动变化。设备编号缺失通常需要查清；未知负载可以成为探索维度；不存在合格规则则不能擅自生成门限。

改条件后使旧证据过期，不等于删除旧记录。若带宽改变，原带宽的测试仍保留，只能在说明适用范围后作为历史参考。

### 复合请求怎样表达顺序

| 原话 | 解释 | 执行顺序 |
| --- | --- | --- |
| 先别跑，给我已有结果 | PAUSE、QUERY | 先阻止新增运行，再读记录 |
| 先给上次报告，再验证修复版 | QUERY、CREATE | 返回旧报告，建立关联验证任务 |
| 先测，失败再查 | TEST 加条件后续策略 | 先判定有效测试结果，失败时才转调查 |
| 只看日志，别跑测试 | 只读分析 | 可查询已有证据，不创建可执行实验 |

复合动作应有明确的支持组合，不能把任意动作数组直接循环执行。尤其取消与新建同时出现时，要确定各自对象，不能默认作用于同一任务。

“失败再查”触发的是产品判定 FAIL。平台提交失败或监测缺失要走执行异常处理，不应直接当作产品缺陷进入原因搜索。

### 修复跟进怎样关联原问题

修复任务引用原 `issue_id`、原任务与复现方法版本，实际版本由查询或受检附件元数据确认。原任务已经结束时，建议新建关联任务，保留原报告。

“继续上次”如果只是恢复暂停，则沿原任务；如果是复现完成后继续查原因，则更新目标或创建关联后续任务。文档和接口应明确采用哪一种，保证原目标与新目标的结果都能回查。

### 什么时候询问用户

查询不能消除的对象歧义、相互冲突的明确限制、缺少必需规则，或者操作范围是否扩大，都需要澄清。把所有未知参数一股脑抛给用户会中断调查价值；可探索且已允许变化的因素则留给实验设计。

给用户的确认说明应简短表达“对象、目标、范围、接下来做什么”，内部 schema 留在详情。准确率之外，要直接检查是否误启动、错取消、丢约束或把只读改成执行。
