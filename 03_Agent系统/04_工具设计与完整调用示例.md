# 工具设计与完整调用示例

本章整合六个核心工具与局点测试扩展工具，说明工具契约、选择依据、调用依赖，以及消息与 State 的完整演变。以下按目标架构描述，示例数字、统计结论与阈值不代表生产实测。通用调用协议见 [[03_Agent系统/03_Function-Calling与消息协议]]。

## 工具输入输出完整定义

工具契约可以通过 LangChain `StructuredTool`、Pydantic 模型或 MCP 工具描述承载。LLM 根据可见的名称、说明、输入输出契约及当前测试状态选择工具，执行器负责校验参数和结果、检查执行条件并调用实际平台。

### 工具能力总览与职责划分

保留现有六个核心工具的职责，在局点验收所需能力缺失处补充工具，避免为同一能力重复命名。工具目录可以包含全部能力，每轮仅向模型提供当前任务适用的工具子集。

| 工具 | 主要职责 | 调用后获得的关键证据或标识 |
| --- | --- | --- |
| `Test_Case_Query` | 检索适用的测试用例 | 用例 ID、步骤、前置条件、期望指标 |
| `Simulation_Runner` | 在仿真环境提交测试 | 仿真 `session_id`、提交状态 |
| `Metrics_Collector` | 采集指定测试会话的 KPI | 指标、采集状态、原始数据引用 |
| `Baseline_Comparator` | 与指定历史基线比较 | 差异、回归项、满足数据前提时的统计结果 |
| `Log_Analyzer` | 解析日志和协议事件 | 异常事件、原始证据、待验证的根因假设 |
| `Fleet_Manager` | 调度多个局点的 Worker 或探针资源 | 分配关系、子会话列表、集群状态 |
| `Test_Spec_Query` | 检索测试规范与验收依据 | 适用版本、条款、门限来源 |
| `Site_Inventory_Query` | 查询局点资产和拓扑 | 设备、软件版本、业务及连接关系 |
| `Device_Snapshot_Query` | 查询设备当前状态和配置 | 主备角色、接口、告警、配置快照 |
| `Business_Monitor` | 管理独立的业务连续性监测 | 监测 ID、就绪状态、业务观测数据 |
| `Site_Test_Runner` | 在局点执行已登记的测试动作 | 现场测试 `session_id`、动作事件 |
| `Task_Controller` | 查询或取消单个异步任务 | 任务状态、取消结果、清理状态 |
| `Test_Result_Evaluator` | 根据验收规则判定测试结果 | 逐项结论、证据缺口、判定依据 |
| `Test_State_Restorer` | 恢复本次测试引入的环境变化 | 恢复记录、未恢复项、复核结果 |
| `Test_Report_Generator` | 汇总测试过程与证据 | 报告引用、覆盖项、待处理事项 |

`Simulation_Runner` 与 `Site_Test_Runner` 分别面向仿真和现场执行；`Baseline_Comparator` 回答“相对基线是否退化”，`Test_Result_Evaluator` 回答“是否满足验收要求”，两种结论分别保存。`Fleet_Manager` 管理多局点资源，`Task_Controller` 管理单个任务的生命周期，取消任务也不等同于恢复环境。

### 工具契约除了输入输出还要定义什么

以下是工具目录的建议元数据，不要求全部成为模型调用时的参数，也不表示所有字段都是某个协议的标准字段。

| 定义项 | 应描述的内容 | 局点测试中的用途 |
| --- | --- | --- |
| 名称、契约版本与说明 | 稳定标识、版本、能力和边界 | 区分查询、执行、诊断和判定 |
| `inputSchema` | 类型、必填项、枚举、范围、条件依赖 | 限定局点、设备、动作和会话参数 |
| `outputSchema` | 返回结构、字段语义、单位、空值及状态约束 | 判断工具能否补齐所需证据，连接后续调用 |
| 适用范围 | 支持的设备型号、软件版本、协议和环境 | 排除当前局点不适用的工具 |
| 前置条件 | 必须已有的状态、资源或上游结果 | 如备设备就绪、监测已开始、已有快照 |
| 执行影响与权限 | 只读、测试流量、配置修改、切换；所需权限及资源范围 | 由执行器检查是否允许执行 |
| 时间特性 | 同步或异步、超时、采样间隔、数据有效期 | 避免把提交成功当成测试完成 |
| 幂等和重试 | 请求去重键、重复调用语义、可重试错误 | 防止超时重试导致再次触发切换 |
| 并发与资源约束 | 设备锁、探针配额、互斥测试 | 避免两个测试同时修改同一设备 |
| 错误契约 | 错误码、原因、能否重试、建议补充的信息 | 区分无数据、版本不支持与设备故障 |
| 证据与来源 | 对象、观测窗口、采集时间、原始记录、规范版本 | 支持审计与后续复核 |
| 使用示例 | 正确调用、边界情况及上下游依赖 | 减少选错工具或误读结果 |

工具定义、执行器校验和结果验证各有职责：说明让模型理解用途，schema 约束数据结构，执行器检查权限与当前条件。模型提出的调用请求不能代替执行侧校验。

### 输出 Schema 与证据有效性

输出契约既帮助解析结果，也帮助模型在调用前判断“该工具将返回什么，能否回答当前问题”。例如，返回 `session_id` 的提交工具无法直接证明测试通过；需要继续获取对应会话的观测结果。

- **明确单位和分母**：成功率使用 0～1 的比例还是百分数，时延使用 ms 还是 s；比例指标还应说明成功次数、总尝试数和无样本情况。
- **记录观测范围**：指标关联 `site_id`、测试对象、会话以及 `observed_from`、`observed_to`，跨工具事件按统一时间基准关联；采样精度和时间同步误差应满足测试要求。
- **区分状态与结论**：执行状态使用 `queued / running / completed / failed / cancelled` 等枚举；测试判定另用 `PASS / FAIL / INCONCLUSIVE / BLOCKED`。运行完成不等于测试通过。
- **显式表示缺失**：没有样本或未覆盖切换窗口时，值应为空并附带原因；不能把缺失填成 0，也不能将“未检测到异常”自动解释为业务正常。
- **验证条件字段**：运行中只返回已取得的数据和进度；完成后检查必需证据；执行失败返回错误信息及已完成动作。执行状态、数据是否完整和测试结论分别表达。
- **保留证据引用**：返回摘要与 `evidence_refs`，原始日志、采样数据和配置快照保留在存储中，模型按需读取，避免把全量日志塞入上下文。

MCP 支持可选的 `outputSchema`；声明后，结构化返回值必须符合该 schema，客户端应进行校验。接入模型时还要确认框架是否将输出契约传给模型；未传递时，应在工具说明中补充关键输出字段及其语义。Pydantic 输出模型的存在本身不保证模型能看到它。[MCP 工具规范（2025-11-25）](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

以下保留六个核心工具的输入输出示例，再补充局点测试工具的字段契约。字段表中的 `?` 表示可省略，`或空` 表示允许返回空值；具体实现需进一步落成完整 schema。

### 9.1 Test_Case_Query（用例检索）

```python
# ---- 输入 Schema ----
class TestCaseQueryInput(BaseModel):
    scenario: str          # 测试场景名称，如 "handover", "idle_mode_reselection"
    band: str              # 频段，如 "n78_100MHz", "n41_60MHz"
    feature_tags: list[str] # 特性标签，如 ["mobility", "beamforming"]
    top_k: int = 10        # 最大返回用例数，默认 10

# ---- 输出 Schema ----
class TestCaseQueryOutput(BaseModel):
    cases: list[TestCase]  # 匹配用例列表
    total_found: int        # 库中总命中数（用于判断检索质量）
    retrieval_scores: list[float]  # 每条用例的相关性得分（0~1）

class TestCase(BaseModel):
    case_id: str           # 唯一标识，如 "TC_HO_NR_001"
    title: str             # 用例标题
    steps: list[str]       # 执行步骤
    expected_kpi: dict     # 期望 KPI，如 {"ho_success_rate": ">= 0.98"}
    source: str            # 来源：3gpp / bugzilla / golden
```

**工具描述（注入 System Prompt 的 Schema 片段）**：
```
Tool: Test_Case_Query
Description: 从知识库检索匹配指定场景和频段的测试用例。
             当需要获取测试用例时调用，不可凭空生成用例。
Parameters:
  - scenario (str, required): 测试场景关键字
  - band (str, required): 频段规格
  - feature_tags (list[str], optional): 细化特性筛选
  - top_k (int, optional): 返回条数上限，默认 10
```

### 9.2 Simulation_Runner（仿真执行）

```python
# ---- 输入 Schema ----
class SimulationRunnerInput(BaseModel):
    case_ids: list[str]     # 待执行的用例 ID 列表
    env_config: dict        # 仿真环境参数，如 {"ue_count": 32, "speed_kmh": 120}
    timeout_seconds: int = 300  # 单用例超时时间

# ---- 输出 Schema ----
class SimulationRunnerOutput(BaseModel):
    session_id: str         # 异步任务 ID，后续 Metrics_Collector 凭此轮询
    status: Literal["queued", "running", "failed"]
    estimated_duration_s: int   # 预估完成时间（秒）
    error_msg: str | None   # 若 failed 则携带错误原因
```

> 注意：Simulation_Runner 是**异步工具**，只返回 session_id，不等待执行完毕。  
> Agent 需要在下一轮 Action 中调用 Metrics_Collector 轮询结果。

### 9.3 Metrics_Collector（指标采集）

```python
# ---- 输入 Schema ----
class MetricsCollectorInput(BaseModel):
    session_id: str         # Simulation_Runner 返回的任务 ID
    metric_names: list[str] # 需要采集的指标，如 ["ho_success_rate", "rlf_count"]
    poll_interval_s: int = 5    # 轮询间隔（工具内部重试逻辑）
    max_wait_s: int = 600   # 最大等待时间

# ---- 输出 Schema ----
class MetricsCollectorOutput(BaseModel):
    session_id: str
    status: Literal["running", "completed", "timeout"]
    metrics: dict[str, float]   # 指标名 → 实测值，如 {"ho_success_rate": 0.976}
    raw_log_path: str           # 原始日志在共享存储的路径
    collection_time: str        # ISO8601 时间戳
```

### 9.4 Baseline_Comparator（基线对比）

```python
# ---- 输入 Schema ----
class BaselineComparatorInput(BaseModel):
    session_id: str  # 当前测试会话
    baseline_version: str  # 对比基准版本，如 "v2.3.1_golden"
    metrics: dict[str, float]  # 当前实测值（来自 Metrics_Collector 的输出）
    test_method: Literal["t_test", "ks_test", "envelope"] = "envelope"
    sample_refs: dict[str, str] | None = None  # 统计检验所需的原始样本引用


# ---- 输出 Schema ----
class BaselineComparatorOutput(BaseModel):
    verdict: Literal["PASS", "FAIL", "INCONCLUSIVE"]
    p_value: float | None  # T-Test/KS-Test 显著性检验结果
    delta_summary: dict  # 每项指标与基线的差值和百分比
    regression_flags: list[str]  # 检测到的回归项，如 ["ho_success_rate 下降 3.2%"]
    confidence: float  # 本判定的置信度（0~1）
```

`envelope` 按基线中登记的容差范围比较汇总指标。选择 T/KS 检验时，需通过 `sample_refs` 取得当前与基线样本并检查实验前提；缺少必要数据时返回 `INCONCLUSIVE`，不生成 p 值。`confidence` 是需单独校准的辅助评分，不能代替证据完整性检查。

# ---- 输入 Schema ----

### 9.7 Test_Spec_Query（测试规范与验收依据检索）

与用例检索分工：`Test_Case_Query` 查“测什么、怎么测”，本工具查“依据哪个版本、如何判定”。可以复用同一个知识库和检索服务，但返回契约分别定义。

| 契约 | 字段与语义 |
| --- | --- |
| 输入 | `scenario: str`、`device_model: str`、`software_version: str`、`spec_version?: str`、`customer_profile?: str` |
| 输出 | `matched_rules: list`，每项包含 `rule_id`、规则版本、适用条件、指标、比较符、门限、单位、文档引用和条款位置；另返回 `missing_requirements: list[str]`、冲突项和检索来源 |

规范中的协议行为与项目验收门限不能混为一谈。没有找到适用门限时返回缺口；多份规则冲突时交由已配置的优先级或人工澄清处理，LLM 不自行编造数值。

### 9.8 Site_Inventory_Query（局点资产与拓扑查询）

| 契约 | 字段与语义 |
| --- | --- |
| 输入 | `site_id: str`、`resource_types?: list[str]`，限定设备、业务或连接关系 |
| 输出 | 局点类型、设备 ID、型号、软件版本、业务 ID、拓扑关系、可用测试能力，以及资产来源和更新时间 |

用于解析“该局点”“目标小区”“主设备”等对象，并选择适用工具。资产记录不等于实时状态，执行前还需查询现场快照；对象存在歧义时不能猜测设备 ID。

### 9.9 Device_Snapshot_Query（实时状态与配置快照）

| 契约 | 字段与语义 |
| --- | --- |
| 输入 | `site_id: str`、`device_ids: list[str]`、`sections: list[str]`，限定角色、接口、告警或配置 |
| 输出 | `snapshot_id: str`、设备状态、配置版本、活动告警、采集时间、各字段是否成功采集及原始快照引用 |

用于测试前检查和测试后复核。返回采集事实；是否满足具体测试的前置条件，由执行器结合用例规则检查。快照需关联测试会话，并记录可用于恢复的配置范围，不能把部分查询成功当作全部设备正常。

### 9.10 Business_Monitor（业务连续性监测）

| 契约 | 字段与语义 |
| --- | --- |
| 输入 | `action: start / read / stop`；启动时提供局点、业务或探测端点、监测指标、采样间隔和最长运行时间；读取或停止时提供 `monitor_id` |
| 输出 | `monitor_id: str`、监测状态、`ready: bool`、实际观测窗口、采样间隔、样本数、丢包率、中断区间与时长、数据缺口及原始证据引用；尚不可计算的指标为空 |

执行器用条件 schema 或分别绑定子工具约束不同动作的参数。监测状态包含 `starting / observing / stopped / failed`，与测试任务状态分别定义；`ready=true` 只在探测已开始且满足预设就绪条件后返回。

本工具管理跨越切换前后的独立观测窗口；`Metrics_Collector` 仍负责测试会话的 KPI 采集。两者可共享采集后端，但不混淆 `monitor_id` 和 `session_id`。监测启动和就绪之后才能触发切换；监测中断或窗口不完整时，不得给出“零业务中断”的结论。

### 9.11 Site_Test_Runner（现场测试动作执行）

| 契约 | 字段与语义 |
| --- | --- |
| 输入 | `site_id`、`case_id`、目标设备或业务 ID、`action_type`、动作参数、前置快照 ID、所需的监测 ID、`idempotency_key`；动作及参数由适用的能力清单和 schema 限定 |
| 输出 | `session_id: str`、任务状态、已执行动作、事件 ID 与时间戳、状态查询引用，以及失败原因或恢复上下文引用 |

仅执行已登记的测试动作，例如指定测试场景的切换、发流或受控故障注入。设备权限、资源互斥、前置条件和监测就绪状态由执行侧检查；重复提交同一去重键返回原任务。请求超时后先查询任务是否已创建或动作是否已发生，再决定是否重试。

这里的 `action_type` 必须区分 UE 小区切换（Handover）与设备主备倒换，两者的对象、触发方式和验收指标不同，不能仅凭“切换”二字选用同一动作。

### 9.12 Task_Controller（单任务生命周期管理）

| 契约 | 字段与语义 |
| --- | --- |
| 输入 | `session_id: str`、`task_type: simulation / site_test`、`action: status / cancel`；取消时提供原因 |
| 输出 | 任务状态、进度、已完成动作、结果引用、是否收到取消请求、是否已取消以及待清理资源 |

会话标识必须来自提交工具；适配层将它映射到实际平台任务。取消请求受理不等于任务已经停止；任务结束也不等于现场环境已恢复。`Fleet_Manager` 可调用该能力取消子任务，但仍负责集群资源的整体调度。

### 9.13 Test_Result_Evaluator（验收规则判定）

| 契约 | 字段与语义 |
| --- | --- |
| 输入 | 测试用例与规则的 ID、版本、现场前置条件检查结果、指标和事件证据引用；需要回归检查时附带基线对比结果引用 |
| 输出 | `verdict: PASS / FAIL / INCONCLUSIVE / BLOCKED`、逐项实测值和门限、证据引用、未满足条件、证据缺口及规则版本 |

由程序执行门限比较、时间计算和覆盖检查。`FAIL` 表示有效证据证明某项验收要求未满足；`INCONCLUSIVE` 表示数据不足或矛盾；`BLOCKED` 表示前置条件不满足而无法开展测试。具体聚合规则按测试配置确定，并在报告中保留逐项结果。

验收通过和相对历史基线退化可能同时发生，分别记录两种结论。T/KS 检验需要适当的样本和实验前提，不能仅凭两个汇总值生成有效的显著性结论。

### 9.14 Test_State_Restorer（测试环境恢复）

| 契约 | 字段与语义 |
| --- | --- |
| 输入 | `site_id`、测试会话 ID、测试前快照 ID、本次动作记录、需停止的监测或发流任务 ID，以及恢复请求去重键 |
| 输出 | `restore_status: completed / partial / failed`、已恢复项、未恢复项、冲突项、残留任务和恢复后复核证据 |

只恢复本次测试实际修改且仍符合恢复条件的项目。恢复前检查当前配置版本与变更记录，存在其他任务的并发修改时返回冲突，不能直接覆盖整份旧快照。正常结束、失败和取消均进入清理分支，恢复失败需明确报告。

### 9.15 Test_Report_Generator（测试报告生成）

| 契约 | 字段与语义 |
| --- | --- |
| 输入 | 局点与会话 ID、用例和规则版本、判定结果引用、执行记录、原始证据引用、恢复结果，以及报告格式 |
| 输出 | `report_id`、报告文件或资源引用、测试覆盖清单、未完成项、证据缺口、恢复状态和待跟进事项 |

以 `Test_Result_Evaluator` 的结构化判定为准，LLM 可辅助撰写解释。报告不得把日志中的根因假设改写成已确认事实，也不能省略数据不足、取消或恢复失败的状态。报告文件生成成功与测试通过分别表达。

### 9.16 Agent 如何根据证据缺口选择工具

先将自然语言需求整理为测试对象、场景、验收项、前置条件和执行约束，再按下列循环决策：确定缺少的证据 → 检索适用工具 → 执行器筛选权限、版本和前置条件 → LLM 选择工具及参数 → 执行与验证 → 更新任务状态。

参数必须来自用户输入、资产记录、用例规范或上游工具结果；不能猜测设备 ID、会话 ID 和门限。每次决策只需记录本次目标、证据缺口、所选工具、参数来源和预期输出，便于追溯。

以“验证 A 局点设备主备倒换后的业务连续性”为例：

| 阶段 | 工具及依赖 | 对下一步的影响 |
| --- | --- | --- |
| 明确测试对象 | `Site_Inventory_Query` | 获取真实设备、版本、业务及拓扑 |
| 确认测试依据 | `Test_Case_Query`、`Test_Spec_Query` | 匹配用例、适用门限；无法确定关键要求时先澄清 |
| 检查前置条件 | `Device_Snapshot_Query` | 记录快照；备设备不就绪时停止执行并记录阻塞 |
| 建立观测 | `Business_Monitor.start` | 等待就绪并覆盖所需的切换前观测窗口 |
| 触发动作 | `Site_Test_Runner` | 保存会话与事件 ID；本场景不调用仿真工具 |
| 取得结果 | `Task_Controller`、`Metrics_Collector`、`Business_Monitor.read`、后置状态查询 | 覆盖动作前后窗口并验证业务与设备恢复，不能只看设备角色 |
| 补充诊断 | 按证据缺口调用 `Log_Analyzer` 或继续查询 | 异常时再补查，不默认扫描所有日志；假设需进一步验证 |
| 判定与收尾 | `Test_Result_Evaluator`、`Test_State_Restorer`、`Test_Report_Generator` | 保留验收结论与恢复结果，缺证据时报告无法判定 |

执行器将清理注册为必经收尾步骤，异常退出也要停止测试流量、释放资源并复核恢复状态；收尾顺序按用例规定执行，不能由固定示意顺序覆盖现场要求。

### 9.17 与自动编排的分工和选工具评测

成熟测试步骤交给编排引擎执行；LLM 负责理解需求、匹配用例和规范、补齐参数以及处理未预先穷举的异常。条件分支、轮询和重试本身不要求使用 LLM，是否引入 Agent 应看它能否在相同测试质量下减少人工接手及流程维护成本。

工具选择评测以有效证据和业务结果为主：验收项覆盖率、工具与参数适用性、依赖顺序、无效或重复调用率、异常后的合理处置、证据不足时的误判率。允许多个等价的有效调用序列，不以复现唯一工具顺序作为唯一标准。

## 测试用例格式与存储

### 典型测试用例举例

系统面向 5G 无线网络测试，测试用例覆盖三大类场景：

**切换场景（Handover）**

```
用例 ID：TC_HO_001
名称：同频切换成功率验证
场景：UE 在两个 gNB 之间执行基于 A3 事件触发的 X2 切换
前置条件：UE 驻留源小区，RSRP 满足 A3 触发阈值（offset=3dB, TTT=160ms）
执行步骤：
  1. 触发 RRC 测量上报（MeasurementReport）
  2. 源 gNB 下发 RRCReconfiguration（含切换命令）
  3. UE 向目标小区发起随机接入（PRACH）
  4. 完成 RRC 重配置，路径切换（PathSwitchRequest）
预期结果：切换成功率 >= 98%，中断时间 < 50ms
关联协议：3GPP TS 38.331 Section 5.4.3
```

**随机接入场景（PRACH）**

```
用例 ID：TC_PRACH_003
名称：高负载下竞争随机接入成功率
场景：50 个 UE 同时发起竞争随机接入（Contention-Based RA）
前置条件：小区负载 > 70%，PRACH 配置 Format 0，preambleTransMax=10
执行步骤：
  1. 50 个 UE 并发发送 Preamble（Msg1）
  2. 基站响应 RAR（Msg2），含 TA 和上行授权
  3. UE 发送 RRC Setup Request（Msg3）
  4. 基站完成竞争解决（Msg4）
预期结果：随机接入成功率 >= 95%，平均接入时延 < 20ms
关联协议：3GPP TS 38.321 Section 5.1
```

**CA（载波聚合）场景**

```
用例 ID：TC_CA_007
名称：双 CC 下行聚合吞吐量验证
场景：UE 配置 2CC CA（PCC: n78 100MHz + SCC: n41 60MHz）
前置条件：两路 CC 信号质量均 >= -85dBm，SCC 已激活
执行步骤：
  1. 下发 RRCReconfiguration 激活 SCC
  2. 触发全缓冲 FTP 下载（iperf3）
  3. 持续 60s 采集 PDCP 层吞吐量
预期结果：峰值下行吞吐量 >= 2.4Gbps，SCC 激活时延 < 100ms
关联协议：3GPP TS 38.331 Section 5.7.1
```

### 测试用例如何存储

测试用例在系统中以**双索引结构**存储，同时支持关键词精确检索和语义检索：

**Milvus 向量库（语义检索）**

每条测试用例拆分为两级存储：

```
用例描述（叶子 Chunk，512~800 Token）→ Embedding → 384/768 维向量
用例摘要（父级节点，含场景标签）      → Embedding → 向量

metadata 字段：
  - case_id: "TC_HO_001"
  - scenario: "切换"
  - feature: "X2切换"
  - band: "n78"
  - priority: "P1"
  - spec_ref: "38.331-5.4.3"
  - version: "R16"
  - is_golden: true/false（是否经专家确认的 Golden Case）
```

metadata 中的标量字段支持过滤查询（如只检索 P1 优先级或 Golden Case）。

**Elasticsearch（BM25 关键词检索）**

用例中大量 3GPP 术语（PRACH、HARQ、RRC、PDCP 等）依赖无线专有词表分词，BM25 负责精确匹配协议编号和参数名（如 `preambleTransMax=10` 这类数字配置项语义检索会漏召回）。

**Agent 查询时的流转**

```
Agent 推理：需要查切换相关用例
     ↓
调用 Test_Case_Query(scenario="切换", feature="X2切换", band="n78")
     ↓
Tool 内部走三级召回（ES + Milvus 粗筛 → RSF 融合 → Reranker 精排）
     ↓
返回 Top-K 用例列表（含 case_id、步骤摘要、关联协议）
     ↓
Agent 将用例内容注入 Prompt，决策是否触发 Simulation_Runner 执行
```

**Golden Case 的特殊地位**

经 HITL 专家审核通过的用例会被标记 `is_golden=true`，在检索时作为加权正样本优先召回。同时这批数据会持续回流进入 Embedding/Reranker 的微调训练集，形成数据飞轮——系统使用越久，召回的用例质量越高。
