# 模型需要哪些工具，怎样用起来

## 一、直观理解

主线定位：将已检查的实验计划交给执行能力，取得真实观测与恢复记录。完整链路见 [系统运行全流程与交互拓扑](18_系统运行全流程与交互拓扑.md)。

工具就是模型可以通过程序使用的实际能力，比如查用例、跑仿真、读日志、比较结果。原来的测试脚本大部分仍然可以用，只需要把调用方式和返回信息整理清楚。

先看模型要查“升级后移动视频卡顿”时，具体需要做什么。

### 开始前，先查对象、用例和标准

系统要查清是哪台设备、哪个版本、什么配置。然后找到适用用例，以及本项目怎样判断业务正常。

查询工具应返回实际编号、适用条件和来源。只返回“找到了一个相似用例”还不够，因为相似不一定适用。

历史缺陷也可以查，但用途是提供思路。以前同样的卡顿由服务端造成，不表示这次也是。

### 真正测试时，要先准备监测

如果要判断视频是否停顿，就要在动作发生前启动业务监测。设备自己说“切换成功”，不一定能说明用户业务没有断。

监测准备好后，执行脚本开始工作，平台返回任务编号。程序等待完成，收集指标和日志，再按测试方案恢复环境。

这里需要保留实际版本、实际负载和操作时间。计划写了高负载，不代表整个测试期间真的保持了高负载。

### 原有工具怎样继续使用

下面只保留一张工具表，英文名方便后续和代码对应。读业务流程时，可以直接按中文理解。

| 工具名 | 做什么 |
| --- | --- |
| Test_Case_Query | 找测试用例、步骤和可调参数 |
| Test_Spec_Query | 找适用判断标准和来源 |
| Site_Inventory_Query | 查设备、版本和连接关系 |
| Device_Snapshot_Query | 查当前状态，保存测试前后的配置 |
| Simulation_Runner | 在仿真环境运行测试 |
| Site_Test_Runner | 执行已允许的现场测试 |
| Business_Monitor | 启动、读取和停止业务监测 |
| Metrics_Collector | 取本次测试的指标和样本 |
| Task_Controller | 查平台任务进度或请求取消 |
| Baseline_Comparator | 比较两组条件和结果 |
| Log_Analyzer | 提取相关日志、事件和时间顺序 |
| Test_Result_Evaluator | 按明确规则判断通过、不通过或无法判断 |
| Test_State_Restorer | 停止测试活动，恢复本次改过的环境 |
| Test_Report_Generator | 根据已有记录整理报告 |
| Fleet_Manager | 分配测试设备和其他资源 |

这些名称代表建议保留的能力，是否已经接通要看实际接口。仿真工具和现场工具分开使用，报告也要说明结果来自哪里。

### 调查层还需要什么记录

需要补一份“实验记录”。

假设要比较普通负载和高负载，系统应该先记下：为什么比较、其他条件怎么保持、各跑几次、怎样判断异常。跑完再追加真实结果。

接下来要能查询这些记录。否则模型可能忘记已经做过什么，反复安排相同测试。

还需要保存“当前怀疑什么、哪些结果支持、哪些结果不支持”。开发给出修复版时，再把修复版本与原问题、复现方法关联起来。

这些可以先做成应用中的普通功能，不必每一项都拆成独立服务。需要给模型调用的部分，再提供工具接口。

### 每个工具的说明至少写清五件事

第一，能做什么。例如只会读日志，还是能启动测试。

第二，需要什么输入。设备编号、版本、单位和参数范围都要明确。

第三，什么条件满足后才能调用。例如监测已经启动、设备已经就绪。

第四，返回什么。排队、运行、完成要区分，缺数据要说明，不能用零代替。

第五，出错以后怎么处理。能不能重试，动作是否可能已经发生，怎样取消和恢复。

这就是工具的输入输出约定。写得清楚，模型才知道什么时候用；程序也才能检查它有没有用错。

### 普通测试怎样串起来

用户说“测当前版本的下载速度”。

系统查设备和配置，找用例与标准，检查环境，启动必要监测，再执行测试。完成后取数据，按规则判定，恢复环境并出报告。

失败但用户只要求测试时，就如实报告。不自动追加大量排查。

### 调查任务怎样串起来

用户说“移动视频偶尔卡，先帮我复现”。

系统查已有场景和历史案例，提出先比较两种负载。程序登记实验、检查设备与次数，按计划重复运行，保存每次结果。

比较工具检查两组实际条件。模型看到结果后，再决定是否复核、改动作顺序或补查日志。

因此，同一批工具能服务两种工作。差别主要在于：调查时，每轮结果会决定下一轮测什么。

### 两个容易写错的小地方

重复提交同一次运行，应返回同一个平台任务；计划里的另一次重复测试，则必须真正新跑一次。不能把“重复请求不重复执行”做成“十次测试只跑了一次”。

另外，日志工具输出的“怀疑原因”仍然是猜测。报告工具不能把它改写成“原因已确认”。

## 二、详细技术拆解

### 给实现者：保留哪些编号

test_case_id 表示用例，issue_id 表示异常问题。原平台如果用 case_id 表示用例，由程序明确转换。

每次运行保存 run_id，与平台 session_id 对应；日志和指标附上运行编号、时间、单位及文件位置。实际结果由工具写入记录，模型可以引用和解释，不能随意改写。

更完整的调用关系见 [消息与调用](03_Function-Calling与消息协议.md)，实验怎样设计见 [复现与实验](12_异常复现与实验设计.md)。

### 一份工具契约应该长什么样

工具契约要说明“每个工具补齐哪份证据”，同时保存实验归属、实际条件和重试语义。下面用提交仿真说明，类型是教学设计，不依赖现有脚本签名。

```python
from typing import Literal

from pydantic import BaseModel, ConfigDict, Field


class SubmitRunInput(BaseModel):
    model_config = ConfigDict(extra="forbid")

    run_id: str
    experiment_id: str
    plan_version: int = Field(ge=1)
    test_case_id: str
    device_id: str
    config_snapshot_id: str
    monitor_id: str
    parameters: dict[str, int | float | str | bool]
    timeout_seconds: int = Field(default=600, ge=1, le=3600)


class SubmitRunOutput(BaseModel):
    run_id: str
    session_id: str | None
    status: Literal["queued", "running", "rejected", "unknown"]
    actual_version: str | None
    actual_config_hash: str | None
    error_code: str | None
    side_effect: Literal["none", "started", "unknown"]
```

`parameters` 的宽类型只是展示工具外壳，正式用例还要用专用 schema 限定每个参数的单位、枚举和范围。设备、快照、监测、用例等引用必须能查询，并属于当前任务范围。

同一 `run_id` 用相同输入重传，返回相同的提交结果；同一编号换参数应报冲突。实验里的下一次重复运行使用新的 `run_id`，所以会真正再测一次。

输入输出以外，再登记以下元数据：

| 元数据 | 具体约定 |
| --- | --- |
| 契约版本 | 参数变化是否兼容，历史结果按哪个版本解释 |
| 适用范围 | 设备型号、构建版本、用例与环境 |
| 执行前提 | 设备就绪、监测就绪、配置与计划匹配、资源已取得 |
| 执行影响 | 只读、测试流量、配置修改或设备动作 |
| 生命周期 | 同步还是异步，提交、查询、取消和收尾各怎样调用 |
| 错误语义 | 动作是否已发生，允许重试什么，是否先核查状态 |
| 观测约定 | 时间基准、单位、采样窗口、缺失数据和原始记录位置 |

这些字段属于项目的工具目录，不应未经转换就塞进某个模型 API 的工具定义。

### 关键工具的输入输出怎样衔接

| 工具 | 核心输入 | 关键输出 | 下游怎样使用 |
| --- | --- | --- | --- |
| Test_Case_Query | 现象、特性、设备与版本过滤 | `test_case_id`、步骤、可调参数 | 决定能运行什么 |
| Test_Spec_Query | 指标、规则适用范围 | `rule_id`、版本、条款、门限、单位 | 固定本轮判定方法 |
| Device_Snapshot_Query | `device_id`、配置项 | `snapshot_id`、版本、配置摘要 | 校验初始条件，支持差异恢复 |
| Business_Monitor | 对象、业务、观测窗口、操作类型 | `monitor_id`、就绪、覆盖范围 | 执行前检查，完成后取业务观测 |
| Simulation_Runner / Site_Test_Runner | 运行、用例、快照、参数、监测 | `session_id`、提交状态 | 后台查询真实运行状态 |
| Metrics_Collector | `session_id`、指标与时间窗 | 样本、单位、分母、缺失区间 | 交给规则判定和统计比较 |
| Baseline_Comparator | 两组运行引用、比较方法 | 可比性、差值、区间、适用时的统计结果 | 判断差异与后续验证方向 |
| Log_Analyzer | 运行引用、时间窗、事件类型 | 事件顺序、原始位置、待验证解释 | 更新假设，不直接确认代码根因 |
| Test_Result_Evaluator | 样本引用、规则版本 | 逐项 PASS/FAIL/INCONCLUSIVE、理由 | 保存产品判定 |
| Test_State_Restorer | 本次改动、初始快照、当前状态 | 已恢复项、冲突、未恢复项 | 决定环境能否继续使用 |

`Baseline_Comparator` 回答“相对基线怎样变化”，`Test_Result_Evaluator` 回答“是否满足要求”。两者需要区分：两组都不合格但新版本有所改善，不能把“改善”写成“通过”。

### 一次版本比较的完整调用链

以下是教学轨迹。用例、规则和编号均是假设，目的是说明真正需要传递哪些信息。

1. 查询得到用例 `TC-MOB-01`，允许调整负载和切换序列；取得规则 `BUSINESS-R1`，记录业务停顿的判断方式。
2. 保存原设备配置与版本，确认业务监测就绪，创建新版本实验 `exp-new`，重复 3 次。每次运行有独立 `run_id`。
3. 对 `run-new-1` 提交测试，平台返回 `session-new-1/queued`。执行器查到完成后采集业务样本与设备日志；其他两次同样处理。
4. 本轮假设得到 3 次有效运行，1 次同类停顿。恢复环境，保存每次恢复结果。
5. 创建对照 `exp-old`，通过 `comparison_id=exp-new` 关联，保持设备、配置、负载、动作和规则，仅替换版本。
6. 假设对照 3 次有效运行均未观察到同类停顿。比较工具先检查实际条件，再计算观测差异；少量样本只用于寻找方向。
7. 模型读到差异，提出“简化动作后重新复核”。此时交付的是版本相关线索，还不是“已确认升级引入资源泄漏”。

每次运行内部的依赖可以画成：

```text
对象与规则查询 → 取得资源 → 保存快照 → 准备业务监测
    → 提交动作 → 查询完成 → 取样本与日志 → 判定
    → 恢复本次改动 → 复核环境 → 释放资源
```

需要保留故障现场才能取日志时，先采集再恢复；不能先重启抹掉证据。若任一步失败，仍进入对应的收尾路径。

### 返回结果怎样支持有效比较

采集结果应记录 `requested_conditions` 与 `observed_conditions`。例如计划负载 80%，实际只到 45%，只能说没有达到预设负载，不能把该运行当作高负载正常样本。

原始样本引用至少关联对象、时间、单位、采集器和内容校验值。成功率保存成功数与尝试数，时延保存采样定义和数量。未采到样本返回空值和原因，不填零。

同一组比较应输出 `comparability` 与差异项。发现配置、时钟或规则不一致时，先补查或重做；模型不能靠改写报告消除真实偏差。

工具目录可以很全，每轮给模型的集合应较小。例如等待测试时，普通程序只需状态查询；分析原因时再提供日志细查。详情加载不会改变执行端的权限和参数检查。
