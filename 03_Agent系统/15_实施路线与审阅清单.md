# 第一版先做什么，怎样一步步推进

先别把目标定成“所有故障都能自动定位”。

更适合的起点是：选一类真实问题，让系统在实验室里完成几组有用比较，找到别人照着也能复现的方法，并整理好材料。

这一步如果能减少工程师的操作，就值得继续扩大。

## 先选一个合适的真实问题

最好具备三个条件：已有工具能跑，有足够日志或指标，有熟悉它的工程师。

先让工程师按原方法完整处理一次，记录做了什么、为什么做、每步结果和实际花的主动时间。

这份记录既是功能样例，也是以后比较是否省人工的起点。只看最后一份缺陷单通常不够。

## 第一步，把统一入口和原测试跑稳

支持“帮我测”“改条件”“查进度”“暂停”“继续”和“取消”。

这阶段不急着让模型自由调查。先保证不会听错对象，不会问进度却开测试，改了带宽不会丢掉其他要求。

普通测试仍然按原脚本执行，完整保存结果和恢复情况。

## 第二步，失败以后能补做几组比较

限定一个场景和允许参数。比如发现连续切换异常后，自动检查单次切换、旧版本或普通负载。

每组都记录为什么测、实际条件、结果与下一步。先把有限补测和材料整理做好，不必马上确认代码原因。

检查它是否真的减少了人工配置、等待取数和比较的工作，设备花费是否还能接受。

## 第三步，能根据结果换方向

加入反复验证、调整猜测、删掉无关步骤和重新复现。

例如旧版本也失败，就回头查共同环境；去掉背景业务仍能出现，就保留更简单步骤；少了一段监测，就补数据，不认定产品正常。

用没参与设计的相近问题试一试，检查系统是不是只会照演示流程走。

## 第四步，再增加原因和修复验证

工具能读取更多内部状态后，再做更深的原因检查。先写清什么程度可以叫确认，哪些仍需开发检查。

修复版本来了，使用原复现方法比较，并检查相关业务有没有变慢或变差。

如果原问题尚未稳定复现，先说明这会限制修复验证，不能直接换几个简单用例跑通就宣布成功。

## 第五步，按实际错误决定是否训练

收集模型反复做错的决定和专家修改。先修提示、工具、资料和任务记录，仍然出错再微调。

不需要为了完整展示技术，把大模型训练、多 Agent 和各种组件一起加入。每增加一项，都要说明解决了什么问题，以及是否真的更好。

## 审阅时，先回答这些问题

- 第一批支持什么异常，哪些工具已经能用？
- 默认做到复现、缩小范围，还是继续验证原因？
- 测试失败后是否自动排查，最多跑几次？
- 哪些参数可以自动调整，哪些必须先确认？
- 谁提供业务标准，谁确认具体代码缺陷？
- 修复版本怎样关联原问题？
- 设备和时间够不够，怎样记人工投入？

这些决定清楚以后，才比较容易估算工作量。

## 第一版至少展示哪些情况

普通测试完成后结束；一句模糊反馈变成复现；失败后按要求继续；查询不启动测试；改对象保留其他条件；暂停取消处理真实运行；新结果推翻原猜测；工具做不了时把材料交给人。

再补一个修复例子：原问题改善，但等待变长，系统也能报告。

模拟演示、真实工具接通和实际省人工，分别验证，分别记录。

## 文档融合后按什么方案学习

当前正文保留新版的统一入口与异常调查主线，吸收旧版的工具契约、控制循环、记忆与恢复、统计评测和后训练原理。通俗说明解释为什么做，技术展开说明具体怎样设计。

设计不受现有教学代码的能力上限限制。允许范围内的参数变化由程序检查；新动作另行处理；日志线索不能直接作为代码原因；任务状态、产品判定、调查进展和恢复分别表达。

旧版归档保留历史设计与原文。文档中的样例数字用于学习，不转换为新版实测成绩。统一术语和范围见 [范围与约定](01_项目事实与实现状态.md)。

## 每个阶段都看同一件事

工程师主动操作、分析和整理材料的时间有没有减少，结果是否同样可靠，总花费是否合理。

机器跑了八小时，不代表节省八个人工小时；模型调用很多，也不代表工作做得多。

项目范围见 [范围与约定](01_项目事实与实现状态.md)，效果怎样比较见 [评测](07_Agent评测体系设计.md)。

## 技术展开：每个阶段都应有可检查的产物

| 阶段 | 主要产物 | 怎样检查学会了 |
| --- | --- | --- |
| 范围与基线 | 一个问题说明、工具能力表、人工处理轨迹 | 能说明目标、未知、约束与停止条件 |
| 统一入口 | 意图 schema、消息例子、条件补丁规则 | 查询不启动，修改保留未变条件，控制对象明确 |
| 一次运行 | 工具契约、依赖顺序、结果与收尾记录 | 能从规则和样本得出结论，失败也能收尾 |
| 多轮调查 | 初筛、对照、简化和确认记录 | 下一步会随证据变化，保留反证 |
| 原因与修复 | 假设记录、区分实验、关联验证报告 | 不把相关写成确认，能发现修复副作用 |
| 评测与改进 | 动态任务集、对照报告、专家反馈 | 能区分流程收益与模型收益 |
| 可选训练 | 分组数据、标签检查、SFT/DPO 对照 | 不泄漏未来信息，完整任务表现有依据 |

## 可以先做一份完整的纸面演练

不写代码也能先验证设计。给出用户原话、初始状态与工具说明，请读者填写意图、第一组实验和不同结果下的分支；再依次揭示模拟观测，检查下一步是否随结果改变。

至少演练四个分支：候选场景可复现、旧版本也异常、监测缺失、预算耗尽。再插入一句“带宽改小，其他不变”，检查旧实验和新计划的关系。

演练产物包括任务快照、实验表、假设变化和报告，而不只是最终答案。若这些记录之间已经矛盾，先修文档与数据设计，没必要靠更多组件掩盖。

## 进入实现前，哪些契约要先统一

优先统一标识符与版本语义、条件的来源和可变范围、有效性与产品判定、暂停取消与恢复、证据引用、实验停止规则和报告字段。

这些契约稳定后，可以先使用规则计划器和确定性工具，再替换为真实模型或平台。替换后仍运行相同任务和检查，才能看出组件变化带来的差别。

技术选型可以后置。一个模型与普通执行循环已经能讲清新版 Agent 的核心；多 Agent、复杂队列和微调各自需要明确收益。

## 学习文档怎样继续维护

新增概念先在负责它的章节解释，再由其他章节链接；不要每章复制一份略有不同的字段定义。修改规则或术语时同步案例和样本，假设结果始终标注为示例。

正文优先回答业务和技术问题，代码运行记录单独维护。这样即使示例实现更换，文档仍能完整说明这套 Agent 怎样工作。
