# 怎样判断原因，怎样确认修复有用

## 一、直观理解

主线定位：从复现证据继续验证解释，再关联原问题检查修复与相关影响。完整链路见 [系统运行全流程与交互拓扑](18_系统运行全流程与交互拓扑.md)。

问题能复现以后，离“知道为什么”更近了，但还没有到终点。

比如，每次视频卡顿前都出现超时日志。超时可能导致卡顿，也可能是别的故障导致处理变慢，最后才超时。只看到两件事挨着发生，还不能直接确定因果。

### 把看到的事和猜测分开写

先写事实：

> “这几次异常前，旧连接相关资源持续占用。”

再写猜测：

> “可能是资源没有及时释放，影响了后续处理。”

然后问：如果这个猜测对，正常和异常运行应该有什么差别？有没有别的原因也能解释？下一次怎样测，能把它们区分开？

例如，一种解释是设备处理异常，另一种是业务服务器变慢。需要比较同一时段两边的记录，不能只反复看设备日志。

### 原因可以查到不同程度

最先确认的是现象：确实发生了业务停顿。

再往前一步，是找到条件：指定版本、负载和动作下可以重复出现。

继续补充记录，可能缩小到某个处理阶段或模块。最后要确认具体代码错误，往往需要开发看内部状态和实现。

第一版做到条件清楚、步骤可复现，就能减少大量人工。能够继续查多深，要看工具到底能读到什么。

### 报告怎样表达，才不会说过头

只有同时发生的记录，就说“发现相关线索”。

解释符合现象，但还没验证，就说“目前怀疑”。

几组可比较的测试都支持它，就说“实验支持这个解释”，并列出仍没排除的情况。

达到项目事先规定的确认要求，例如开发结合代码和内部记录确认了缺陷，才写“已经确认”，并说明是谁、用什么依据确认。

如果新结果不支持原来的猜测，就更新判断。保留那些结果，比坚持原来的解释更重要。

### 有些验证，平台做不了

现有工具可能没有内部资源记录，也不能控制相关状态。此时系统可以给出需要补采什么、开发需要检查什么。

不能因为报告需要一个原因，就声称已经读过不存在的内部数据。

修复后问题消失是重要信息，但一次修复同时改了好几处，也不能单靠结果说明到底哪一处是原始原因。

### 验证修复，先找回原来的问题

用户说“这是修复版，再测一下”，系统先找到原异常、原版本和复现方法，再核实实际加载的是哪一版。

如果原来还没有稳定复现，就要说明：目前只能做有限测试，无法完整证明修复效果。必要时先把复现补好。

不能把附件名称写着“修复版”，就当成设备已经运行该版本。

### 先照原方法测，再看相关影响

第一步是在相同条件和同一判断规则下，重跑原复现方案。尽量保留旧异常版本做比较，确认环境仍然能触发原问题。

第二步是围绕修改内容补测。例如问题出在连续切换，就检查相关次数、间隔和负载，而不是无目的跑全部用例。

第三步看有没有代价。延长等待时间可能减少断线，却让业务停顿更久；修复资源处理也可能影响吞吐或资源使用。

具体检查哪些项目，要有理由，并在用户允许的时间和次数内完成。

### 几种容易误判的情况

修复版没出现异常，但旧异常版也测不出来：先查环境和步骤变化，暂时不能说明修复有效。

原卡顿减少了，但等待超过要求：把改善和新问题分别报告，不能只说通过。

跑了一次正常：只能说明这一轮没观察到，要结合重复和样本范围说明。

用户只要求验证原问题：完成约定测试，明确哪些其他影响没有检查，把额外建议列出来即可。

### 最后把几件事分别告诉用户

产品测试结果、排查进度、原因是否确认，以及设备是否恢复，不要压成一个成功或失败。

例如：

> “规定条件下仍不满足要求；已找到简化复现步骤；资源处理原因得到部分支持，但还需开发确认；环境已恢复。”

修复报告则补充实际版本、比较结果、重复情况、其他影响和未测范围。经过审核的经验可以保存，供下次参考。

评测怎样判断这些结论是否可靠，见 [评测](07_Agent评测体系设计.md)。

## 二、详细技术拆解

### 原因假设不是一句自由文本

每个假设保存描述、提出依据、预期现象、替代解释、验证方法和状态变化。例如：

```yaml
hypothesis_id: hyp-resource-01
claim: 连续切换后旧连接资源回收延迟，造成后续业务处理受阻
status: PROPOSED
supporting_evidence: [ev-resource-growth, ev-outage-window]
counterevidence: []
predictions:
  - 异常运行中相关资源残留高于相同条件的正常运行
  - 资源异常应发生在业务停顿之前
alternatives:
  - 业务服务变慢，资源积压只是结果
  - 时钟偏差造成事件先后误判
next_check: 对齐设备和服务端窗口，比较资源生命周期与业务时序
confirmation_requirement: 区分替代解释，并取得可复核的实现或干预证据
```

支持与反对证据都保留引用。状态可以采用 `PROPOSED`、`SUPPORTED`、`CONFLICTED`、`NOT_SUPPORTED_IN_SCOPE`、`CONFIRMED`；最后一种必须满足项目约定的确认要求，不能由模型一句话升级。

### 从相关到确认，需要增加什么证据

可以按“现象确认 → 条件定位 → 阶段或模块线索 → 机制验证 → 具体缺陷确认”逐层推进。每层回答的问题不同。

例如资源占用增加与停顿同时出现，只能说明相关；先发生也不充分，因为两者可能由共同因素导致。更有区分力的验证是：在其他条件保持的情况下，通过受支持的开关或受控改动改变资源回收路径，观察资源与业务是否按预期共同变化。

干预必须在可控范围内，并确认没有同时改变业务等待、流量或其他机制。没有这种能力时，比较正常与异常运行、排除服务端因素仍有价值，但报告停在相应证据层级。

代码检查也要可追溯：开发指出具体路径、对象生命周期或竞态条件，并能与观察到的触发步骤对应。提交一个修复补丁不自动证明原来的机制猜测正确。

### 日志时序怎样避免“看起来有关”

对齐设备、终端和业务服务的对象标识与时间基准，记录时钟误差、采样间隔和窗口。若事件间隔小于同步误差，就不能依据日志顺序断言谁先发生。

提取异常前后窗口，与同条件正常运行比较。不要只展示报错最密集的一段，也要查正常运行是否有同类日志；正常也常见的超时可能不是区分性证据。

日志分析器可给候选解释，规则或解析器给事件事实，模型组织比较。原始位置、过滤条件和解析器版本都应能回查。

### 修复验证设计为三个比较

| 比较 | 改变什么 | 回答什么 |
| --- | --- | --- |
| 原异常版重测 | 尽量维持原复现条件 | 当前环境还能触发原问题吗 |
| 修复版主比较 | 只换修复构建，保留规则与方法 | 原问题在约定范围内是否改善 |
| 相关回归 | 按修改风险调整邻近条件 | 改善是否伴随时延、吞吐、资源或其他功能退步 |

保留问题之前的安全旧版时，也可加入第三种版本，但要区分“安全旧版”和“原异常版”。两者在调查中用途不同，不能都含糊叫“旧版”。

每次验证引用原 `issue_id`、复现方法版本和实际构建号。修复版命名或附件标签只提供线索，实际加载状态由工具核对。

### 验证结论怎样判

先规定每项验收范围、重复与停止规则。原异常版未复现时，主比较缺少触发能力证明，结论应受限；修复版没有出现异常时，报告样本与不确定性，不能直接写永不发生。

若业务停顿改善，但 P99 时延超过项目要求，两项分别报告。修复验证任务可以完成，修复版产品判定仍为 FAIL。整体汇总规则事先规定，不能在看到结果后改门限。

若修复同时修改多个模块，验证可以支持“这个构建在此范围内改善了问题”，但不能仅凭结果定位是哪一处代码起作用。需要更细的变更对照或实现证据才能继续确认。

### 报告的四类结果与任务状态分开

```json
{
  "task_result": "COMPLETED",
  "test_verdict": "FAIL",
  "investigation_progress": "REPRODUCED",
  "cause_status": "SUPPORTED",
  "cleanup_status": "COMPLETED",
  "summary": "原异常已有简化复现，修复版停顿改善，但时延未满足要求；资源处理解释仍需进一步确认"
}
```

这里任务已完成，指完成了约定验证；产品不通过，指某项要求未满足。调查进展可能引用原任务已经确认的复现，不表示修复版也发生同样异常。正文应附逐项结果、对照、证据与未测范围，使这些字段容易理解。
