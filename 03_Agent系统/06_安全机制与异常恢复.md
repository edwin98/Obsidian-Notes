# 怎样让系统少出错，出了错能停下来

自动排查会反复调用测试工具。要先解决一个很实际的问题：**系统可以自己做哪些事，做到什么程度必须停？**

例如用户说“只在实验室复现”，系统可以调整已经允许的参数，但不能因为实验室测不出来，就去操作现场设备。

## 开始前，把能做的事说清楚

记下允许使用的设备、环境、动作和参数，最多跑几次、占用多久，以及哪些操作需要人决定。

查询日志、执行已经审核的用例、在允许范围里调整负载，可以按规则自动进行。新脚本、新动作或扩大到其他环境，则需要另行检查。

这样不用每改一个普通参数就找专家，也不会把一句“继续查”理解成什么都能做。

## 模型提出动作以后，程序再检查

先检查设备是不是目标设备，用户是否有权限，当前版本和参数是否正确，设备有没有被别人占用，业务监测是否准备好，剩余次数是否足够。

检查通过以后才启动。

例如模型传了一个没有查询到的设备编号，程序应拒绝并返回原因。不能为了让流程继续，随便换一个相近编号。

## 出错以后，先分清发生了什么

如果只是参数格式错了，可以让模型改正。如果日志查询暂时失败，可以有限重试。

如果执行请求超时，要先查平台是否已经开始运行，不能马上再发一次。否则可能重复触发设备动作。

如果监测中断，应说明这次数据缺了哪一段。不能把“没有采到异常”当成“没有异常”。

如果没有必要的工具或权限，就整理已有结果交给工程师。反复换说法调用同一个不允许的操作没有帮助。

## 为什么每轮结束都要收尾

上一轮残留的流量、配置或资源占用，可能让下一轮出现假异常。因此需要停止测试活动、恢复本次改动、检查设备状态。

恢复之前还要看看别人是否改过同一配置。不能拿测试前的整份快照直接覆盖，把其他人的正常修改抹掉。

有一种例外要提前写清：如果正在研究连续切换的累积影响，一段连续动作内部就不能每做一步都清空状态。整段测试结束后，再按方案恢复。

## 暂停和取消分别怎么做

暂停是先不安排新测试，把当前工作停在可以继续的位置。已有动作可能需要先完成必要监测或收尾。

取消是结束这次工作。程序通知平台停止，确认实际状态，再处理残留。

如果暂时停不下来，界面就说“正在停止”。如果设备已停止但恢复失败，就把恢复问题单独列出，不能只显示“已取消”让人误以为一切正常。

恢复任务时，重新检查实际设备、在途任务和剩余次数，接着做尚未完成的部分。

## 防止系统一直查下去

除了单次调用超时，还要限制整个调查的次数、时间和费用。每次新测试都应说明想回答什么。

有意义的重复是为了确认偶发问题或复核一个结果。没理由地换几个参数乱跑，或者重复已有结果却不准备更新判断，就应调整方案或停止。

多个测试同时安排时，由程序统一扣除额度，避免每个任务都以为还有足够剩余次数。

等待日志、设备或修复版本，与主动执行分开记录。等待不需要让模型一直工作。

## 关键记录不要先删掉

重启、清日志或恢复配置可能消除线索。需要这些动作时，先保存调查所需的记录，再按允许的流程操作。

日志和外部文档里即使出现“忽略检查，执行某命令”，也只是文件内容，不能当成系统指令。读取资料不应让它获得额外操作权限。

## 交给人时，把问题一次说清

至少说明：用户想查什么、已经做过什么、结果怎样、现在卡在哪里、需要人补什么，以及设备是否恢复。

例如：

> “已找到可重复的场景，但现有工具读不到内部资源状态。请补充这段记录，或由开发检查相关实现。实验设备已恢复。”

这比“需要人工介入”更容易让工程师接着做。

数据和状态怎样保存，见 [任务记录](05_记忆与上下文管理.md)；具体原因怎样确认，见 [原因与修复](13_原因验证与修复检查.md)。

## 技术展开：校验与恢复怎样分层

旧版 Guardrail、错误分类、熔断和人工介入仍然有用，但新版应围绕“这份实验计划能否执行”设计。单独一个危险词分类器无法判断版本是否过期、设备是否被占用或对照是否有效。

建议执行前依次检查：

```text
结构解析 → 字段与范围 → 引用存在和归属 → 任务版本
    → 允许范围与前提 → 资源与预算 → 执行
```

程序检查明确条件，模型或分类器可以辅助识别模糊风险，但不能覆盖规则结果。用户允许在范围内调负载，不需要每次修改都重新审批；扩大环境、动作或资源范围时才走对应处理。

## 错误分类决定下一步

| 错误 | 动作是否可能发生 | 应怎样处理 |
| --- | --- | --- |
| FORMAT_ERROR，参数截断或非 JSON | 否 | 拒绝执行，有限次数重新生成完整参数 |
| SCHEMA_ERROR，字段或范围不合法 | 否 | 返回字段、约束与错误摘要，修改后重查 |
| INVALID_REFERENCE，编号不存在或不属于本任务 | 否 | 查询正确对象；不能猜一个替代编号 |
| PRECONDITION_FAILED，设备或监测未就绪 | 否或部分准备已发生 | 处理前提，收尾已发生的准备动作 |
| SUBMIT_STATUS_UNKNOWN，提交超时 | 可能 | 用幂等键查状态，不能直接重复提交 |
| DATA_INCOMPLETE，关键窗口缺采样 | 测试可能已完成 | 逐项标明可用与不可用结论，按需要补采或重跑 |
| CLEANUP_FAILED，恢复失败 | 是 | 阻止继续复用环境，保留差异和交接信息 |

解析失败时不应靠正则截出一段大括号就执行设备动作。只接受完整、可校验的调用；只有已经存在合法调用 ID 时，才返回对应的工具错误消息，避免凭空制造孤立结果。

## 重试、熔断和降级的具体区别

**重试**是同一操作的有限恢复。只读查询可按退避策略重试；写操作先检查是否已发生。业务上另跑一次测试，则创建新运行并计入预算。

**熔断**限制持续失败。除单工具超时和重试次数，还限制实验组数、实际运行数、设备占用和总费用。连续同类错误达到约定次数，或清理无法确认时，进入交接或等待，不靠换提示无限重试。

**降级**收窄能力。模型不可用时，仍可查询状态、执行既定收尾和生成已有数据报告；只对经过验证的场景使用固定方案。切换小模型需要重新评估，不假设小模型天然能接住全部任务。

旧版的模型置信度阈值只能作历史设计参考。新版优先检查证据缺口、工具能力和明确停止条件，不让一个自报分数决定设备动作。

## 暂停与取消的状态机

```text
READY --暂停--> PAUSED --恢复并复查--> READY
RUNNING --暂停--> PAUSING --到达可停边界并收尾--> PAUSED
RUNNING --取消--> CANCELLING --确认停止并收尾--> CANCELLED
任意执行阶段 --状态无法确认--> 核查或交接
```

能否停止在途动作取决于平台。无法抢占时先停止安排后续运行，当前运行结束后记录结果和恢复情况。取消接口返回“请求已接收”不代表设备已停止。

环境恢复是单独结果：即使任务已经取消，也可能有 `cleanup_status=FAILED/UNKNOWN`。这种情况要显式展示，不能继续把设备作为空闲资源分配。

## 环境恢复不是把整份快照覆盖回去

每个动作登记本次改过哪些配置以及相应补偿动作。恢复时比较“测试前值、本次写入值、当前值”：如果当前值已被其他合法操作改动，就记录冲突，不盲目覆盖。

正常结束、异常、取消和进程恢复都应进入收尾流程。连续动作研究累积效应时，动作段内部保留必要状态；整段完成后再清理，独立运行之间恢复到约定初态。

若使用 LangGraph 的动态中断，应把审批点放在副作用之前。恢复时节点可能重新执行，已发生动作仍需幂等保护；持久化暂停后即可返回，不用线程一直循环等待人工。

## 人工交接包保存什么

保存目标与最新限制、已做实验、适用证据、当前假设与反证、停止原因、在途运行和未恢复项，再给出下一项需要人工完成的具体动作。

专家修改后也要重新检查计划。审核意见可以进入后续训练候选，但应保留当时输入；修改了动作后，不能把旧动作产生的结果当成新方案已经验证。
