# 系统需要记住什么

## 一、直观理解

主线定位：把最新条件和历史证据保存为业务记录，再投影为下一轮模型输入。完整链路见 [系统运行全流程与交互拓扑](18_系统运行全流程与交互拓扑.md)。

假设今天查到一半，明天开发给了修复版本。系统应该知道昨天用什么条件复现、哪些猜测已经被否定、哪些日志还没拿到。

只保存一长段聊天记录，很容易把这些信息混在一起。因此要另外保存一份清楚的任务记录。

### 先记住用户现在的要求

例如：

> “只在实验室，目标是找到复现方法，暂时不用查到代码原因。”

后面用户改了带宽，系统只更新带宽。实验室限制、目标和设备等没改的内容都保留。

每次修改都记下时间和对应消息。不能聊天里已经改成 C 到 D，后台仍拿 A 到 B 的结果做结论。

### 再记住做过哪些测试

一次完整调查里面可能有很多组实验：版本比较、负载比较、连续切换比较。每组又可能重复运行多次。

要记清楚每组为什么做、设置什么条件、实际条件是什么、结果怎样、日志在哪里，以及设备最后有没有恢复。

计划和实际分开很重要。设定负载很高，但平台实际没有达到，这次结果可能就不能用于原来的比较。

### 猜测要和事实分开

事实可以写：

> “这几次卡顿前，设备记录里出现了资源占用增加。”

猜测可以写：

> “可能是旧连接资源没及时释放。”

系统还要保留不支持猜测的结果。例如低负载也出现一次同类异常，就不能只在摘要里保留“高负载会触发”。

后面换了判断方向，旧猜测和旧结果保留，写清为什么不再沿着它查。这样工程师不用重新走一遍弯路。

### 每次交给模型的信息不用很多

模型最需要知道的是：当前目标、最新要求、已经做过的关键测试、当前怀疑、与猜测不符的结果、还缺什么，以及还能花多少时间。

完整日志可以放在文件里，给模型相关片段和查询位置。它需要细看时再读。

摘要要保留“可能”“只在这些条件下”和“还没检查”等限制，不能越总结越肯定。原始记录始终可以回查。

### 暂停后，怎样接着做

保存当前计划、已完成测试、正在运行的任务和还占用的设备。恢复时先去测试平台查真实状态，再决定继续或收尾。

不能因为程序重启，就把最后一次请求重新发一遍；那次操作可能已经完成，只是结果还没取回。

等待修复版本时，也要记清等的是哪个问题、哪一个版本。等待不等于失败，不必不停重试。

### 报告要能回到原始记录

报告里的成功率、异常次数和版本，应能找到对应的运行数据。后来重新计算或发现错误，可以增加修订说明，不要悄悄改变原报告。

旧结果仍然有用，但要检查是否适用于当前条件。换了设备、规则或版本，不能直接沿用旧结论。

### 任务状态怎样分

用户界面可以直接显示“待补信息”“准备执行”“正在测试”“等设备”“等修复”“已暂停”“已完成”等中文。

内部可以对应 WAITING_INFO、READY、RUNNING、WAITING_RESOURCE、WAITING_FIX、PAUSED、COMPLETED 等名字。取消时先进入 CANCELLING，确认动作停止后再到 CANCELLED；程序出错则记录 ERROR。

测试是否通过另外保存，环境恢复是否成功也另外保存。一个复现任务可以已完成，同时产品测试不通过。

同一任务的修改要按顺序处理，或检查任务版本。旧请求迟到时，只更新它所属的旧运行，不覆盖新计划。

### 当前任务和长期经验有什么区别

“这次查到哪里”属于当前任务；“这类问题通常怎样查”属于经验库。后者应经过整理和审核，再用于其他任务。

不同项目的记录还需要检查访问权限。不能因为模型能搜索，就把别人的设备日志拿来使用。

经验怎样整理，见 [知识库](16_知识库与经验沉淀.md)；后台怎样保存和恢复，见 [工程实现](14_系统架构与工程实现设计.md)。

## 二、详细技术拆解

### 给实现者：建议保存的几类数据

| 记录 | 主要内容 |
| --- | --- |
| 用户消息与理解结果 | 原话、对应任务、想做什么、采用了什么修改 |
| 任务 Task | 类型、目标、最新条件、进度、允许操作和剩余次数 |
| 异常问题 Issue | 最初现象、涉及对象、已查清和未查清部分 |
| 实验 Experiment | 要回答的问题、比较条件、重复安排 |
| 运行 Run | 实际执行、平台任务、数据和清理 |
| 原始记录 Evidence | 日志、样本、计算结果和来源 |
| 猜测 Hypothesis | 解释、支持结果、不支持结果和当前判断 |
| 报告 Report | 某一时点的结论、引用和限制 |

task_id、issue_id、experiment_id、run_id 分别对应这些记录。聊天编号只用来关联对话，不能替代全部业务编号。

### 保存状态与构造上下文是两件事

数据库保存完整任务，模型每轮只读取相关视图。不能因为数据已经持久化，就把全部历史反复塞进上下文；也不能因为摘要变短，就删掉唯一的原始证据。

建议分成四层：

| 层次 | 内容 | 更新方式 |
| --- | --- | --- |
| 当前任务状态 | 最新目标、约束、计划版本、预算、等待项 | 通过明确消息或执行事件更新 |
| 实验与证据历史 | 所有计划、实际运行、反证和原始引用 | 追加记录，修订有版本 |
| 模型工作上下文 | 当前状态、关键摘要、近期调用与工具定义 | 每次调用按预算重建 |
| 跨任务经验 | 经审核的复现方法、已确认缺陷和适用范围 | 独立审核、发布和失效管理 |

LangGraph 的 checkpointer 可以保存线程执行状态；业务数据库保存实验和证据关系。它们可以互相引用，但 checkpoint 不会自动替你定义实验模型，也不提供业务授权隔离。

### 每轮发给计划器的状态视图

下面是精简示意，不是整份数据库记录：

```json
{
  "task_id": "task-01",
  "goal": "REPRODUCE",
  "task_version": 8,
  "plan_version": 3,
  "constraints": {"environment": "lab", "bandwidth_mhz": 40},
  "fixed_fields": ["environment", "device_id", "bandwidth_mhz"],
  "completed_experiments": ["exp-01", "exp-02"],
  "facts": ["新版本高负载连续切换出现同类业务停顿"],
  "hypotheses": [
    {"id": "hyp-01", "claim": "连续切换是触发条件之一", "status": "PROPOSED"}
  ],
  "counterevidence": [],
  "missing_evidence": ["旧版本同条件对照", "简化步骤的独立复核"],
  "remaining_budget": {"runs": 12},
  "evidence_refs": ["ev-01", "ev-02"]
}
```

`facts` 的每项在完整记录里都应有证据引用；摘要中的结论不是新的测量。模型需要细节时，按引用读取相关运行和日志窗口。

上下文预算可以分给约束、实验摘要、相关证据和近期交互，再预留输出空间。优先保留最新用户限制、反证、未完成事项及工具调用配对，不按固定字符数从头删。

### 用户中途修改为何要用两个版本

`task_version` 表示用户可见任务状态或约束的修订，用来检查并发修改；`plan_version` 表示哪些实验属于同一套有效条件，用来控制证据复用。项目可以采用不同递增策略，但两个职责应明确。

例如模型基于版本 7 安排下一组时，用户把带宽改成 40 MHz，任务更新到版本 8、计划更新到版本 3。旧模型结果到达后，执行前发现版本过期，放弃该计划。

已提交运行可能仍然结束。它的结果保留在旧计划，不覆盖新条件。原始数据满足新规则时，可以经过明确检查后引用；不能仅因同一个任务就默认可比。

普通生成请求已经发出后，修改本地 `messages` 不会自动让该次请求读到新消息。通用做法是在模型或工具边界重新读取任务状态，下一次调用使用新约束。停止文字生成和停止外部测试也要分别处理。

### 摘要怎样避免越写越确定

摘要中保留“观察到”“假设”“支持”“反对”“尚缺”几个不同区域。新结果推翻旧假设时，写下状态变更，不删除原先依据。

例如不能把“20 次中未观察到，但监测有缺口”压成“20 次正常”，也不能把“资源问题可能解释现象”压成“资源问题已确认”。

摘要附上所覆盖的事件范围与生成版本。重要判断从结构化记录重算；摘要只是阅读加速层，不能反向改写证据。

### checkpoint、长期存储与 KV cache

checkpoint 记录程序执行到哪里；长期业务记录保存任务事实与经验；KV cache 缓存模型前缀的中间计算。三者解决不同问题。

进程恢复时先读业务记录，再核查平台在途运行。即使恢复了模型消息，也不能据此认定设备仍保持原状态。修改历史中间内容后，也不能假设原前缀之后的缓存仍然有效。
