# 记忆与上下文管理

按作用域区分线程状态、跨线程记忆与知识检索。持久化不自动等于长期记忆，thread_id 也不自动提供授权隔离。数据库比较见 [[04_工程与框架/07_检索引擎选型与过滤检索]]；RAG 项目的预算和缓存策略见 [[02_RAG系统/05_答案生成与上下文管理]]。

## 1. 短期记忆：线程状态与上下文管理

LangChain/LangGraph 的短期记忆可以是 thread state，包含消息、任务进度及其他当前会话状态，通过 checkpointer 持久化和恢复。即使对话历史写入 Redis 或数据库，仍可属于短期记忆。[记忆概念](https://docs.langchain.com/oss/python/concepts/memory)

保存下来的历史不必全部送入模型。常见上下文管理方式包括：

- **滑动窗口**：按 token 预算保留近期内容；不能随意拆开工具调用与结果。
- **摘要**：将较早历史压缩为摘要，但可能损失细节或引入错误，重要原始信息仍需可查。
- **结构化状态**：保存用户约束、任务进度和待处理事项，避免仅靠对话文本恢复业务状态。
- **按需检索**：需要时再取回旧信息，控制上下文长度。

长上下文模型仍有输入上限、成本和有效利用范围，不能将某型号称作“无限窗口”。[短期记忆文档](https://docs.langchain.com/oss/python/langchain/short-term-memory)

## 2. 长期记忆：跨线程 Store 与知识检索

长期记忆可包括跨会话用户偏好、事实和已形成的经验。在当前 LangChain/LangGraph 体系中，Store 与 namespace 用于跨线程访问；namespace、身份和权限应与实际隔离需求一致。checkpointer 负责线程状态恢复，两者职责不同。[官方记忆概念](https://docs.langchain.com/oss/python/concepts/memory)

RAG 接入 Agent 常有两种方式：在模型调用前检索并注入上下文，或把检索暴露为工具，由 Agent 按需调用。前者便于固定流程，后者更灵活但需要评估工具选择和额外调用成本。记忆写入、更新、删除和来源可信度也需要明确策略。

## 3. 模型对话过程中如何插入新消息

**核心结论**：以普通文本生成接口为例，用户在模型回答或 Agent 执行期间补充要求，通常由应用接收消息、调度当前任务、更新上下文，再发起下一次模型调用。前端允许继续输入，不代表正在运行的那次模型请求已经读到了新消息。

### 3.1 为什么修改 messages 不会立即改变正在生成的回答？

一次普通生成请求会先把消息通过 chat template 转成 token，完成 prefill，再基于已有前缀逐步 decode。请求发出后，修改应用内的 `messages` 列表，不会自动修改服务端正在使用的输入。[自回归生成与 KV cache](https://huggingface.co/docs/transformers/en/cache_explanation)

流式返回与接收新输入是不同能力。例如 Agent Server 的 Streaming API 持续返回状态或 token；SSE 等输出流本身不提供向同一次模型请求追加输入的能力。[Streaming API 文档](https://docs.langchain.com/langsmith/streaming)

因此，“模型一边生成，一边听到补充要求”往往是产品对多次调用的连续展示。专门支持双向实时交互的协议可以有不同机制，不能由普通文本流式接口类推。

### 3.2 三种常见处理策略

| 策略      | 新消息何时进入模型上下文                        | 适合的情况            |
| ------- | ----------------------------------- | ---------------- |
| 排队      | 当前运行完成后，合并新消息并开始下一次运行               | 补充问题不影响当前任务      |
| 打断并重新调用 | 停止当前生成，在有效历史后加入新消息，重新调用             | 用户纠正条件、要求立即改方向   |
| 在执行边界接收 | Agent 在模型调用前、工具返回后等边界读取待处理消息，再决定下一步 | 希望保留已完成工作，接受少量等待 |

LangSmith Deployment 的 Agent Server 提供 `enqueue`、`interrupt`、`reject`、`rollback` 等并发运行策略；这是部署服务能力，不能假设仅使用开源 LangGraph 就自动具备同样的调度行为。[Double texting 文档](https://docs.langchain.com/langsmith/double-texting)

### 3.3 “打断并重新调用”的实现流程

例如用户先说“分析 n78 测试结果”，回答过程中又说“只看切换成功率，忽略吞吐量”。一种可行的应用设计是：

1. **接收并保存消息**：新要求作为同一会话的 `user` 消息入队，携带消息 ID 和顺序；根据会话归属验证访问权限。
2. **停止旧运行**：向运行中的任务发送取消信号，并尽可能取消底层模型请求。只关闭前端显示不一定停止后端生成；取消也可能与最后几个输出事件并发发生。
3. **确认有效状态**：保留已完成的工具结果和任务进度。未完成回答可以丢弃，或明确标记为中断的部分输出；不能把半段文本当作已完成结论。
4. **重组上下文**：将原请求、有效历史、已完成结果和新要求按顺序交给模型，并更新结构化任务约束，例如“当前仅分析切换成功率”。保留原任务目标，使模型知道补充要求修改了哪一部分。
5. **启动新运行**：为下一次调用分配新的 `run_id`，在同一会话下生成后续回答。底层模型仍按接口接收完整上下文或受支持的状态引用。
6. **过滤旧输出**：前端和状态提交逻辑同时校验 `run_id` 或状态版本，避免旧任务迟到的 token 或最终结果覆盖新回答。同一会话的写入应串行化，或使用版本校验。

```text
原问题 → 运行 A → 已完成查询，正在生成解释
                        ↓ 用户补充：只看切换成功率
              保存消息 → 停止 A → 整理有效上下文
                        ↓
              运行 B → 根据查询结果和新约束继续回答
```

这是通用工程设计示例，不代表本项目已实现完整的中途插话功能。Agent Server 的 `multitask_strategy="interrupt"` 则提供了保留先前运行记录、将其标记为中断并启动新运行的具体接口。[Interrupt concurrent 示例](https://docs.langchain.com/langsmith/interrupt-concurrent)

### 3.4 Agent 续跑时需要处理的边界

- **中断不等于撤销工具动作**：模型停止生成，不会自动撤销已经提交的仿真、文件写入或外部请求。工具仍在运行时，应确认能否取消；无法取消则记录真实结果，再按新要求重新规划。恢复或重试前检查任务状态和幂等键。
- **保持工具消息合法**：不能将半截工具参数作为完整调用执行。已经进入有效历史的工具调用，应有与调用 ID 匹配的成功、失败或取消结果；若清理未执行的调用，需一致地处理对应历史，避免留下孤立调用。
- **区分运行取消与 HITL**：LangGraph 的动态 `interrupt()` 是代码主动设置的暂停点，依赖 checkpointer，并通过同一 `thread_id` 下的 `Command(resume=...)` 提交恢复值。它不会自动把任意新消息注入正在解码的请求；节点恢复时会从头重执行，暂停前的副作用需要幂等。[LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)
- **区分 checkpoint 与 KV cache**：前者保存消息、节点和任务状态，后者缓存模型前缀计算。重新调用时，可否复用相同 token 前缀取决于推理服务；修改历史中间部分后，不能直接沿用该位置之后的旧缓存。[KV cache 原理](https://huggingface.co/docs/transformers/en/cache_explanation)

人工审批与异常恢复另见 [[03_Agent系统/06_安全机制与异常恢复#人工介入与状态恢复]]；消息配对规则见 [[03_Agent系统/03_Function-Calling与消息协议#消息结构与调用关联]]。

## 4. 主动记忆与分层管理

MemGPT 等工作探索让 Agent 主动读写外部记忆，将当前上下文和外部存储分层管理。它不是物理上扩大模型上下文，而是通过检索、摘要和写入策略管理有限上下文。

效果应同时看任务成功、信息准确性、隔离、更新一致性和调用成本，不能用“记住得更多”替代完整评测。历史项目的数据库与记忆实现仍按当时方案解释。
