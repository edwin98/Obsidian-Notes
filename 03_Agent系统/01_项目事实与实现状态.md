# 项目范围、设计假设与学习约定

本文保留原文件名，便于沿用已有链接；内容用于说明新版 Agent 的设计范围。学习时以文档的合理性、完整性和可解释性为主，不用现有代码是否已经实现来限制方案。

## 项目具体解决什么

对象是通信测试与异常调查：已有脚本能执行测试，Agent 负责理解自然语言要求、组织实验、根据结果调整调查、整理复现材料，并帮助验证原因和修复。

| 任务类型 | 输入 | 主要交付物 | 结束条件 |
| --- | --- | --- | --- |
| TEST，按需测试 | 对象、版本、用例或测试要求 | 测试报告与证据 | 约定测试完成，或明确无法执行 |
| INVESTIGATE，异常调查 | 现象、背景和调查目标 | 对照结果、复现步骤、原因线索 | 达到目标、预算耗尽或需要外部能力 |
| VERIFY_FIX，修复验证 | 原问题、修复版本与验证范围 | 原问题对照、修复结果、相关回归 | 约定比较完成，明确结论与未测范围 |

任务类型说明做哪类工作；目标说明做到哪一层。调查可只到 REPRODUCE，也可继续 NARROW 或 CHECK_CAUSE。用户只要求复现，就不必强行查到代码根因。

## 本文假定已经具备什么

假定有一组可调用的测试脚本或仿真接口，能查询测试对象，取得业务指标和日志，并执行必要的环境恢复。具体工具可以先用模拟器实现。

假定每项判定都有项目认可的规则，明确指标、单位、统计窗口和适用版本。没有规则时只能报告观测，不让模型临时编一个合格门限。

假定任务开始时能够约定可用环境、可变参数和资源预算。生产认证、跨机调度等可以在工程章节理解，但不是先学会 Agent 原理的前置条件。

## 统一术语，避免把不同层次混起来

| 名称 | 含义 | 例子 |
| --- | --- | --- |
| 会话 Conversation | 用户交互的上下文 | 一段连续聊天 |
| 任务 Task | 用户委托的一项工作 | 复现升级后卡顿 |
| 问题 Issue | 被调查的同一异常 | 同一缺陷及后续修复 |
| 用例 TestCase | 可执行步骤与判定依据 | 连续切换业务测试 |
| 实验 Experiment | 回答一个问题的一组运行 | 同负载比较新旧版本 |
| 运行 Run | 从准备到收尾的一次执行 | 新版本执行一次完整切换序列 |
| 证据 Evidence | 观测或可追溯的计算结果 | 日志、样本、配置快照 |
| 假设 Hypothesis | 解释现象的待检验说法 | 旧连接资源回收延迟 |

一次实验可以包含两个实验臂，每个实验臂重复多次。为简化教学，也可以把每个实验臂保存成一份计划，用 comparison_id 关联；同一组文档中说明所用口径即可。

## 设计约定与示例结果分开

“结果必须能追到运行和证据”是设计约定；“新版本 6/20 次异常”是讲解假设。示例里的 new、old、fixed 是版本别名，真实使用时应映射到可核实的构建编号和配置。

示例使用的重复次数、门限、模型规模、训练批次与耗时，都用来讲机制，不是通信统一标准，也不是已经取得的项目成绩。没有给出测量依据的收益数字不写成结论。

首版可以用一个模型、一个应用、一个数据库。多 Agent、MCP、独立推理服务和微调都按需要增加，不能用组件数量代替系统能力。

## 不再沿用旧版的几个简化假定

旧版主要围绕一次测试请求组织流程。新版要保存多轮实验、反证、计划版本和修复关联，不能用一条 messages 列表代替全部业务状态。

不再用一个总置信度决定一切：规则判定、实验有效性、原因确认和恢复状态分别保存。模型自报分数也不等于正确概率。

不再将固定训练规模、显卡配置或演示成功率当作项目默认事实。训练是否必要，先通过完整任务评测判断。

## 学习完成后应该能够解释什么

能解释一句话如何变成结构化意图，实验怎样被检查和执行，结果怎样改变下一步，用户中途修改时为何不能沿用旧计划，以及报告怎样回查证据。

进一步能设计动态评测，构建不泄漏未来结果的决策数据，说明 SFT/DPO 分别优化什么，并估算训练与实验资源。
