# Agent 项目上手与能力提升指南

把这个项目作为 Agent 应用开发实验室，按“运行观察 → 阅读源码 → 动手修改 → 测试验证 → 追踪评测”的顺序学习。目标是能够解释一次请求、独立增加能力、定位失败，并用证据说明修改是否有效。

所有命令均在 `03_Agent系统/code` 目录执行，使用 Python 3.12 或更新版本。需要具备 Python、异常处理、JSON 和基本 HTTP 知识；遇到类型标注、异步代码时再针对性补充。

## 1. 先跑起来，跟踪一次完整请求

```powershell
uv sync --group dev
uv run python demo.py --ui
```

打开 <http://127.0.0.1:8000>，选择“正常通过”和“单步执行”。每点击一次“执行下一步”，观察一个节点：

```text
用户请求 → clarify → agent → guardrail → tools → agent → … → result_judge
```

先只跟踪第一次 `test_case_query`：

1. `clarify` 判断需求是否明确。
2. `agent` 提出工具名称、参数和调用 ID，此时工具尚未执行。
3. `guardrail` 检查请求是否允许执行。
4. `tools` 执行 Python 工具，生成对应的 `ToolMessage`。
5. 下一轮 `agent` 读取观察结果，再决定下一步。

切换“状态变化”“输入快照”和“完整状态”，记录每一步的输入、更新和下一节点。界面刷新可回看当前任务，服务重启后内存任务丢失。

离线演示中，`OfflineModel` 按规则请求工具；状态图、工具执行和审批机制实际运行。在线模式才由真实模型选择动作，5G 工具仍是教学沙盒。

**本阶段产出：**一份执行记录，能说明谁提出动作、谁执行动作、结果如何影响下一轮。不看代码也能讲清整个循环。

## 2. 沿着调用链读代码，理解消息与状态

不要从头逐行阅读全部文件，按下面的顺序对照刚才的轨迹：

| 顺序 | 源码入口 | 要回答的问题 |
|---|---|---|
| 1 | [state.py](state.py)：`initial_state()`、`AgentState` | 一次任务需要保存哪些数据？ |
| 2 | [graph.py](graph.py)：`_build_workflow()`、路由函数 | 谁决定下一节点，何时循环或结束？ |
| 3 | [nodes.py](nodes.py)：`agent_node()` → `guardrail_node()` → `tool_node()` | 模型请求怎样变成实际执行？ |
| 4 | [tools.py](tools.py)：`create_sandbox_tools()` | 参数如何定义，工具怎样返回证据？ |
| 5 | [demo.py](demo.py)：`OfflineModel.invoke()` | 规则替身怎样根据观察选择下一工具？ |

重点理解四个机制：

- **消息协议：**用户输入是 `HumanMessage`，模型输出是 `AIMessage`，工具观察是 `ToolMessage`。请求的 `id` 必须与观察的 `tool_call_id` 匹配。
- **状态更新：**节点返回局部更新，由框架合并。`messages` 使用 `add_messages` 按消息 ID 合并，新消息通常追加，同 ID 消息可以更新；普通字段默认由新值替换。
- **证据保存：**`tool_outputs` 保存最近成功结果，`tool_history` 保留全部执行和错误。工具再次失败时需要清除旧成功缓存。
- **记忆分工：**消息保存交互历史，Checkpoint 保存执行状态，RAG 提供可检索知识。

画出第一次工具调用前后的消息列表，标出调用 ID、参数来源及观察结果。再读 [test_workflow.py](tests/test_workflow.py) 中的完整流程测试并运行：

```powershell
uv run pytest tests/test_workflow.py -k full_react -vv
```

**本阶段产出：**一张消息与状态对照表。能够在运行前预测某个节点会新增什么数据，以及下一步走向哪里。

## 3. 主动制造故障，学习恢复与约束

```powershell
uv run python demo.py --scenario regression
uv run python demo.py --scenario danger
uv run python demo.py --scenario review
```

后两个场景会暂停，终端输入 `approve` 批准，其余输入拒绝。也可以在学习界面切换场景并提交审批。

结合 [test_nodes_tools.py](tests/test_nodes_tools.py) 和 [test_workflow.py](tests/test_workflow.py)，每次只改变一个条件，先预测结果再运行：

| 实验 | 应观察的行为 |
|---|---|
| 业务指标失败，模型仍报告 PASS | `result_judge_node()` 的硬规则保留 FAIL |
| 缺少采集证据或模型替换 KPI | 不允许凭空通过，依赖校验拒绝不一致参数 |
| 在模型请求中替换 `session_id` | 工具返回错误观察，模型获得纠错信息 |
| 工具成功后再次失败 | 删除旧缓存；成功时连续错误计数归零 |
| 运行 `danger` 并分别批准、拒绝 | 危险请求在工具执行前暂停，拒绝后工具不执行 |
| 运行 `review` 后批准 | 允许继续不等于提高置信度或判定通过 |
| 降低 `recursion_limit` | 超限抛出异常，不能被报告成通过 |

审批重点读 `hitl_node()`：`interrupt()` 保存断点，调用方用相同 `thread_id` 传入 `Command(resume=...)` 恢复。当前内存模式需要保留原图实例；跨进程恢复需要持久化 Checkpoint。恢复时中断节点会从头运行，因此中断前的外部写入必须考虑幂等性。

记住：模型自报置信度不等于真实正确率；`recursion_limit` 是图的 super-step 上限；关键词围栏只是教学规则，实际应用还需要权限控制。

**本阶段产出：**至少三份“故障输入 → 实际轨迹 → 原因 → 对应测试”的记录。能够区分模型错误、工具错误、业务失败和正常待审批。

## 4. 增加一个工具，完成一次独立开发

建议做一个“测试报告查询”工具：先读取本地样例报告，再替换为真实 HTTP 接口。

1. 定义报告 ID、返回结构，以及报告不存在、参数错误等情况。
2. 实现并注册工具，确认模型收到的工具定义也包含它。
3. 根据需要修改提示词、依赖校验和结果判定。
4. 为成功和关键失败情况补充测试。
5. 如果需要离线演示，更新 `OfflineModel` 的选择逻辑；仅注册工具不会让替身自动调用它。

修改代码后执行：

```powershell
uv run ruff format .
uv run ruff check .
uv run pytest tests -q
uv run python offline_evaluation.py
```

**本阶段产出：**一个能被调用的新工具及必要测试。能解释修改涉及模型、执行器、状态和业务规则中的哪些部分，原有流程仍正常工作。

## 5. 切换真实模型，用 LangSmith 定位和评估问题

复制 `.env.example` 为 `.env`，填写本地配置：

```dotenv
DEEPSEEK_API_KEY=你的DeepSeek密钥
LANGCHAIN_TRACING_V2=true
LANGSMITH_API_KEY=你的LangSmith密钥
LANGSMITH_PROJECT=5g-test-agent
```

这里沿用项目现有追踪变量。非默认区域的 LangSmith 账户还需按账户区域配置 `LANGSMITH_ENDPOINT`。追踪会上传输入、输出等运行数据，使用适合上传的样例。

```powershell
uv run python main.py --interactive
```

在 [LangSmith](https://smith.langchain.com) 中查看对应追踪，核对实际提示词、历史消息、工具参数、观察结果和耗时。重点找出第一次偏离预期的调用，例如选错工具、编造参数、重复调用或提前结束，并确认新增工具能被真实模型使用。

随后运行在线评测，阅读 [evaluation.py](evaluation.py)：

```powershell
uv run python main.py --eval
```

先用现有样例跑通云端数据集和实验评分，再扩充固定用例：正常请求、模糊请求、危险请求、工具失败和证据不足。故障需要可控输入或故障注入，仅改变问题描述不能保证实际发生。

区分三种验证：测试检查程序规则；`offline_evaluation.py` 检查替身下的工程流程；在线评测检查真实模型在给定任务上的表现。`eval_system.py` 中部分入口使用模拟轨迹和模拟 Judge，其演示分数不能作为实测结果。

**本阶段产出：**成功、失败案例各一份追踪分析，以及一次修改前后对比。记录请求、首次异常节点、证据、修改和复测结果，对比成功率、工具调用正确性及耗时。根据任务判断人工介入是否合理，不能只追求更少审批或更高分数。

## 6. 跑通服务接口，再拓展整个项目

阅读 [api.py](api.py) 和 [test_api.py](tests/test_api.py)，理解任务创建、后台执行、节点级 SSE、会话隔离以及审批和澄清续接。

```powershell
$env:AGENT_MODE = "offline"
$env:AGENT_SCENARIO = "danger"
uv run uvicorn api:app --host 127.0.0.1 --port 8000
```

打开 <http://127.0.0.1:8000/docs>，按顺序操作：

1. `/run` 提交请求，保存返回的 `task_id`。
2. `/result/{task_id}` 查询状态，`/stream/{task_id}` 查看执行事件。
3. 状态变为 `hitl_pending` 后，向 `/resume/{task_id}` 提交审批；尚未等待审批时返回 409。
4. 在线模式出现 `awaiting_clarification` 时，通过 `/clarify/{task_id}` 补充回答。

审批请求体为 `{"approved":true,"feedback":"已复核"}`；澄清请求体为 `{"answer":"具体测试目标"}`。观察恢复后是否继续原任务，以及事件是否在执行过程中到达。当前 SSE 按节点推送，不是逐 token 输出，任务和事件保存在单进程内存。

完成单 Agent 后，按下表继续，每次只选一项拓展：

| 模块与入口 | 动手任务 | 要提升的能力 |
|---|---|---|
| [rag.py](rag.py)，运行 `uv run python rag.py` | 加入一条知识，比较不同查询的召回及引用；再尝试真实检索服务 | 理解知识如何进入工具链；当前检索与精排为本地近似 |
| [multi_agent.py](multi_agent.py)，运行 `uv run python multi_agent.py` | 增加一种 Worker 任务；把结果设为 INCONCLUSIVE，检查整体结论与签发标记 | 任务拆分、`Send` 分发、状态隔离、结果汇总；当前未完整支持跨请求子图审批 |
| [graph.py](graph.py) 的 PostgreSQL 工厂 | 安装 `uv sync --group dev --extra postgres`，配置数据库和 `POSTGRES_URI`，运行 `main.py --postgres` 验证状态写入，再用固定 `thread_id` 编写重启恢复实验 | 持久化、连接生命周期与恢复语义 |
| [statistical.py](statistical.py) | 用多次实验的原始样本比较结果，解释统计差异与业务阈值的区别 | 实验设计与证据判断；未检测到差异不等于业务通过 |
| [learning.py](learning.py)、[training/](training/) | 导出已确认专家反馈，切换 `confirmed` 检查导出数量，再了解 SFT/DPO | 反馈质量与数据闭环；导出样本不代表模型已完成训练 |
| [api.py](api.py) | 选做持久化任务、审批权限、超时取消或外部操作幂等性 | 从本地演示走向可维护的服务 |

**本阶段产出：**一次完整的接口调用记录，以及一项拓展的代码、测试和效果说明。实际数据库、检索、模型服务和训练需要各自集成验证。

## 如何判断自己真正掌握了

- 能从用户请求画出消息、状态、工具、审批和最终判定的流转。
- 能增加一项能力，并处理关键异常和会话隔离。
- 能从测试或追踪找到问题，解释原因并验证修复。
- 能用固定用例比较两个版本，而不是只展示成功案例。
- 能说明哪些部分已经实际运行，哪些仍是替身或待验证集成。

每个阶段保留一份简短实验记录，积累后就是可复现的项目材料。第一步只做一件事：在单步界面中跟踪 `test_case_query`，写清参数来自哪里、谁执行、结果存在哪里、下一轮如何使用，再运行对应测试核对。
