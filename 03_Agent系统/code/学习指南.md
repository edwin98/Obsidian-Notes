# 从描述文档走到可运行的 Agent

建议先运行，再读代码，最后修改测试验证自己的理解。所有命令均在 `03_Agent系统/code` 目录执行。首次运行先执行 `uv sync --group dev`。

## 1. 文档里的组件分别落在哪些代码中

| 文档概念 | 实现位置 | 当前范围 |
|---|---|---|
| ReAct 推理循环 | `graph.py`、`nodes.py` | 真实状态图，模型可切换为在线服务或离线替身 |
| Function Calling | `agent_node`、`tool_node` | 真正执行工具、逐条返回匹配 call_id 的观察消息 |
| 短期记忆 | `AgentState.messages` | 当前会话历史，由 add_messages 合并 |
| 状态存档 | MemorySaver / PostgresSaver | 本地测试覆盖内存断点；数据库需额外服务 |
| 检索记忆 | `rag.py`、`test_case_query` | 本地知识条目、词法/向量近似融合和引用 ID |
| Guardrail / 熔断 | `guardrail_node`、图路由 | 关键词拦截、连续错误计数、低置信度和递归上限 |
| 人工介入 HITL | `hitl_node`、`/resume` | 动态 interrupt；审批后从原断点继续 |
| 双轨判定 | `result_judge_node` | 业务规则 + 模型归纳，硬规则失败不可被模型改成通过 |
| 正式样本统计 | `statistical.py` | Welch、配对 t、KS、多指标校正、效应量及 t 区间 |
| 多 Agent | `multi_agent.py` | Send 并发分发，每个 Worker 运行完整单 Agent 图 |
| 工程接口 | `api.py` | HTTP、逐节点 SSE、审批和澄清接口，单进程内存任务 |
| 评测 | `tests/`、`offline_evaluation.py` | 验证工程行为；在线模型能力另做数据集评测 |
| 学习飞轮 | `learning.py` → 原有 `training/` | 专家标签导出与格式衔接；不自动启动 GPU 训练 |

概要文档包含早期的工具 Schema 和统计占位说明。本轮实现保留已有 Python 工具的 snake_case 命名及主要参数，以代码中装饰后的 Schema 为准。文档里的 `Test_Case_Query` 等大写名称是概念角色。

## 2. 第一个实验：观察 ReAct 的一次完整循环

也可以先启动可视化界面：

```powershell
uv run python demo.py --ui
```

打开 <http://127.0.0.1:8000>，保留默认“正常通过”和“单步执行”，点击“开始实验”。每次点击“执行下一步”只运行一个节点，完成后暂停。依次观察：

1. `clarify`：请求被判断为明确，下一步进入 `agent`。
2. `agent`：在“动作与观察”查看 `test_case_query` 的参数与 `call_id`，此时已执行工具数仍为 0。
3. `guardrail`：安全检查完成，此时工具仍未执行。
4. `tools`：查看带有同一 `tool_call_id` 的观察，此时已执行工具数变为 1。
5. 切换“状态变化”，比较 `messages`、`tool_outputs` 和 `tool_history`；再打开“输入快照”及“完整状态”理解节点前后状态。

点击历史轨迹可回看，点击“回到最新”继续跟随新步骤。界面顶部显示任务的实时状态，工具数、评分和错误数对应当前选中的历史步骤。刷新页面会恢复当前任务；关闭或重启服务会丢失内存轨迹。

完成后依次尝试“回归故障”“危险请求”“低置信度复核”。危险请求在工具执行前拦截；低置信度报告在判定后复核。两者都必须在审批面板作出决定，普通“下一步”无法绕过审批。可在开始前选择“连续执行”，再按轨迹回看。

界面使用同一张真实图的 `updates` 和 `values` 流：前者是节点返回的增量，后者是 reducer 合并后的实际状态。`teaching.py` 的路由说明调用 `graph.py` 中的原始路由函数；不是另写一份模拟流程。单步断点以 `None` 续接，人工断点则必须以 `Command(resume=...)` 恢复。

下面继续介绍终端方式，两种界面复用同一套节点与工具：

```powershell
uv run python demo.py --scenario pass
```

你会依次看到 `clarify → agent → guardrail → tools → agent` 重复出现，最后进入 `result_judge`。

离线模式里，`OfflineModel.invoke()` 根据已有观察选择下一次请求；在线模式中，这个决定来自 DeepSeek。两者共享状态图、节点、工具执行器、安全检查和结果规则。

第一次 `agent` 输出类似：

```python
AIMessage(tool_calls=[{
    "id": "call-0",
    "name": "test_case_query",
    "args": {"feature": "验证 Xn 切换回归"},
}])
```

这时工具尚未执行。`guardrail` 检查后，`tools` 调用注册表里的 Python 工具，并追加 `ToolMessage(tool_call_id="call-0", ...)`。下一轮模型读取这条观察，取出真实的用例 ID，再提出仿真请求。

重点检查三个字段：

- `messages`：输入、模型动作和工具观察组成的对话协议。
- `tool_outputs`：每种工具最近一次成功结果，便于判定节点取证。
- `tool_history`：完整执行轨迹，同一工具重复调用也不会丢失历史。

节点不能直接修改共享状态。它只返回更新，例如 `{"messages": [response]}`。`messages` 的 reducer 负责合并消息；普通字典字段由新的值替换，因此工具节点先复制缓存再更新。

阅读顺序：`state.initial_state()` → `graph._build_workflow()` → `agent_node()` → `guardrail_node()` → `tool_node()`。

对应测试：`tests/test_workflow.py::test_full_react_uses_real_tool_observations`。这个测试还验证模型请求和工具观察的 call_id 一一匹配。

## 3. 第二个实验：模型不能自行决定系统是否通过

```powershell
uv run python demo.py --scenario regression
```

故障注入后，沙盒返回低吞吐、高时延和高丢包。`baseline_comparator` 比较业务阈值，日志工具返回已知的注入异常。

`result_judge` 将两个来源合并：

1. 确定性业务证据，例如丢包率是否超过 1%。
2. 模型对这些证据的语义归纳及根因假设。

当业务规则确认失败时，即使模型输出 PASS，最终结果仍为 FAIL。证据缺失、非有限数值或未完成采集不能通过默认正常值填补，而应得到 INCONCLUSIVE 并要求复核。

模型的 `confidence_score` 是自报评分，不是统计置信区间，也没有经过概率校准。不能将 0.9 解释为真实正确率必然达到 90%。

对应测试：`test_hard_failure_cannot_be_overruled_by_model`、`test_missing_evidence_never_passes`、`test_model_cannot_replace_collected_metrics`。

## 4. 第三个实验：人工审批究竟暂停了什么

```powershell
uv run python demo.py --scenario danger
```

`danger` 在查询工具的参数中注入 `force_reboot` 字样，用于演示执行前拦截；它不会真的重启设备。暂停时，`tool_history` 为空，说明工具尚未执行。

状态图停在 `hitl_node` 的 `interrupt(payload)`。Checkpoint 保存消息、待执行动作和其他状态。输入 `approve` 后，调用方传入：

```python
graph.invoke(
    Command(resume={"approved": True, "feedback": "专家确认参数"}),
    config,
)
```

恢复必须使用相同图实例及相同 `thread_id`。内存模式下，换进程就失去了断点；跨进程需要持久化 Checkpoint。

恢复时 `hitl_node` 会从函数起点重新运行。因此 `interrupt()` 前不能执行有副作用的工具、写训练集或发送重复通知。决定返回后，图直接执行已审核的工具请求，不再让模型重新生成这个动作。

拒绝会生成 REJECTED 结果。批准只代表允许继续；之后仍可能 FAIL。`review_history` 记录审批历史，而 `hitl_required` 只是当前状态，清零后也不能据此推断“从未发生过人工介入”。

再运行 `uv run python demo.py --scenario review`，观察低置信度报告的审批。批准后评分仍保持 0.4，系统不会为结束流程而偷偷提高置信度。

对应测试：`test_danger_pauses_before_side_effect_and_resumes_once`、`test_low_confidence_review_does_not_raise_confidence`。

## 5. 错误、重试与循环上限

工具异常被转换成 `ToolMessage(status="error")`，模型能根据观察调整策略。`error_count` 表示连续错误，成功一次就归零。它与累计错误不同。

重复调用某个工具失败后，其旧成功缓存会被移除，避免判定节点误用过期结果。模型调用不存在的工具、编造 session_id 或替换采集后的 KPI，都产生可观察的错误。

达到连续错误阈值后转人工介入。`recursion_limit` 是 LangGraph 的 super-step 上限，不是工具次数或模型 token 数；超限抛出 `GraphRecursionError`，API 将其标记为 error。

LLM 重试只处理连接、限流与服务器错误，参数错误或鉴权失败应直接暴露。工具自动重试还涉及幂等性，本实现没有对真实外部操作承诺“恰好执行一次”。

## 6. RAG：知识与执行状态是两回事

```powershell
uv run python rag.py
```

`retrieve()` 执行查询增强、双路召回、按名次融合和近似精排。`test_case_query` 会把检索引用 ID 放进结果，便于观察知识如何进入工具链。

这里的向量是确定性词袋近似，精排是词重叠近似，BM25 使用简化的集合统计。它们适合解释流程，不能据此推断生产检索质量，也没有启动 Milvus 或 Elasticsearch。现有示例知识条目的协议解释需要在真实业务中核对正式规范。

原来的精排默认阈值 0.05 高于单轮融合分数的理论最大值约 1/61，可能把全部候选过滤掉；现在默认保留候选，再由精排排序。生产阈值需要真实标注集校准。

`messages` 是短期对话；Checkpoint 是执行状态；RAG 文档是可检索知识。三个存储面向不同目标。当前没有把人工批准自动写入长期知识库，因为“允许执行”和“知识正确”需要不同的审核依据。

## 7. 多 Agent：并发的是完整的 Worker 流程

```powershell
uv run python multi_agent.py
```

普通宏站有 5 项，室分有 3 项，高铁宏站有 4 项。主控根据局点类型规划任务，然后通过条件路由返回 `list[Send]`。`Send` 是调度指令，不能作为普通节点的状态更新字典。

每个 Worker 创建独立单 Agent 图和 thread_id，默认使用离线替身，查询内容来自该 Worker 的任务描述。结果通过 `worker_results` 的追加 reducer 汇聚，再统一 Reduce。

汇总保留原有优先级策略：P0 任一失败则整体失败，P1 失败比例超过 50% 则整体失败。缺失、重复、未知或未决任务会阻止签发。即使优先级策略允许整体 PASS，只要仍有失败子项，也不会标记 `sign_off_ready`。

若注入在线 Worker 图并遇到审批，当前主控会输出未决结果；它尚未提供跨请求管理子图审批的服务。多 Agent 示例也不会实际完成割接或写网元配置。

对应测试：`test_real_send_fanout_collects_each_worker_once`、`test_missing_or_inconclusive_worker_cannot_sign_off`。

## 8. 接口：SSE 是执行过程中发送的事件

在一个终端启动离线服务：

```powershell
$env:AGENT_MODE = "offline"
$env:AGENT_SCENARIO = "danger"
uv run uvicorn api:app --host 127.0.0.1 --port 8000
```

在另一终端提交并审批：

```powershell
$task = Invoke-RestMethod -Uri http://127.0.0.1:8000/run -Method Post -ContentType application/json -Body '{"query":"验证 Xn 切换回归"}'
Invoke-RestMethod -Uri "http://127.0.0.1:8000/result/$($task.task_id)"
Invoke-RestMethod -Uri "http://127.0.0.1:8000/resume/$($task.task_id)" -Method Post -ContentType application/json -Body '{"approved":true,"feedback":"专家确认"}'
```

提交是异步操作。先查询结果，看到 `hitl_pending` 后再审批；状态不是等待审批时会返回 409。拒绝时把 `approved` 改为 `false`。

`api._run_agent_async()` 在线程中迭代状态图，每个节点结束都把事件投递回 asyncio 事件循环。不能先执行 `list(graph.stream(...))` 再发送，那样前端直到任务结束才能看到第一批事件。

`/stream/{task_id}` 为每个订阅者保留独立游标，支持历史回放。审批期间连接等待，任务真正完成后才发 `stream_end`。`/resume` 会恢复原图，不会直接伪造通过结果，也不允许提交任意 `patched_state`。

在线模式下，模型可能先要求澄清，此时任务为 `awaiting_clarification`，通过 `/clarify/{task_id}` 追加 `{"answer":"具体测试目标"}` 即可继续同一会话。

对应测试：`tests/test_api.py`，其中 `test_stream_emits_before_graph_finishes` 故意阻塞后续推理，确认此前的节点事件已经发出。

## 9. 正式统计检验要有原始样本

聚合 KPI 的阈值比较与显著性检验分开。下面在 Python 中运行：

```python
from statistical import compare_samples

report = compare_samples(
    {"throughput": [81, 84, 83, 80, 82]},
    {"throughput": [98, 101, 99, 102, 100]},
    method="welch",
)
print(report)
```

每个数应是一轮独立实验的原始观测。不能把一轮实验的聚合 pass_rate 当成多次独立观测。

- `welch`：两组独立样本均值比较，允许不同方差。
- `paired`：相同条件下逐项配对，要求调用方保证配对顺序正确。
- `ks`：两组分布比较，不提供均值差的 t 置信区间。

多指标使用 Bonferroni 校正，报告原始/校正 p 值、均值差、样本量；t 检验另报标准化效应量和同步校正的置信区间。Welch 使用合并标准差作为描述性效应量，配对检验使用差值标准差。

`NO_DIFFERENCE_DETECTED` 只表示没有检测出差异，不能解释为等效或业务 PASS。样本独立性、重复测量、检验功效、指标方向及业务容忍度仍需要实验设计。常量样本导致 t 推断退化时，代码明确报错。

## 10. 学习飞轮从专家标签开始

在 Python 中构建一个明确确认的反馈：

```python
from pathlib import Path
from learning import ExpertReview, export_reviews

review = ExpertReview(
    task_id="demo-review-001",
    query="请判定本次切换测试",
    original_answer="PASS：测试正常",
    corrected_answer="FAIL：采集到的丢包率超过业务阈值",
    reviewer="人工审核者",
    confirmed=True,
)
print(export_reviews([review], Path("artifacts/reviews-001")))
```

`sft.jsonl` 保存 system/user/assistant 消息，学习正确回答；`dpo.jsonl` 保存文本 prompt/chosen/rejected，让模型学习同一问题下的偏好。两种格式与现有 `training/clean_data.py` 的主要契约兼容。

未确认反馈被过滤，同一任务相同反馈去重，冲突反馈报错；正负回答一致时仅输出 SFT。已有文件不会被覆盖。审核者和任务 ID 留在元数据中供追溯。

这些样本只是数据入口，还需要脱敏、质量审核、按任务划分训练/验证集、训练和独立评测。原有 `training/`、`training_llamafactory/` 保留作训练参考，本轮没有下载模型或执行 SFT/DPO，也没有声称模型已得到提升。

## 11. 如何用测试真正学会系统

```powershell
uv run pytest tests -q
uv run pytest tests/test_workflow.py -vv
uv run python offline_evaluation.py
```

先看每个测试中的“输入 → 执行 → 断言”，再读对应节点。建议做以下练习：

1. 在沙盒里把丢包率调到 0.02，预测结果，再运行回归测试。
2. 在模型请求中替换 session_id，观察工具返回的错误消息和缓存变化。
3. 去掉成功后清零连续错误的语句，观察哪条测试发现问题。
4. 将 Worker 结果改为 INCONCLUSIVE，检查整体结论和签发标记。
5. 把专家反馈的 confirmed 设为 False，检查导出数量。

`offline_evaluation.py` 运行同一张真实图上的四个固定场景，检查结论、动作顺序和人工介入。它验证工程行为；真实模型的泛化能力、工具选择质量和延迟费用，需要单独构建冻结评测集并运行在线实验。

原有 `eval_system.py` 仍包含模拟轨迹和模拟 Judge 入口，其演示分数不能当成系统实测指标。`evaluation.py` 是可选在线 LangSmith 入口，需要密钥；本地测试不会向云端写入评测数据。
