# 怎样把专家排查方法写成 Skill

这里的 Skill，可以先理解成一份给 Agent 看的工作说明。

例如，专家知道查“移动视频卡顿”通常要先确认哪些信息、看哪些记录、怎样区分设备和服务问题。把这些经验写清楚，模型遇到合适任务时再读，就不必每次从零开始。

## 一份说明应该写什么

先写适合什么问题，以及什么情况下不适用。

然后写需要哪些信息和工具、常见的几种解释、建议比较什么、怎样看结果、什么时候需要停下来找人。

最后给出报告应该包含什么，并附上资料来源和版本。

它不应只写“先读日志，再找根因”。更实用的写法是：

> “如果设备切换记录正常，但业务发生停顿，核对是否同一终端、同一时间；再检查业务恢复是否晚于设备连接完成。”

## 为什么不要一次把所有说明都塞给模型

设备、故障和版本多了，说明会越来越长。全部放进去，既花钱，也容易用错。

可以先给一个简短目录。模型发现当前问题适合“移动业务异常”这一项，再读取正文，需要时继续查相关资料。

这就是按需加载。原来叫“渐进披露”，在这里实际做的就是先看目录，再读相关部分。

## 可以先整理哪些说明

先选最常用的几种：普通测试准备、移动业务异常、偶发问题复核、复现步骤简化、原因检查、修复验证。

一项调查可能先用复现说明，后用简化说明，等修复来了再用验证说明。不需要每份说明都配一个独立 Agent。

如果某段步骤已经完全固定，也可以写进程序，直接执行。

## 说明、资料和工具怎么配合

说明告诉模型怎样开展工作；资料提供事实、规则和历史记录；工具负责真的查询和操作。

写了“运行测试”不代表获得运行权限。说明中附带脚本，也不表示脚本可以直接执行，仍需按应用规则检查。

用户只要求读报告时，模型不能因为读到一份排查说明，就自行启动测试。

## 读了说明，也要根据结果调整

历史方法是参考。当前结果不支持原来的猜测，就换方向；设备版本不适用，就找其他办法。

例如以前的卡顿由资源问题引起，这次仍要检查本次记录，不能照抄原因。说明里最好写出哪些情况会否定原来的方向。

## 文档怎样保存

可以用 SKILL.md 保存正文，旁边放参考资料、例子和已经验证的脚本。实际宿主是否自动发现和加载，需要实现时确认。

记录每份说明的版本、来源和适用设备。修改时保留原因，已开始的调查也记下当时读的是哪一版。

从外部取得说明时先审查。里面的文字不能要求跳过权限、隐藏失败结果或删除不符合猜测的数据。

## 怎么知道这些说明有帮助

让模型分别在没有说明、只有资料检索、有说明三种条件下处理相近任务。

看实验安排有没有更合理，追问和人工接手有没有减少，是否仍能识别不适用情况。输入变短只是附带收益，不能为了省内容删掉关键要求。

第一版少写几份、认真验证，通常比一下建一个庞大目录更容易检查效果。
