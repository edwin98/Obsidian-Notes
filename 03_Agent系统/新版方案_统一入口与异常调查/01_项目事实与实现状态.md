# 目前做到了哪里

目前完成的是这套新方案文档。还没有按新方案修改代码、连接真实设备、训练模型或跑效果对比。

原项目已有的东西能复用多少，需要对照实际接口和运行记录检查。旧文档里写过某项设计，不等于现在就能直接使用。

## 哪些东西准备沿用

原来查询用例、启动仿真、采集指标、分析日志、比较旧版本、暂停恢复和生成报告的思路都可以保留。

新版主要改变这些能力的使用方式。以前选好测试就执行；现在还要根据结果决定是否改条件、重跑或补查。

例如，日志工具原来分析一次失败日志；新版可能先比较两组测试，再只查异常发生前后的相关日志。

## 哪些是这次新增的设计

统一入口要听懂新建、修改、查询、暂停、继续和取消。排查过程要记录每轮为什么测、改了什么、结果说明什么。复现以后，要能尝试删掉无关步骤，再重新验证。

原因分析也要写得更准确：哪些是看到的现象，哪些是怀疑，哪些已经有实验支持。

最后，修复验证要接着原问题往下做，不能换一套条件跑通就说修好了。

这些内容目前都在方案阶段，不能写成已经完成的功能。

## 后面怎样记录进度

可以按下面几步记录，但每一步都要写清环境：

| 进度 | 应该能拿出什么 |
| --- | --- |
| 方案已确定 | 采用哪些做法、第一版做到哪里 |
| 演示已跑通 | 模拟输入、程序版本和完整运行记录 |
| 真实工具已接通 | 平台、参数、实际返回和失败处理记录 |
| 小范围试用有效 | 真实任务、人工对照、耗时和问题 |
| 已投入使用 | 明确设备、场景、版本和日常运行记录 |

模拟演示证明流程能走通，真实工具测试证明接口能工作，实际试用才能回答是否减少了人工。这几件事分别记录。

## 原来的数字怎样处理

原文档里的模型规模、训练条数、显卡数量、训练时长和效果数字，继续属于原来的记录。

新方案没有实际测过，就不沿用那些数字。尤其不能把“旧系统跑测试更快”直接变成“新系统排查问题更快”。

模型自报的一个分数，也不能解释成“原因有这么大概率是对的”。

## 每次验证留一条简单记录

记录做了什么、在哪个环境做、使用什么模型和程序、输入是什么、工具实际返回什么、结果如何、还缺什么。

比如：

> “在实验室 A，用指定版本运行连续切换场景。已接通业务监测，但还不能读取设备内部资源，因此只能验证复现，暂时不能确认资源处理原因。”

这样的记录比“异常定位模块已完成”更有用。
